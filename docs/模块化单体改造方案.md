## 1. 背景、结论与目标

### 1.1 背景

本系统目前承载 SN 管理，后续还要承载箱号管理、托号管理等需求（见 `new.md` 与侧栏「箱号管理」「托号管理」占位页）。现在 web 与 api 一起构建、一起发版，大家担心新需求加进来以后，容易改坏已有的 SN 功能。

### 1.2 结论

**改错代码的根源在代码内部没有模块边界，不在部署方式。**

- 部署上 web 与 api 已经是两个镜像（`sn-center-web`：nginx 托管前端；`sn-center-api`：FastAPI），只是放在同一个 `docker-compose.yml` 里一起发版。
- 即使拆成两个仓库、分别部署，箱号功能改坏了公共代码（订单、号池、权限），SN 照样出问题。
- 真正的风险在后端：业务服务平铺在一层、相互引用（还有循环依赖），核心表被多个服务直接写 SQL（见第 2 章）。

所以先做**模块化单体**：按业务域划边界，用工具强制执行；等确实需要独立部署时，再按已经划好的边界拆服务（第 13 章）。

### 1.3 目标（可验收）

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 新增箱号 / 托号模块时，不修改 SN 模块的任何文件 | 箱号模块的 PR 里，`app/modules/sn/**`、`frontend/src/modules/sn/**` 没有改动 |
| G2 | 模块依赖单向、无循环 | CI 中 `lint-imports` 通过，没有忽略清单 |
| G3 | 每张表只有一个模块写入 | 第 5.2 节的归属表在 CI 中校验（脚本扫描 `INSERT / UPDATE / DELETE`） |
| G4 | 改造过程中业务行为不变 | 现有 270 个自动化测试一直全绿，断言不改，只改 import 路径 |
| G5 | 合并前自动拦截问题 | GitHub Actions：ruff、import 契约、pytest（MySQL）、前端测试与构建；不通过不能合并 |

### 1.4 不做的事

- 不拆微服务，不引入消息队列、服务注册、分布式事务。
- 不换技术栈（仍是 FastAPI + PyMySQL + MySQL 8，Vue 3 + Element Plus）。
- 不改业务规则、接口路径与返回结构、MES 对接协议。
- 开发阶段仍**只保留一个完整的建表脚本 `V1__init.sql`**（见第 9 章），不出现「先建表、再用别的脚本补字段」。

- `sn-center-python-v2` 已把侧栏菜单按模块分组（工单、SN、箱号、托号、日志、账户、组织），页面路径不变。前端的模块划分可以直接沿用。

## 3. 方案概述

### 3.1 什么是模块化单体

**一个仓库、一个部署单元**，内部按业务域分成模块。每个模块：

- 拥有自己的代码（路由、服务、模型、错误码、前端页面、词条）；
- 拥有自己的表（只有它能写）；
- 通过一个**公开接口**（`api.py`）对外提供能力，其他模块只能调这个接口；
- 可以通过开关整体启用 / 停用。

模块之间的依赖方向是固定的，并且由工具在 CI 里检查。

### 3.2 业界做法

| 案例 | 做法 | 借鉴点 |
| --- | --- | --- |
| Shopify（Packwerk） | 巨型 Rails 单体按 package 划边界，声明公开接口，CI 检查违规引用 | 先登记现有违规，再逐步清零 |
| Spring Modulith | 包即模块，`ApplicationModules.verify()` 检查依赖；模块间用应用内事件 | 同步、同事务的应用内事件 |
| ABP / .NET 模块化 | 每个模块自带路由、服务、表与注册类 | 模块注册机制 |
| Python：import-linter | 在 `pyproject.toml` 声明分层与禁止引用的契约，`lint-imports` 检查 | 本方案的检查工具 |

### 3.3 与方案 B（微服务）的比较

| 维度 | 方案 A：模块化单体 | 方案 B：按域拆微服务 |
| --- | --- | --- |
| 改造成本 | 低：目录搬迁 + 收口跨域调用 | 高：服务拆分、接口化、数据拆库 |
| 一致性 | 单库事务，箱号装 SN、托号装箱号可以在一个事务里完成 | 跨服务需 Saga / 补偿，重复装箱等问题更难防 |
| 运维 | 不变（2 个镜像 + 1 个库） | 多服务、多库、服务间鉴权、链路追踪 |
| 隔离程度 | 代码级（CI 强制） | 进程级 |
| 适合 | 当前团队规模、中等并发、强一致的号段业务 | 多团队各自负责一个域、需要独立扩容或独立发版 |

当前业务是「号不能重复、不能丢」的强一致场景，团队规模也不大，**选方案 A**。转向方案 B 的条件见第 13 章。

## 4. 目标结构

### 4.1 后端

```
app/
  main.py                    只做装配：加载启用的模块，挂路由、启动任务、注册异常处理
  platform/                  公共底座（任何模块都可以用；底座不能引用业务模块）
    config.py  logging.py  errors.py（错误基类与 biz()）  exceptions.py  security.py  secretbox.py
    db/                      连接池、事务、迁移（migrate.py、migration/V1__init.sql）
    http/                    deps.py（鉴权依赖、分页、下载）、middleware/request_id.py
    audit.py                 写操作痕迹（sn_audit）
    locks.py                 MySQL 命名锁（PI 锁、组织锁、同步锁）
    scheduler.py             定时任务
    events.py                应用内事件（同步、同事务，见第 7.3 节）
    files.py  metrics.py（sn_daily_counter）  maintenance.py（分区、归档、清理）
    integrations/
      k3.py                  金蝶 WebAPI
      mes_client.py          MES HTTP 客户端
    module.py                模块描述 Module 与加载器（见第 8 章）
  modules/
    org/                     组织管理 + 账户管理
      api.py                 对外公开接口
      routes/  services/  schemas/  errors.py  module.py
    order/                   工单管理：生产订单快照、订单变更提醒、物料行补录
    sn/                      SN 管理
      api.py
      rule/  generate/  allocation/  delivery/  transfer/  query/
      errors.py  module.py
    log/                     日志管理：操作日志查询与导出（写痕迹在 platform.audit）
    dashboard/               首页看板：只读汇总，可依赖所有业务模块的 api.py
    box/                     箱号管理（新）
    pallet/                  托号管理（新）
tests/
  platform/  modules/org/  modules/order/  modules/sn/  ...   conftest.py 拆为 fixtures/
```

### 4.2 前端

```
frontend/src/
  platform/                  layouts、api/http.ts、stores/auth.ts、i18n、通用组件（PageHead、FactorySelect、StatusTag …）
  modules/
    order/   { views/, api.ts, types.ts, menu.ts }
    sn/      { views/（generate、allocate、export、transfer、query、rules）, components/batch, api.ts, types.ts, menu.ts }
    box/     { … }
    pallet/  { … }
    log/  account/  org/  dashboard/
  router/index.ts            用 import.meta.glob('../modules/*/menu.ts') 自动收集菜单与路由
frontend/scripts/
  ui/<模块>.py               词条源按模块；error_messages 按模块
```

**页面路径不变**（`/orders`、`/generate`、`/rules` …），书签与页面间的链接继续可用。

### 4.3 依赖方向

```
                 dashboard（只读汇总）
                     │
     pallet ──► box ──► sn ──► order ──► org
                     │       │        │
                     └───────┴────────┴──► platform（底座）
                 log ─────────────────────► platform
```

- 箭头表示「可以引用」。**只能从上往下、从左往右**，反方向一律禁止。
- `sn` 不知道 `box` 的存在；箱号需要 SN 的能力时调 `sn.api`，SN 需要通知箱号时发事件（第 7.3 节）。
- `platform` 不能引用任何业务模块。

## 5. 模块划分与数据归属

### 5.1 模块职责

| 模块 | 职责 | 由现有代码迁入 |
| --- | --- | --- |
| `platform` | 配置、日志、数据库、鉴权、操作痕迹写入、锁、定时任务、维护、外部系统客户端 | `core/*`、`db/*`、`middleware/*`、`api/deps.py`、`services/audit.py`、`locks.py`、`files.py`、`partitions.py`、`k3.py`、`mes_client.py` |
| `org` | 生产组织（金蝶同步、MES 对接配置）、账户与角色、登录 | `services/factories.py`、`services/users.py`、`routes/factories.py`、`routes/users.py`、`routes/auth.py` |
| `order` | 生产订单快照与同步、订单变更提醒、单据台账、物料行补录（附件项次、米数、单位）、生产部门 | `services/orders.py`、`services/changes.py`、`routes/orders.py` |
| `sn` | 规则库、生成与撤销、分配、交付（推送 / 拉取 / 回执 / 人工处理 / 自检）、转单与转组织、SN 查询与导出、MES 接口 | `rules.py`、`generate.py`、`workbench.py`、`allocation.py`、`delivery/`、`transfers.py`、`query.py`、`sn_export.py`、`sn_sheet.py` 及对应路由（含 `routes/mes.py`） |
| `log` | 操作日志查询、导出 | `services/audit_query.py`、`routes/audits.py` |
| `dashboard` | 首页统计 | `services/dashboard.py`、`routes/dashboard.py` |
| `box` / `pallet` | 箱号、托号（新） | — |

### 5.2 表的归属（只有归属模块能写）

| 模块 | 拥有的表 |
| --- | --- |
| `platform` | `sn_audit`、`sn_audit_archive`、`sn_daily_counter`（只通过 `platform.metrics.count_daily()` 写） |
| `org` | `sn_factory`、`sn_user`、`sn_user_factory` |
| `order` | `sn_prd_mo`、`sn_sync_state`、`sn_bill_ledger`、`sn_bill_ledger_line`、`sn_order_alert`、`sn_line_attach`、`sn_line_length`、`sn_line_unit` |
| `sn.rule` | `sn_rule`、`sn_rule_version`、`sn_pi_rule`、`sn_line_rule` |
| `sn.generate` | `sn_gen_job`、`sn_gen_preview`、`sn_pi_counter`、`sn_line_count`、`sn_item`（号池，由 `sn` 模块统一写入） |
| `sn.delivery` | `sn_seq`、`sn_delivery_batch`、`sn_delivery_item`、`sn_delivery_receipt`、`sn_delivery_alert`、`sn_push_task`、`sn_rate_counter`（MES 拉取限流） |
| `sn.transfer` | `sn_transfer`、`sn_transfer_item`、`sn_bill_transfer` |
| `box` / `pallet` | 新表用 `box_` / `plt_` 前缀 |

**读**：同一个库里的跨模块读（如 SN 查询关联订单快照显示物料信息）开发阶段允许，但只能读、不能写。上线后高频的跨模块读，改为调用对方 `api.py` 或使用对方提供的视图。

**写**：只有归属模块能对它的表做 `INSERT / UPDATE / DELETE`。`sn` 模块内部的子包（rule、generate、delivery、transfer）之间可以互相写，对外仍是一个模块。

### 5.3 需要收口的跨模块写入

| 现在的写法 | 位置 | 改为 |
| --- | --- | --- |
| 订单变更直接改号的暂停标记 `UPDATE sn_item SET suspend …` | `changes.py`（order） | order 发事件 `BillSuspendChanged(bill_no, suspend)`，sn 订阅后在同一事务内更新号池 |
| 订单变更调用交付、转移 | `changes.py` 函数内 import `delivery`、`transfers` | 同上，sn 订阅订单事件；order 不再引用 sn |
| 组织开关 MES 时改号状态、删推送任务 | `factories.py`（org）→ `sn_item`、`sn_push_task` | org 发事件 `MesToggled(factory_code, enabled)`，sn.delivery 订阅处理 |
| 推送回写组织的配置状态 | `delivery/push.py` → `sn_factory` | 调 `org.api.set_mes_cfg_status(code, ok, message)` |
| 订单页显示生效规则（`orders` → `rules`） | `orders.lines_of` | 规则是 SN 的概念：订单接口只返回订单数据；生效规则由前端再调 sn 接口取，或由 sn 提供「订单行 + 规则」的组合接口 |
| 规则读订单物料行（`rules` → `orders`） | `rules.py` 函数内 import | 调 `order.api`（sn 依赖 order，方向正确） |
| 按天计数 `count_daily` 写在订单模块里，交付模块也调用 | `changes.py`（被 `orders`、`delivery.pull` 调用） | 移到 `platform/metrics.py` |
| 每日维护顺带清理 SN 的表（过期预演 `sn_gen_preview`、限流计数 `sn_rate_counter`） | `partitions.py`（底座）→ SN 的表 | 底座只管分区与痕迹归档；SN 模块注册自己的每日清理任务（第 8.1 节 `jobs`） |

收口以后，第 2.2 节的循环依赖全部消失。

## 6. 边界规则

| # | 规则 | 怎样检查 |
| --- | --- | --- |
| R1 | 依赖只能按第 4.3 节的方向；`platform` 不能引用业务模块 | import-linter `layers` 契约（附录 B） |
| R2 | 跨模块只能引用对方的 `api.py`（和 `events` 里的事件类型），不能引用 `services/`、`routes/` | import-linter `forbidden` 契约 |
| R3 | 只有归属模块能写自己的表（第 5.2 节） | `devtools/check_table_owners.py` 扫描 SQL 写语句，在 CI 运行 |
| R4 | 新表用模块前缀（`box_`、`plt_`）；现有 `sn_` 表不改名 | 代码评审 + 建表脚本检查 |
| R5 | 错误码归属模块，前缀区分（如 `BOX_`、`PLT_`），不改已有错误码 | `test_every_error_code_translated` 扩展为按模块收集 |
| R6 | 前端模块之间不能互相 import 内部文件，只能用 `platform/` 和对方导出的组件 | ESLint `no-restricted-imports`（或 `eslint-plugin-boundaries`） |
| R7 | `api.py` 的函数视为对外契约：改签名或语义要同步改调用方并补契约测试 | `tests/modules/sn/test_api_contract.py` |

**违规登记**：引入检查时，现有违规先写进忽略清单（`ignore_imports`），新代码不得增加。每个阶段结束时清单只减不增，到阶段 2 结束清零。

## 7. 模块间怎样协作

### 7.1 公开接口 `api.py`

公开接口只暴露其他模块需要的能力，参数和返回值用普通的 `dict` / dataclass，不暴露表结构。示例（SN 模块给箱号模块用）：

```python
# app/modules/sn/api.py
"""SN 模块对外接口：其他模块只能调这里。签名或语义变更须补 tests/modules/sn/test_api_contract.py。"""

from app.modules.sn.generate import pool


def sn_status(sns: list[str]) -> dict[str, str]:
    """SN → 当前状态（不存在的不返回）。"""
    return pool.status_of(sns)


def bind_container(cu, sns: list[str], kind: str, container_no: str) -> None:
    """把 SN 标记为已装入箱 / 托（同一枚号只能装一次，已装的整批拒绝）；须在调用方事务内调用。"""
    pool.bind_container(cu, sns, kind, container_no)
```

### 7.2 事务

模块之间的调用都在**同一个进程、同一个数据库事务**里完成（沿用 `db.tx()`）。这是选择单体的主要原因：例如「订单变更 → 暂停交付 → 停推送」现在在一个事务里完成，改造后仍在一个事务里完成。

### 7.3 应用内事件（反方向通知）

下游模块需要通知上游时（例如订单变化要影响 SN），**不能反向 import**，改为发事件：

```python
# app/platform/events.py
"""应用内事件：同步分发，在发布方的事务内执行；订阅方抛错则整个事务回滚。不是消息队列。"""

from collections import defaultdict
from collections.abc import Callable

_subs: dict[type, list[Callable]] = defaultdict(list)


def subscribe(event_type: type, fn: Callable) -> None:
    _subs[event_type].append(fn)


def publish(event: object) -> None:
    for fn in _subs[type(event)]:
        fn(event)
```

```python
# app/modules/order/events.py：order 模块定义并发布
@dataclass(frozen=True)
class BillSuspendChanged:
    bill_no: str
    suspend: str | None      # None = 解除暂停

# app/modules/sn/module.py：sn 模块启动时订阅
events.subscribe(BillSuspendChanged, generate.pool.on_bill_suspend_changed)
```

约定：

- 事件是**同步、同事务**的，行为与现在的直接调用完全一致，只是依赖方向反过来；
- 事件类型由发布方定义，订阅方 import 发布方的 `events.py`（方向正确：sn → order）；
- 不做异步、不落库、不重试。真需要异步时（如通知外部系统），沿用现有的推送任务表机制。

## 8. 模块注册与功能开关

### 8.1 后端注册

每个模块提供一个 `module.py`，声明自己的路由、启动步骤、后台任务和依赖：

```python
# app/platform/module.py
@dataclass(frozen=True)
class Module:
    name: str                                   # "sn"
    depends_on: tuple[str, ...] = ()            # ("order", "org")
    routers: tuple[APIRouter, ...] = ()
    startup: tuple[Callable[[], None], ...] = ()      # 如 generate.recover_interrupted
    jobs: tuple[Callable[[], Job | None], ...] = ()   # 如 delivery.start_scheduler
    subscribe: Callable[[], None] | None = None       # 注册事件订阅
```

`main.py` 只做装配：按 `SN_MODULES` 读取启用的模块 → 检查依赖都已启用 → 按依赖顺序执行 `subscribe`、`startup` → 挂路由（前缀仍为 `/api`，路径不变）→ 启动任务。现在 `main.py` 里的启动顺序（检查密钥 → 建表 → 回收中断的生成任务 → 建管理员 → 维护分区 → 演示数据）保持不变，只是从写死改成由各模块声明。

### 8.2 功能开关

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `SN_MODULES` | `org,order,sn,log,dashboard` | 启用的模块。箱号、托号开发期间正式环境不加，测试环境加上 `box,pallet` |

模块未启用时：它的路由不挂载，后台任务不启动，菜单不显示（前端从 `/api/auth/me` 返回的 `modules` 判断）。开启 `box` 时必须同时开启它依赖的 `sn`，否则启动报错。

### 8.3 前端注册

每个前端模块提供 `menu.ts`：

```ts
// frontend/src/modules/box/menu.ts
export default {
  module: "box",
  group: { title: "nav.groupBox", icon: "Box" },
  items: [
    { path: "/box/generate", title: "nav.boxGenerate", icon: "Finished", roles: OPS, view: () => import("./views/BoxGenerate.vue") },
  ],
} satisfies ModuleMenu;
```

`router/index.ts` 用 `import.meta.glob("../modules/*/menu.ts", { eager: true })` 收集菜单与路由，按 `modules` 开关过滤，**不再手工维护 `MENU` 与 `views`**。

## 13. 何时考虑方案 B（拆服务）

出现以下任一情况再评估把某个模块拆成独立服务。因为边界已经划好，拆的就是一个模块：

- 某个模块需要独立扩容（如 MES 推送 / 拉取量远超其他功能），单进程已经撑不住；
- 不同团队各自负责不同模块，发版节奏互相阻塞；
- 某个模块需要不同的技术栈或运行环境；
- 合规要求某些数据物理隔离。

拆分时：模块的 `api.py` 变成 HTTP 接口，事件改为消息，模块拥有的表迁到独立库。没有跨模块写表，拆库才可行，这正是第 5 章要先做到的。

| 术语 | 含义 |
| --- | --- |
| 模块 | 一个业务域的全部代码、表、页面、词条的集合，如 `sn`、`box` |
| 底座（platform） | 所有模块共用的基础能力，不含业务规则 |
| 公开接口（`api.py`） | 模块对外提供的唯一调用入口 |
| 应用内事件 | 同进程、同事务、同步分发的通知，用于反方向通知，不是消息队列 |
| 归属模块 | 唯一有权写某张表的模块 |

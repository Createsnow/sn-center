## 双端界面结果

新增 4 个场景，原型与新版各执行一次，共 8 项。订单同步、选单、预演、生成、分配、历史切换和刷新均通过页面完成；本机合成 K3 与专用夹具提供订单和规则，数据库只辅助核对成员、身份及清理测试数据。

| 场景 | 两边一致的实际结果 |
| --- | --- |
| 改 PI 后使用不重叠流水 | 首次 PI 生成 3 枚，新 PI 从 10 再生成 2 枚；顶部累计 5，新 PI 汇总生成 0；分配首批 3 枚保留原成员 |
| 改 PI 后从 1 重新起号 | 先生成 IDA1—3，再生成 IDB1—2；首批实际选中 IDA1、IDB1、IDA2，余量为 IDB2、IDA3；分配历史首尾分别为 IDA1～IDA2、IDB2～IDA3 |
| 退出及返回当前快照 | 已生成订单以历史行保留，计划量/额度为 0；未生成订单退出后不显示；已生成订单返回后恢复当前计划与额度，累计不丢失 |
| 未映射组织 | 只列同组织、同 PI 的当前订单，不混入已映射工厂的同 PI 单据；预演按钮禁用，提示先到工厂页同步 |

改 PI 后，成员各自的实际 PI、客户和来源保持不变，分配记录仍使用首次生成 PI/客户。查看旧 PI 的兄弟订单时，原单作为历史行显示整单累计，刷新后结果不变。跨前缀的分配首尾是实际成员边界，不能据此推算连续字符串号段。

## 修正内容

原型使用自增成员 ID，在本机 MySQL 8.4 的双端操作中，相同流水优先分配先生成的成员。新版原查询为 `seq_dec,id`，随机 UUID 可能让后生成成员排在前面。首次 8 项页面检查碰巧通过，因此增加一次性集成库的确定性回归：真实生成两批后，将旧批 UUID 排在新批之后。旧实现稳定选中 G1/H1/H2，预期为 G1/H1/G2，见[修复前证据](evidence/parity-20261008-stage11/ordering-before-fix.json)。

提交与执行现统一按 `seq_dec,created_at,id` 选择固定成员，V29 重建对应待分配索引，不改任何业务行。测试同时核对首批与余量、首尾记录、来源额度和 SN 唯一护栏；固定成员、事务及权限检查继续保留。V1—V28 字节不变。

候选框去掉原型远程搜索框没有的后缀箭头，避免客户编码被挤成省略号；选项之间使用同类箭头。未映射工厂提示补全原型的同步指引，并对齐错误提示颜色、背景与间距。中、英、越三语均在两边切换并检查，结束后恢复中文。

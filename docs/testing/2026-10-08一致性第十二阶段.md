# 第十二阶段 起始号与历史导入界面检查

本阶段对齐 P08 的查询、初始化表单、确认、成功刷新和历史记录，并通过两边真实页面检查六组操作。一次 12 项双端回归通过；随后完善截图的动画等待，对三语查询和确认场景追加 2 项复查。完整 P01—P16 目标仍在执行，P08 的异常、资源边界、恢复和角色组合也未全部验收。

## 已对齐的操作

| 场景 | 双端实际检查及结果 |
| --- | --- |
| 查询与切换 | 空查询不提交；编辑输入框不改变上次结果；明确查询后切换 PI；有规则和无规则状态、客户提示、表单保留、刷新后清空入口一致 |
| 纯起始号 | 空表单禁用；0 和小数显示正整数提示；重复清单显示数量并阻止提交；`1e1` 确认为 10；取消不产生初始化记录；确认后水位为 9、起始号为 10，禁止再次初始化 |
| 混合清单 | `INI00000`、`INI00005`、`UNPARSED` 导入 3 个、反解 2 个；起号 20 使水位为 19，导入最大流水仍为 5；默认取订单客户，工厂和物料按选择保存 |
| CSV 与手工修改 | 只读取首列、跳过标题；单引号及不成对双引号作为号码原文保留；上传后编辑文本仍保留文件名；无规则导入的流水为空，水位为 0 |
| 仅导入及继续操作 | 无起号导入 `INI00008` 和未解析号码，水位为 8；成功后只清空起号和清单，保留工厂、客户、物料，再查询另一 PI 设置起号 |
| 已有生成记录 | 原基线 PI 保持锁定；其显式起始号为空，提示显示“—”；不虚构初始化历史；中、英、越三语均检查 |

所有导入成员均核对为 `PRINTED / IMPORT`。两边的号码、实际 PI、来源 PI、流水、客户、物料、工厂、计数器和成功历史形成 19 组配对快照，排序归一化后逐字段相同。初始化、全量同步及确认均经页面按钮执行；建规则和读取核对值使用隔离环境的辅助脚本。

## 实现调整

新版采用与原型一致的查询状态区、单列表单和成功历史列。正常完成时显示导入数量、反解数量及当前最大号，刷新当前查询并隐藏已锁定 PI 的初始化表单。持久任务继续保留在后端，成功记录显示工厂编码、文件名、操作工号和时间。

清单解析只移除成对双引号，修正单引号或未闭合引号被删改的问题。起号支持原型常用的前导零、小数形式的整数、指数和进制前缀输入，使用精确字符串归一化；`9007199254740993` 等业务值不经过浮点转换。无效值和超出 long 范围的值仍被拒绝，完整范围的兼容检查继续纳入 P08/P16。

查询、上传及执行按钮有稳定的无障碍名称。确认弹窗补齐原型组件使用的三语按钮文案、居中位置、宽度、关闭和取消操作。状态区、表单间距、上传图标、提示及历史表格也按原型调整。已复核三语表单、确认弹窗、900 像素宽度和完成结果截图；这些截图不代表所有页面或所有像素已完全一致。

## 数据保护与剩余检查

测试只使用 MySQL 33308 中的两个比较库、Redis 36380 和本机合成 K3。清理前检查合成 PI、号码集合、规则绑定、终态任务及下游引用，发现不明引用即保留数据。每个场景通过页面恢复订单快照，再清理声明归属的合成业务数据；真实任务和审计记录保留。

结束时恢复 3 张订单、4 条分录、10 枚基线 SN 和 3 个规则；定时关闭、间隔 1440 分钟，K3 附加订单和控制为空。原成员、唯一性护栏、计数器、规则、额度、历史身份及账号安全字段未变，生成、分配、领取和打印累计也未改变。Java 比较库仍为 V29，两个服务继续运行。Python 源码、原有业务库、公司 ERP 和 GitLab 未改动。

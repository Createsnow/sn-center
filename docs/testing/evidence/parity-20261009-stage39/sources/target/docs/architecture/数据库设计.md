# 当前数据库设计

维护日期：2026-10-04。本文为当前说明；本轮规则见[SN补迁契约](../business/SN补迁契约.md)，验证和未完成项见[当前发布记录](../releases/2026-10-04本地交付.md)。历史阶段原文已另行冻结归档。

目标为独立 MySQL 8.4 schema adtek_sn_test。默认 utf8mb4 / utf8mb4_0900_as_cs，连接与持久时间为 UTC，时间字段 DATETIME(6)。内部身份使用有符号 BIGINT，自增用户/角色/部门 ID；JSON 统一字符串。用户名 ASCII 工号、区分大小写，不规范化后再比较。

| sys_role | role_code 唯一；data_scope=1—5 的 CHECK；factory_scope=1 指定工厂/2 全工厂 |

| sys_user_role / sys_role_menu / sys_role_dept | 关联复合主键，当前初始化与认证读取使用 |

| sys_oper_log | 账号/管理/入口失败审计；主体及部门/工号快照、模块/类型/动作/对象/结果/JSON diff/traceId/UTC 时间；入口失败另存 HTTP 方法、路由模板、状态及受控错误码 |

DataScopeType 对应 1=全部、2=自定义部门、3=本部门、4=本部门及下级、5=仅本人。未知编码拒绝。部门与生产工厂独立，不加无隔离能力的 tenant_id。当前关联没有数据库外键；管理 Service 在协调事务中验证关系、拒绝循环与无效父节点并维护版本，不开放通用 BaseMapper 接口。部门祖先由 parent_id 递归推导，不另存易失配的 ancestors 字符串。自定义授权只装配启用部门；移动部门重算树范围。存在启用子节点或启用用户的部门不能停用，存在启用子节点的菜单不能停用。

V1__system_foundation.sql 创建基础表。V2__identity_authorization_and_audit.sql 新增语言、工厂范围、审计与初始化控制，种入角色/权限而不种账号。V3__user_management_audit.sql 新增 module_name/business_type 和用户部门分页索引。V4__system_configuration.sql 增加配置版本、菜单自增、字典及权限。V5__audit_query_and_request_failures.sql 增加审计快照、HTTP 元数据及索引。V6__durable_operations_tasks_and_files.sql 增加持久操作/任务/文件和审计导出快照，种入 system:audit:export 并递增既有平台角色账号 security_version。V7增加SN业务基础，详见下节。已交付迁移 V1—V19 保持原文，新增结构使用下一个未占用版本，禁止清库重跑冒充升级。

V5 的 actor_dept_id、actor_username 为追加时的身份快照；原有日志保持 NULL，不伪造历史部门。HTTP 方法/模板/状态/错误码同样可空，已有业务审计不补造 HTTP 字段。匿名或身份尚未验证的入口拒绝不记录来访者提供的账号、令牌或工号。应用仅开放查询接口，不开放审计编辑/删除；当前运行账号权限仍为既有 DML，不宣称数据库具备防篡改或归档完整性保证。

默认角色包括 PLATFORM_ADMIN、SN_HQ、FACTORY_OPERATOR、SN_QUERY_ALL、SN_QUERY_FACTORY。用户及独立角色/菜单/部门维护已实现；角色编码、菜单类型/权限标识及字典编码/值不允许原地改写。共享角色可编辑五类范围和自定义部门集合；授予权限需操作者拥有该权限的 ALL 部门范围，工厂范围另行比较。初始管理员通过受控命令关联角色，不依赖固定用户 ID 授权。工厂业务用例和资格端口已由S3实现；用户页通过资格端口校验显式绑定，不能接受越权工厂ID。

## V17 ERP精确计划量

`sn_order_entry.qty`和`sn_order_bill.total_qty`无损扩展为DECIMAL(23,4)，保留非负和long上界约束。`sn_order_bill.quantity_ready`表示所有有效分录均为整数；小数分录即使合计为整数也为false。旧整数自动保持true。SN计数、来源历史额度、流水和固定成员均不改为小数；Java用BigDecimal解析/存取，输出普通十进制字符串，禁止隐式截断。超出4位有效小数在SQL前拒绝。暂存/主数据/有限库存工具增加对17的精确版本识别，转换范围不扩大。

V22 保留 `sn_order_entry.qty` 原始精确小数，重算活动订单 `total_qty=SUM(FLOOR(qty))` 并置 `quantity_ready=TRUE`，不重置来源历史额度或已生成 SN。此后同步发布采用相同算法。V17—V21 的拒绝小数生成规则仅适用于对应历史版本；当前隔离比较库已应用 V22，原开发/HTTPS 库仍为 V17，见[第三阶段证据](../testing/2026-10-08一致性第三阶段.md)。

## V23 当前工作区：定时同步结果

`sn_order_sync_schedule` 新增可空 `last_ok` 与长度 500 的 `last_error_message`。升级按已有 SUCCESS/FAILED 状态回填成败，未运行或正在执行且无法还原上一轮结果时保留 NULL。开始新一轮仍更新执行编号、时间、状态和租期，但保留上一轮的成败、摘要和数量；成功清空错误，失败保留上次成功数量。更新结果继续匹配执行编号和 FETCHING 状态，不能由过期执行者覆盖新结果。

仅本机隔离比较库应用 V23；V1—V22 和既有开发/HTTPS 库保持不变。错误摘要在 K3 适配边界过滤连接秘密与凭据字段、清理控制字符，并限制 500 个 Unicode 字符；不存原始响应或异常堆栈。


## V24—V25 当前工作区：规则创建者与文本语义

V24 在 `sn_rule_version` 新增可空 `created_by_name`。新版本通过框架身份端口记录稳定工号，读取历史时不以可改显示名覆盖；已有可信用户按不可修改的 username 回填，缺失主体保持 NULL。创建主体 ID 字符串仍保留。

V25 将 `sn_rule.code/name/bind_scope/bind_value` 显式设为 `utf8mb4_bin`，与原型一致地进行大小写区分、字符排序及绑定/编码唯一性比较。避免部署库默认 `utf8mb4_0900_ai_ci` 改变业务语义。列表使用原型的 LIKE 通配符规则；分页排序补 ID 保证稳定。

仅比较库应用到 V25；既有开发、HTTPS 数据库和原型表结构保持原状。V1—V23 不改。本阶段证据见[规则目录验收](../testing/2026-10-08一致性第五阶段.md)。

## 2026-10-08 当前生成额度（无新 DDL）

`sn_source_entry_quota` 继续保留全部稳定来源行的历史生成、分配累计，包括已经离开当前快照的行。生成可用量按整单 `total_qty - SUM(全部历史 generated_qty)` 下限零计算；不再把各活动行分别扣减后的正余额相加。预演沿 ERP 返回行序跳过整单已生成数，已发 SN 的来源/物料不改写。发布和执行仍使用既有快照协调锁、PI 锁、固定命令及事务唯一性保护。无需清理历史台账或重算已发号码，SQL 版本保持 V25。

## V26 当前工作区：生成与分配操作工号

`sn_work.actor_name` 为提交时的可信工号快照，通过框架 `IdentityNamePort` 获取，不跨模块读取账户 Mapper。升级只回填仍有对应账号的历史记录，无法确定的保持 NULL。原 V1—V25 不改；仅独立比较库应用 V26，既有开发和 HTTPS 数据库仍保持原版本。

按数量分配复用 `sn_work.payload` 的固定成员及 `sn_item.allocation_id`，不引入第二套业务账本。提交固定最早 quantity 枚；执行对同一前缀逐项比对，成员、SN 状态、来源台账、任务结果及审计一起提交或回滚。当前排序按下述 V29 规则执行。

## V27 当前工作区：生成失败参数

`sn_work.error_params` 为可空 JSON，仅保存受控原因与精确字符串参数。生成失败工作器只接受 `GenerationErrors` 中与数字错误码对应的原因及字段，未知字段不入业务历史；其他处理器沿用原受控错误码。旧记录为 NULL，接口投影为 `{}`，不补造历史异常原文。原 V1—V26 不改，仅独立比较库应用 V27。

生成作业的计划号段来自提交时持久化的预演计划。未完成或失败且 `first_sn/last_sn` 为空时，读取使用计划的起止流水及编码规则投影；成功作业仍使用已提交结果。失败作业的界面 `processed=0`，框架执行代次进度保留为恢复诊断，不能表示已落库 SN。

## V28 当前工作区：整单历史生成身份

`sn_bill_generation` 以稳定 `bill_id` 为主键，保存首次成功生成的 `first_pi / first_customer / first_task_id`、最后成功生成的 `factory_id / last_task_id`。数量继续唯一保存在 `sn_source_entry_quota`，不再维护一份累计。身份、SN、额度、水位和成功审计在同一业务事务内提交；生成失败不建立或更新身份。

回填仅使用成功生成任务和按主体、操作号、PI、工厂、数量关联的成功审计，含 `sn_audit_archive`。首次客户必须有唯一可信值；缺失或矛盾时保留 NULL，分配拒绝，不从可变 ERP、预演客户或转厂后的成员推断。V1—V27 保持原字节。此次没有连接或搬迁原型业务数据。

PI 汇总先按当前 PI/生产组织名称列活动订单，再合并首次 PI/最后生成工厂匹配的历史订单。离开当前范围的历史订单计划量和额度为 0；无生成台账的非活动订单不进入汇总。不同 PI 的新生成不迁移首次台账归属，当前新 PI 汇总可以显示生成 0，而单据顶部仍显示整单累计，保持原型行为。

## V29 当前工作区 同流水分配顺序

ERP 改 PI 后，同一订单的新 PI 可以从 1 重新生成，待分配成员因此可能有相同 `seq_dec`。提交与执行统一按 `seq_dec,created_at,id` 选择固定前缀，相同流水先取早生成的成员，避免 UUID 字典序改变部分分配的实际号码及历史首尾。已有成员的实际 PI、客户和来源不变。

V29 将 `ix_sn_item_pending` 重建为 `(bill_id,status,seq_dec,created_at,id)`，不更新任何业务行。原 V1—V28 保持原字节。分配历史的首尾是实际排序后的第一枚和最后一枚，跨 PI 编码可能不构成同前缀连续号段，不得用首尾字符串重新推导固定成员。

## V30 当前工作区 初始化固定输入分块

`sn_import_chunk` 以 `(task_id,ordinal)` 为主键，每行保存 1—1000 条有序 SN 的 JSON 数组及数量。外键引用 `sn_work`，删除所属工作记录时级联清理；数组类型和数量由 CHECK 约束保护。任务、小型规范化输入、业务元数据和全部输入块在同一次登记事务内提交，不能留下可执行的半份清单。

新任务的 `sn_work.payload.sns` 为空；执行时逐块读取，核对连续序号、每块数量、总量和原有 v1 完整数组摘要。旧内联清单仍可执行，分块不改变操作幂等指纹。丢块或篡改使执行整批回滚；SN、查重键、计数器、规则使用、成功历史和任务终态仍在同一个业务事务中提交。分块输入不等于分批提交业务数据。

V30 只新增输入表，不搬迁旧工作载荷。V1—V29 保持原字节；V30 已应用于独立比较库，也进入冻结范围，下一迁移使用 V31。常驻开发库和原型库不随比较测试升级。

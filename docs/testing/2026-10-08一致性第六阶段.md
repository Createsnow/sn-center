## 修正的行为

- 生成上下文、PI 汇总、预演和实际执行统一按整单计算：`max(0, 当前各分录整数计划量之和 - 整单历史已生成量)`。旧实现逐行扣减历史量后相加，ERP 缩减、删除或替换分录时可能错误阻止生成，或多算可生成量。
- 分段在当前 ERP 返回行序上跳过整单已生成量，再切出本次数量。移除发布时按稳定分录内码的二次排序，使单据 View 和全量查询的实际返回顺序得到保留。同物料多行、空物料和各行小数仍分别处理。
- 稳定来源台账继续记录历史。原 SN 的物料、来源、号码和状态不随 ERP 变更重写；执行前仍复核预演和快照，并保留 PI 占用、权限、事务及完整 SN 双唯一保护。
- 生成页连续展示全部分录，移除 20 行页面分页器；分录数量显示可发 SN 的整数部分。订单页与 API 保留原小数，前端通过字符串提取整数部分，避免大数 Number 舍入。
- 回归发现首页“今日动作”的另一处来源差异：原型按成功审计统计，新版原先从生成、分配、领取和打印业务表汇总。现改为按成功业务审计统计五种动作，保持上海日期边界和当前工厂范围；业务任务清理后仍保留当天已经发生的操作数量。

## 双端按钮检查

`frontend/e2e/parity/generation-quota.spec.ts` 的三个场景在原型和新版分别执行，共 **6 项双端界面检查通过**。使用真实 Edge 登录、菜单、订单同步、选单、“去生成”、数量输入、预演、生成和确认按钮；同时读取真实落库 SN 核对结果。测试通过公共 API 准备专属 PI 绑定规则，没有用 API 代替待验收的生成按钮。

| 场景 | 相同输入与实际结果 |
| --- | --- |
| 缩减并替换分录 | 初始 13 枚先生成 5 枚；改为 `2.5 + 7.9` 后总计划 9、可生成 4，全部落在新物料 NEW；再替换成 `12.4` 后只能续发 3 枚。前 5 枚逐项保持原物料，最终共 12 枚，额度归零后预演按钮禁用 |
| ERP 返回行序变化 | 初始生成 5 枚；将原分录按 13、12、11 返回，数量为 `4.7、3.8、8.9`。跳过整单 5 枚后，本次 5 枚分别切成第 2 行 2 枚、第 3 行 3 枚，物料和连续流水一致 |
| 21 行小数订单 | 21 行各 `1.9`，全部分录同时展示，逐行显示 1；预演形成 21 段并实际生成 21 枚，各自保留对应物料，不把小数余量组合成额外号码 |

新增场景独立运行 6 项通过，原始结果保存在 `generation-browser-run.json`。**六阶段最终合并 62 项全部通过，没有自动重试**，耗时约 10.3 分钟；最终统计和原始结果见本阶段 `summary.json` 与 `full-browser-run.json`。首页修正后的新版独立 8 项复核保存在 `migration-browser-run.json`，复跑次数不累加为新场景。

`tools/testing/parity-generation-fixture.py` 固定连接两个回环比较库。准备前记录原 SN、唯一护栏、规则版本、PI 计数器与来源累计的逐字段摘要；清理前后再次核对。仅清理本次独占 `CMP-UI-GEN-PI` / `CMP-UI-GEN-MO` 的未分配合成 SN、规则、预演和生成业务记录，任务必须已经终结，存在领取、打印或转厂引用则拒绝。订单快照先通过界面恢复，再清理专属历史头与台账。审计和持久任务历史保留，自增 ID 不回退。

# 第十八阶段：打印文件、创建顺序与业务单号

2026-10-08，继续 P09。新打印文件的列、成员顺序和数据类型已对齐本轮原型样本，领取与打印历史增加业务单号和操作人工号。完整页面及功能一致性目标仍未完成。本轮只使用独立 MySQL 33308、Redis 36380 和合成 K3；比较库升级 V31，原开发库及原型保持不变，下一结构迁移为 V32。

## 实现

- `sn_key.creation_order` 保存同事务插入顺序，打印按此固定成员，解决随机 UUID 导致的文件行序差异。生成和初始化沿用批量护栏写入，转厂更新 PI 时保留顺序。原双唯一约束、UUID 和分区键不变。
- 新批次和打印分别使用 B/P + 上海秒时间十四位 + 四位随机尾号。单号在业务事务内保留并由唯一键防冲突；幂等请求仍用 UUID，重放不创建新事实。工号由可信账号读取并固化，后续改名不改历史工号。
- 新格式包含十一列：序号、完整SN、进制流水、十进制流水、PI、物料编码、客户编码、工厂、状态、领取批次、来源订单。文件名为 `print_<printNo>.xlsx/csv`，打印成员另存领取业务单号。
- XLSX 工作表名使用打印号并冻结首行；序号及最多十五位的十进制流水为数值，超长整数和业务编码为文本，不生成公式。CSV 使用 UTF-8 BOM、CRLF、必要引用和文本公式前导保护。前端下载校验增加新文件名的严格白名单。
- 历史页面显示新单号、工厂名、工号和统一时间，正常下载改为紧凑的 xlsx/csv 链接；文件异常仍保留下载错误和原任务恢复入口。

已有打印记录默认格式 1，继续使用原十四列编码器恢复并校验摘要；新记录显式为格式 2。历史没有原业务单号时保持 null 并回退 UUID，不伪造原号。V31 之前的 UUID 数据没有原型自增 ID，升级只能赋予稳定顺序，不能声称重建了历史创建顺序。

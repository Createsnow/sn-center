# 第十三阶段 初始化中断与结果恢复

本阶段修正 P08 初始化页面的两处恢复缺陷，并用真实提交配合浏览器网络中断验证。一次 24 项双端初始化回归通过，包含此前 12 项正常流程和新增 12 项恢复检查。29 组数据库快照逐字段相同，保存 80 张截图。完整 P01—P16 目标仍未完成，P08 也保持“部分通过”。

## 复现与修正

第一处问题发生在后台已完成初始化、页面读取成功历史失败时。新版原先把任务标记为已处理，普通查询不能完成结果处理；表单还保留可提交状态。修复前的浏览器检查实际失败，见[结果读取失败记录](evidence/parity-20261008-stage13/before-fix-recovery-before.txt)。

现在把任务终态和结果读取分开处理。已确认成功的任务只清空一次起号与 SN 清单；结果读取失败时保留原任务，点击“查询”重读其结果。读取成功后再释放原意图，恢复期间不创建新的导入操作。成功提示按任务去重，工厂、客户、物料和文件名继续保留。

第二处问题发生在请求未送达服务端时。新版“执行初始化”一直显示加载，原型已恢复可确认状态。修复前的检查证实按钮持续加载，见[请求未送达失败记录](evidence/parity-20261008-stage13/before-fix-before-delivery.txt)。现在查询确认原操作不存在、且本页仍持有原载荷时，从原“执行初始化”按钮再次确认并重发。确认框展示原提交 PI、起号和数量；操作号和请求内容都保持不变，继续使用后端幂等保护。

网络传输失败使用原型实际显示的 `Network Error` 文案。普通查询失败保留上一 PI 的状态及编辑内容，重新查询成功后切换结果。本阶段未修改后端、数据库结构、acceptance JAR 或 Python 原型。

## 双端页面检查

| 新增场景 | 实际操作与核对 |
| --- | --- |
| 提交成功、读取历史失败 | 页面实际提交，拦截结果 GET；核对数据库已有唯一成功记录；普通查询恢复锁定状态和历史，POST 总数为 1 |
| 已取得结果、刷新状态失败 | 新版单独中断状态 GET，原型中断合并的状态/历史 GET；普通查询恢复，成功记录和提交数仍为 1 |
| 提交成功、响应丢失后查询 | 浏览器将 POST 真实转发，等待实际成功入库后丢弃响应；从页面查询恢复，唯一 SN 和成功记录各 1 |
| 提交成功、响应丢失后刷新 | 同上，刷新浏览器后查询；入口表单按原型清空，重新查询显示原成功结果；新版恢复后清除本地待处理意图 |
| 请求未送达后重新确认 | 首次 POST 在转发前中断，数据库没有 SN 或成功记录；原按钮恢复可用，再次确认；两次请求内容完全相同，实际转发和入库仅 1 次 |
| 普通查询失败 | 编辑 PI 查询条件、起号、SN 和客户后中断查询；上次显示的 PI 和编辑内容保留；恢复查询不产生导入记录 |

原型把状态与历史放在同一个 GET 中，新版分为两个读取请求，因此前两项分别覆盖新版不同的失败位置。以上每项都在原型和新版执行，共 12 项；与此前 12 项正常流程一起串行运行，workers=1、retries=0，24 项均通过，耗时约 5.1 分钟。

测试未伪造业务成功响应。登录、订单同步、初始化、确认、查询、刷新均经实际页面执行。辅助脚本只用于建立声明范围内的合成规则、读取数据库事实和有归属检查的清理。每项检查均断言没有未处理的页面错误。

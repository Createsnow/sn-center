## 3. 核对过、确认没有问题的点（不改代码）

| 位置 | 核对内容 | 结论 |
| --- | --- | --- |
| 全部路由 | 每个接口声明的角色依赖与 PRD F-02 的角色表是否一致 | 一致：写操作都是 `OperatorDep` 以上，配置类为 `AdminDep`，账户管理为 `SuperAdminDep`，痕迹为 `AuditDep`；读接口在服务层按授权范围过滤（`scope_sql`、`check_read`） |
| 拼接 SQL | `f"..."` 拼接的 SQL 是否带入了请求值 | 没有：拼进去的只有代码中的列名、常量与占位符串（`marks(n)`），请求值全部作为参数传入；`ORDER BY` 只取代码里的固定写法 |
| `db/mysql.py` `_begin` | 提交失败、回滚失败时连接是否会带着坏状态回到池里 | 断线类错误（CR 2000–2999）与回滚失败都标记丢弃；服务端错误（死锁、锁等待超时）回滚后连接照常可用，放回池中；`after_tx` 在提交和回滚后都执行，跟事务走的前缀锁不会泄漏 |
| `services/locks.py` | 多把命名锁加锁顺序、部分拿到时是否释放 | 按键排序依次加锁；任一把拿不到即全部释放、关闭独立连接 |
| `generate.generate / _run` | PI 操作锁在当场生成、后台生成、出错各路径是否都释放；死锁重做是否会重复写 | 三条路径都在 `finally` 释放；死锁时整笔已回滚，`retry_deadlock` 只在没有外层事务时重做；进度写在独立事务里，可重复 |
| `generate.recover_interrupted` | 是否会把仍在执行的任务误标失败 | 生成全程持有 PI 操作锁，拿得到锁才回收，并用 `NOWAIT` 再确认计数行未被占用 |
| `delivery.push._claim_task` | 多实例认领是否会超出组织推送并发 | 互斥行 `#push_claim` 加锁读放在事务第一句，之后的计数读到别的实例已提交的认领；认领用 `state + updated_at` 条件更新 |
| `users.mes_authenticate` | 失败计数、锁定、解锁；缓存的密钥摘要在重置密钥、停用后是否失效 | 计数与锁定在行锁内；缓存按口令版本（重置即变）比对；停用、IP 白名单每次都读库判断 |
| `middleware/request_id.py`、`sn_import.parse` | 请求体、导入文件的大小与行数上限 | 写请求体 50 MB（先按 Content-Length、再按实际读取），导入文件按 `MAX_BYTES` 与 `MAX_ROWS` 双重限制 |
| `core/config.py` ↔ `.env.example` | 代码读取的配置项是否都写在 `.env.example`，示例里是否有代码不读的项 | 一致；示例中代码不读的 `LOG_MAX_*`、`WEB_PORT`、`NPM_REGISTRY`、`VITE_*` 分别由 `docker-compose.yml`、前端构建读取 |

## 4. 观察到、本次不改的点

以下不是缺陷或改动收益不足以抵消风险（已联调通过的行为不动），记录备查：

| 位置 | 现象 | 不改的原因 |
| --- | --- | --- |
| `generate._run` | 当场生成（不超过 `SN_GEN_SYNC_THRESHOLD`）被别的页面取消时，各单据各记一条失败痕迹，接口再由全局异常处理记一条 `POST /api/generate/run` 的失败痕迹 | 代码注释明确取消要按单据留痕；多一条请求级痕迹不影响业务，改了会改变审计条数 |
| `generate` 后台线程池 | `executor` 固定 4 个线程，`SN_GEN_CONCURRENCY` 调到 4 以上时后台任务最多 4 个并发（当场生成不受影响） | 默认值就是 4；调大只是后台任务多排一会儿队，不会出错 |
| `sn_import` 留痕起止号 | 导入、整单删除的留痕起止号按字符排序 | 导入的号是现场已有的号，没有流水与位数规则，按字符排序即可；与 FIX-10 的生成号不同 |

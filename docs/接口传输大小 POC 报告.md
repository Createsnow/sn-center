# 接口传输大小 POC 报告

2026-10-27 · 复现脚本：`python devtools/bench_mes_payload.py`

## 结论

维持现方案：HTTPS + JSON，每批 5000 枚；对接 MES 的组织建议开启「gzip 压缩」。

- **方式**：一批一请求，批内不分页；对账查询用游标分页（默认 1000，最多 5000）。
- **大小**：5000 枚一批，默认发原始 JSON 时单次传输 1.02 MB（典型）到 1.11 MB（最坏），已超过 nginx 默认的 1 MB 请求体上限；开启 gzip 后为 44 KB 到 229 KB。
- **压缩**：gzip 6 把 1.02 MB 压到 44 KB，耗时约 3 ms；开 9 级不划算。
- **区间**：合理区间 1000–10000 枚；单请求建议控制在 1 MB 以内。不开 gzip 的组织，单批调到 4000 枚以内，或请 MES 方把请求体上限放到 2 MB 以上。
- **待定**：MES 处理 5000 枚的实际落库耗时，联调时实测。

## 背景与目标

本 POC 只看 SN 交付到 MES 这一条链路：一个「批次」装多少枚号、用什么格式和压缩、单次请求多大最稳。

现状（分支 `sn-center-python`）：

| 接口 | 方向 | 当前做法 |
| --- | --- | --- |
| ① 推送批次 | 本系统 → MES | HTTPS + JSON；建批时以 gzip（level 6，mtime=0）写定，重送逐字节相同；默认发原始 JSON，组织开启「gzip 压缩」后才发 gzip；MES 在响应中回执整批结果（`OK` / `NG`）；每批默认 5000 枚，可按组织配置（1–50000）；超时 60 秒，同组织并发 2 |
| ② 拉取批次 `batches/next` | MES → 本系统 | 返回同一格式的批次，上限同「单批推送枚数」 |
| ③ 回执 `receipt` | MES → 本系统 | 整批结果（`OK` / `NG`），请求体可为 gzip |
| ④ ⑤ 对账查询 | MES → 本系统 | 游标分页，默认 1000，最多 5000 |

要回答的问题：

1. 5000 枚一批，传输体积和耗时是多少，是否在安全范围内。
2. gzip 是否值得，压缩级别选几。
3. 批次大小的合理区间，什么时候应调小或调大。

## 测试方法

组包方式与 `app/services/mes_client.py` 一致：紧凑 JSON（UTF-8，无空格）+ gzip（mtime=0）。报文按《MES 对接接口文档》① 的现协议：批次头含 `toOrgCode`、`count`，明细每枚 12 个字段（交付与转出同一结构）。

| 项目 | 设置 |
| --- | --- |
| 环境 | 云端容器，4 核 Xeon，Python 3.13 标准库 |
| 批次规模 | 500 / 1000 / 2000 / 5000 / 10000 / 20000 / 50000 枚 |
| 数据 A（典型） | 首次下发批次：同一 PI、连续流水、同物料，无附件项次，符合「按流水顺序认领」的真实组包 |
| 数据 B（最坏） | 跨组织转出批次（批次头带 `toOrgCode`）：随机 36 进制流水、单据、附件项次、物料、客户，几乎无重复 |
| 请求体 | 原始 JSON（默认）/ gzip 1 / gzip 6（开启「gzip 压缩」时）/ gzip 9 |
| 端到端 | 本机 HTTP 服务模拟 MES：按 `Content-Encoding` 解压 → 解析 → 响应中回执整批结果；不含数据库写入 |
| 指标 | 传输字节、压缩耗时、解析耗时、往返耗时、MES 侧内存峰值，各取 5 次中位数 |

带宽耗时按字节数换算（未实测公网）。MES 落库耗时取决于对方实现，需联调时实测。

## 测试结果

现行 5000 枚一批，耗时和内存都很小，瓶颈不在网络传输；但不开 gzip 时请求体刚好超过 1 MB。

**单批传输体积**

| 每批枚数 | 典型 · 原始 JSON | 典型 · gzip 6 | 最坏 · 原始 JSON | 最坏 · gzip 6 |
| --- | --- | --- | --- | --- |
| 1,000 | 209 KB | 9.1 KB | 227 KB | 46.1 KB |
| 5,000（现行） | 1.02 MB（超过 1 MB） | 44.0 KB | 1.11 MB（超过 1 MB） | 229 KB |
| 10,000 | 2.05 MB | 87.4 KB | 2.22 MB | 456 KB |
| 20,000 | 4.11 MB | 176 KB | 4.43 MB | 912 KB |
| 50,000 | 10.3 MB | 442 KB | 11.1 MB | 2.23 MB |

体积随枚数线性增长。原始 JSON 每枚约 215 字节（典型）到 232 字节（最坏），约 4500 枚就碰到 1 MB。gzip 6 后，典型数据每枚约 9 字节（压缩比约 24 倍），最坏数据每枚约 47 字节（约 5 倍），最坏数据到 2 万枚一批仍在 1 MB 以内。

**压缩级别（5000 枚，典型数据）**

| 方式 | 传输体积 | 压缩耗时 |
| --- | --- | --- |
| 不压缩（默认） | 1.02 MB | — |
| gzip 1 | 46.5 KB | 1.6 ms |
| gzip 6（开启压缩时） | 44.0 KB | 3.1 ms |
| gzip 9 | 43.4 KB | 9.2 ms |

压缩在建批时一次完成并写入 `body_gz`，重送不再压缩，所以这几毫秒只付一次。

**按批次规模的处理开销（典型数据，本机）**

| 每批枚数 | MES 解析（含解压） | 本机往返（含回执） | MES 解析内存峰值 |
| --- | --- | --- | --- |
| 1,000 | 1 ms | 3 ms | 1.1 MB |
| 5,000 | 6 ms | 10 ms | 5.3 MB |
| 10,000 | 14 ms | 18 ms | 10.6 MB |
| 50,000 | 70 ms | 78 ms | 53 MB |

原始 JSON 和 gzip 6 的解析耗时、内存几乎相同（解压只占零头）。回执只有整批结果，响应固定约 110 字节，与批次大小无关。

**按带宽换算 5000 枚一批**

| 请求体 | 1 Mbps | 10 Mbps |
| --- | --- | --- |
| 典型 · gzip 6（44 KB） | 0.36 秒 | 0.04 秒 |
| 最坏 · gzip 6（229 KB） | 1.9 秒 | 0.19 秒 |
| 典型 · 原始 JSON（1.02 MB） | 8.6 秒 | 0.86 秒 |
| 最坏 · 原始 JSON（1.11 MB） | 9.3 秒 | 0.93 秒 |

都低于 60 秒超时；但不开 gzip 时，低带宽链路上传输就占去 60 秒超时的约 1/6，留给 MES 落库的余量变小。

## 方案建议

保持现有方式：HTTPS + 紧凑 JSON，按批次分块传，默认 5000 枚一批；连接测试通过后优先开启 gzip。

| 问题 | 建议 | 理由 |
| --- | --- | --- |
| 以什么方式 | HTTPS + JSON（UTF-8），不换 Protobuf / 文件 / MQ | 5000 枚解析仅约 6 ms，二进制格式省下的体积和时间可忽略；JSON 对 MES 方接入门槛最低 |
| 怎么传 | 按批次分块，一批一个请求，批内不再分页；重送用同一批次号、同一字节 | 批次是幂等和回执的单位，分页会打破「一包一签收」 |
| 压缩 | MES 支持 gzip 请求体的组织开启「gzip 压缩」，级别保持 6 | 体积降到 1/24（典型）或 1/5（最坏），5000 枚一批从 1 MB 以上降到 229 KB 以内；level 9 只再小 1.3%，耗时约 3 倍 |
| 不开压缩时 | 单批调到 4000 枚以内，或 MES 网关请求体上限 ≥ 2 MB | 原始 JSON 约 4500 枚就到 1 MB；5000 枚最坏 1.11 MB 会被 nginx 默认配置拒绝（413） |
| 传多大 | 每批 5000 枚；可配置区间 1000–10000，不建议超过 10000 | 10000 以上传输不是问题，但单批失败要整批重发、MES 单事务变长、作废粒度变粗 |
| 何时调小 | MES 处理 5000 枚超过 20 秒，或对方网关限制 < 512 KB（已开 gzip）/ < 2 MB（未开 gzip）→ 调到 1000–2000 | 给 60 秒超时留足余量，避免超时重发叠加 |
| 何时调大 | 已开 gzip、单 PI 上 10 万枚、MES 处理 5000 枚 < 5 秒 → 可到 10000 | 推送次数减半，单请求仍 < 1 MB；未开 gzip 时 10000 枚约 2.2 MB，不建议调大 |
| 对账查询 ④⑤ | 游标分页维持默认 1000、最大 5000 | 与批次同量级，单页 < 1 MB（未压缩）；请求带 `Accept-Encoding: gzip` 时响应会压缩 |

联调时请 MES 方确认四件事：

- [ ] 是否支持 `Content-Encoding: gzip` 请求体（《MES 对接接口文档》2.1 第 8 项），支持则开启「gzip 压缩」
- [ ] 网关 / 反向代理的请求体上限：开 gzip 时 ≥ 1 MB，不开 gzip 时 ≥ 2 MB
- [ ] 5000 枚一批的实际落库耗时（目标 < 20 秒）
- [ ] 解压后请求体上限 ≥ 3 MB（部分框架按解压后大小限制）

## 风险与后续

主要风险在 MES 侧落库耗时，不在传输；本 POC 未覆盖这一段。

- **默认不压缩**：「gzip 压缩」默认关，5000 枚一批的原始 JSON 已超过 1 MB；对方网关按默认 1 MB 配置时会整批 413，联调第一步就要确认请求体上限或开启 gzip。
- **未实测公网**：带宽耗时为换算值；跨境工厂（如越南）建议联调时跑一次 5000 枚真实推送。
- **存储上限**：`body_gz` 是 MEDIUMBLOB（16 MB），最坏数据约 35 万枚才到上限，后端单批上限 50000（约 2.3 MB），当前无风险。
- **配置上限偏大**：「单批推送枚数」后端允许 1–50000，大于本报告建议的 10000；建议页面和后端把上限收到 10000。
- **下一步**：用 `docs/MES 联调指南.md` 的模拟 MES 加入真实落库，测 1000 / 5000 / 10000 三档的端到端耗时后定稿。

# 接口传输大小 POC 报告

2026-10-22 · 复现脚本：`python devtools/bench_mes_payload.py`

## 结论

维持现方案：HTTPS + JSON + gzip 6，每批 5000 枚，单次传输 44 KB（典型）到 300 KB（最坏）。

- **方式**：一批一请求，批内不分页；对账查询用游标分页（默认 1000，最多 5000）。
- **压缩**：gzip 6 把 1.03 MB 压到 44 KB，耗时 4.5 ms；开 9 级不划算。
- **大小**：合理区间 1000–10000 枚；单请求建议控制在 1 MB 以内。
- **待定**：MES 处理 5000 枚的实际落库耗时，联调时实测。

## 背景与目标

本 POC 只看 SN 交付到 MES 这一条链路：一个「批次」装多少枚号、用什么格式和压缩、单次请求多大最稳。

现状（分支 `sn-center-python`）：

| 接口 | 方向 | 当前做法 |
| --- | --- | --- |
| ① 推送批次 | 本系统 → MES | HTTPS + JSON，请求体 gzip（level 6，mtime=0，重送逐字节相同）；每批默认 5000 枚，可按组织配置；超时 60 秒，同组织并发 2 |
| ③ 拉取批次 `batches/next` | MES → 本系统 | 返回同一格式的批次，上限同「单批推送枚数」 |
| ④ 回执 `receipt` | MES → 本系统 | 逐枚结果，支持 gzip 请求体 |
| ⑤ ⑥ 对账查询 | MES → 本系统 | 游标分页，默认 1000，最多 5000 |

要回答的问题：

1. 5000 枚一批，传输体积和耗时是多少，是否在安全范围内。
2. gzip 是否值得，压缩级别选几。
3. 批次大小的合理区间，什么时候应调小或调大。

## 测试方法

组包方式与 `app/services/mes_client.py` 一致：紧凑 JSON（UTF-8，无空格）+ gzip（mtime=0），批次头和交付项字段按当时的《MES 对接说明》（旧协议，含逐枚回执）。

| 项目 | 设置 |
| --- | --- |
| 环境 | 云端容器，4 核 Xeon 2.1 GHz，Python 3.13 标准库 |
| 批次规模 | 500 / 1000 / 2000 / 5000 / 10000 / 20000 / 50000 枚 |
| 数据 A（典型） | 同一 PI、连续流水、同物料，符合「按流水顺序认领」的真实组包 |
| 数据 B（最坏） | 随机 36 进制流水、单据、物料、客户，并带转移字段，几乎无重复 |
| 压缩 | 不压缩 / gzip 1 / gzip 6（现行）/ gzip 9 |
| 端到端 | 本机 HTTP 服务模拟 MES：解压 → 解析 → 生成逐枚回执 → gzip 应答；不含数据库写入（按旧协议报文测得，复现脚本同；现协议明细字段更少、回执只有整批结果，实际体积与耗时只会更小） |
| 指标 | 传输字节、压缩耗时、解析耗时、往返耗时、MES 侧内存峰值，各取 5 次中位数 |

带宽耗时按字节数换算（未实测公网）。MES 落库耗时取决于对方实现，需联调时实测。

## 测试结果

现行 5000 枚一批，传输体积、耗时、内存都很小，瓶颈不在网络传输。

**单批传输体积（gzip 6）**

| 每批枚数 | 典型数据 | 最坏数据 |
| --- | --- | --- |
| 1,000 | 9.1 KB | 60.5 KB |
| 5,000（现行） | 44.0 KB | 300 KB |
| 10,000 | 87.5 KB | 600 KB |
| 20,000 | 176 KB | 1.17 MB（超过 nginx 默认 1 MB） |
| 50,000 | 442 KB | — |

体积随枚数线性增长：典型数据每枚约 9 字节（压缩比约 24 倍），最坏数据每枚约 60 字节（约 5 倍）。最坏数据到 2 万枚一批才碰到 1 MB。

**压缩级别（5000 枚，典型数据）**

| 方式 | 传输体积 | 压缩耗时 |
| --- | --- | --- |
| 不压缩 | 1.03 MB | — |
| gzip 1 | 46.5 KB | 2.0 ms |
| gzip 6（现行） | 44.0 KB | 4.5 ms |
| gzip 9 | 43.4 KB | 12.5 ms |

**按批次规模的处理开销（典型数据，本机）**

| 每批枚数 | 未压缩 JSON | MES 解压 + 解析 | 本机往返（含回执） | MES 解析内存峰值 | 回执（gzip） |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 210 KB | 2 ms | 5 ms | 1.1 MB | 2.7 KB |
| 5,000 | 1.03 MB | 12 ms | 27 ms | 5.5 MB | 12.6 KB |
| 10,000 | 2.06 MB | 18 ms | 48 ms | 11 MB | 25 KB |
| 50,000 | 10.3 MB | 95 ms | 283 ms | 55 MB | 125 KB |

按带宽换算 5000 枚一批（44 KB）：1 Mbps 约 0.35 秒，10 Mbps 约 0.04 秒；最坏数据 300 KB 在 1 Mbps 下约 2.4 秒，都远低于 60 秒超时。

## 方案建议

保持现有方式：HTTPS + 紧凑 JSON + gzip 6，按批次分块传，默认 5000 枚一批。

| 问题 | 建议 | 理由 |
| --- | --- | --- |
| 以什么方式 | HTTPS + JSON（UTF-8），不换 Protobuf / 文件 / MQ | 5000 枚解析仅 12 ms，二进制格式省下的体积和时间可忽略；JSON 对 MES 方接入门槛最低 |
| 怎么传 | 按批次分块，一批一个请求，批内不再分页；重送用同一批次号、同一字节 | 批次是幂等和回执的单位，分页会打破「一包一签收」 |
| 压缩 | 请求与应答都 gzip，保持 level 6 | 体积降到 1/24（典型）或 1/5（最坏）；level 9 只再小 1.4%，耗时翻倍以上 |
| 传多大 | 每批 5000 枚（传输 44–300 KB）；可配置区间 1000–10000，不建议超过 10000 | 10000 以上传输不是问题，但单批失败要整批重发、MES 单事务变长、作废粒度变粗 |
| 何时调小 | MES 处理 5000 枚超过 20 秒，或对方网关限制 < 512 KB → 调到 1000–2000 | 给 60 秒超时留足余量，避免超时重发叠加 |
| 何时调大 | 单 PI 上 10 万枚、MES 处理 5000 枚 < 5 秒 → 可到 10000 | 推送次数减半，单请求仍 < 1 MB |
| 对账查询 ⑤⑥ | 游标分页维持默认 1000、最大 5000 | 与批次同量级，单页 < 1 MB（未压缩） |

联调时请 MES 方确认三件事：

- [ ] 网关 / 反向代理允许 `Content-Encoding: gzip` 请求体，请求体上限 ≥ 1 MB
- [ ] 5000 枚一批的实际落库耗时（目标 < 20 秒）
- [ ] 解压后请求体上限 ≥ 3 MB（部分框架按解压后大小限制）

## 风险与后续

主要风险在 MES 侧落库耗时，不在传输；本 POC 未覆盖这一段。

- **未实测公网**：带宽耗时为换算值；跨境工厂（如越南）建议联调时跑一次 5000 枚真实推送。
- **存储上限**：`body_gz` 是 MEDIUMBLOB（16 MB），最坏数据约 26 万枚才到上限，当前无风险。
- **配置无上限**：「单批推送枚数」目前只限最小 1，建议在页面和后端校验上限 10000。
- **下一步**：用 `docs/MES 联调指南.md` 的模拟 MES 加入真实落库，测 1000 / 5000 / 10000 三档的端到端耗时后定稿。

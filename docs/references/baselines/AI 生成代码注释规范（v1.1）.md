## 一、注释的职责与权威来源

注释面向当前审查者、未来维护者和后续 Agent，说明**调用契约、业务约束、实现理由及失败边界**。代码中的类型、名称和结构能清楚表达的内容，不逐行复述；公开契约仍需简明说明用途，不能以“代码自解释”为由省掉权限、事务和失败语义。

注释是与代码同步维护的局部契约，**不是唯一持久知识来源，也不能代替可执行约束或验证证据**。项目的有效知识按以下位置维护。

| 内容 | 权威位置 | 注释如何引用 |
| --- | --- | --- |
| 技术栈、模块与分层、统一编码约束 | 《技术栈和工程结构》；建项后对应 docs 正文及版本锁 | 写当前代码的职责和适用边界，不复制版本表 |
| SN 业务规则、状态机、迁移边界 | 《SN 项目迁移方案》及其引用的有效需求、接口和数据模型 | 摘要说明本方法涉及的规则，并给出相关章节或功能 ID |
| 实际接口、校验、枚举、错误码、数据库约束 | 已实现的类型、注解、OpenAPI、SQL 和有效迁移，与对应契约同步 | 引用实际符号、约束和来源，不虚构索引名、状态或错误码 |
| 设计选择的理由与替代关系 | `memory/决策与变更日志.md` | 必要时引用真实 `DEC-YYYYMMDD-NNN`，不复制讨论过程 |
| 当前进度、实际检查与限制 | `memory/项目状态.md`、`docs/reports/` | 不在源码中写“测试已通过”“迁移已完成”等阶段结论 |
| Agent 的阅读顺序和边界 | `AGENTS.md`；`CLAUDE.md` 等工具入口引用它 | 指向本文，不复制第二套完整注释规范 |

两份依据目前是设计与约束基线，不能据此把“应实现”写成“代码已经保证”。Agent 必须核对所改实现、调用路径、迁移和测试；发现实现与有效规范不一致时，明确差异并在任务范围内修正，不只改注释掩盖缺陷，也不静默改动业务规则。

本文使用“必须/禁止”表示要求，“应”表示默认做法，“可”表示按信息价值选用。简单查询不必机械填满事务、幂等等空栏目；涉及这些语义时必须说明。

## 二、通用写法与覆盖范围

### 2.1 写什么、不写什么

1. 默认使用简洁中文；代码标识符、协议名和稳定标记保留原文。同一模块保持术语一致，业务编码不翻译。
2. 优先说明前提、权限、不可变条件、失败后状态、算法取舍及外部依赖。说明“为什么必须这样做”，而不是逐行描述赋值、循环或保存。
3. 注释描述当前有效契约。禁止“本次修改”“按要求新增”“这里我们”“接下来”等会话式表述；工具、会话、生成过程留在必要的交付记录中。
4. 禁止编造作者、团队、日期、issue、决定编号、类名、索引名或测试结论。`@author`、`@since` 不强制；已有模板要求时，只填写可核实信息，不写模型名或虚构团队。
5. 需求编号、决定编号、数据表或方法引用应稳定且可定位。代码符号可用 Javadoc `{@link ...}`；仓库文档使用可定位的路径与章节/条目，不以易漂移的行号作为唯一依据。
6. 注释不得保存密码、token、密钥、真实个人信息、完整敏感报文或机器私有配置。示例使用明确的非敏感数据。
7. 修改逻辑、类型、SQL、约束或调用关系时，同步检查相关注释及对外契约；删除失效信息，不保留相互矛盾的新旧说明。

### 2.2 按风险和职责决定覆盖范围

| 对象 | 注释要求 |
| --- | --- |
| 手写的公开 Service 接口方法、跨模块端口 | 必须有 Javadoc，说明调用方需要遵守的契约，详见第三节 |
| 手写模块入口、关键策略、框架扩展点和复杂算法 | 必须说明职责、适用范围及关键约束；模块级背景可集中在 `package-info.java` 或模块说明 |
| ServiceImpl 的覆写方法 | 继承接口契约；只补实现决策、事务与并发机制，不整段复制接口注释 |
| Controller | OpenAPI 维护对外协议；Javadoc 按需补充非重复的入口职责或内部契约引用 |
| Mapper/XML/JDBC、Entity、DTO/Query/VO、MapStruct | 按第三节的查询、字段和映射要求执行 |
| 可复用前端组件、Hooks、API 包装和复杂状态逻辑 | 使用 TSDoc/JSDoc 说明调用约束、副作用和非显然行为，详见第五节 |
| 简单私有方法、局部变量、显然的访问器或简单展示组件 | 不强制写注释；有隐藏约束时在最近位置补充 |
| 测试、脚本、配置与迁移 | 说明业务场景、执行前提、破坏性副作用和恢复边界，详见第六节 |
| 自动生成代码、第三方源码、历史只读资产 | 不为补注释手改；生成问题修改契约/模板后重新生成，历史资产遵守迁移边界 |

不执行“所有类、所有 public 方法一律补齐注释”的机械要求。方法可见性不是风险的唯一标准；一段没有公开 API 的 SQL 或任务工作器同样可能承载关键契约。

### 2.3 使用所属语言支持的格式

- Java：`/** ... */` 写 Javadoc，`//` 写局部理由；必要的多行说明、许可证和工具要求允许使用块注释。
- TypeScript/JavaScript：`/** ... */` 写 TSDoc/JSDoc，`//` 写局部说明；JSX 内使用 `{/* ... */}`。不重复 TS 已表达的参数类型。
- MyBatis XML：使用 `<!-- ... -->`；SQL 使用该数据库支持的 `--` 或 `/* ... */`。
- YAML、Shell、PowerShell 等使用各自合法语法；严格 JSON 不添加注释，说明放在 schema 或相邻文档。
- 禁止把废弃代码注释掉后提交；历史由版本控制或已有历史资产保存。许可证、生成器标识、有效工具指令不属于废弃代码，不随意删除。

## 三、Java 后端分层要求

后端沿用 `controller / service / service.impl / mapper / domain / dto / query / vo / convert`，其中 `domain` 是数据库 Entity。注释不得引入另一套分层或把跨模块直接访问 Mapper、framework 反向引用业务实现写成既定做法。

### 3.1 Controller 与 OpenAPI：说明外部契约

Controller 负责协议解析、参数校验、已认证主体传递、Service 调用及响应包装。公开接口的用途、输入输出、鉴权要求、错误、幂等和限流行为应体现在 OpenAPI 及接口正文中；复杂语义可链接正文，不假定 OpenAPI 只能写字段和路径。

Javadoc 可补充入口职责和对应 Service，不重复整套字段描述。以下表述禁止使用：

- “调用方已经鉴权，服务内部不需要权限检查。”HTTP、任务工作器和集成都必须经过用例授权；应说明实际鉴权位置与主体来源。
- “客户端传入 Idempotency-Key 即保证幂等。”项目统一业务操作号为 `operationId`，保证来自持久操作记录、数据库约束及恢复流程；字段或请求头位置以实际接口契约为准。
- “统一返回 Long ID。”业务 ID 在 JSON 中采用字符串；普通对象、分页、游标、任务分别遵守 `Result<XXXVO>`、`Result<PageResult<XXXVO>>`、`Result<CursorResult<XXXVO>>`、`Result<TaskVO>`。
- “下载也返回 Result 包裹二进制。”成功文件响应是文件流；开始输出前的失败和流中断的处理按文件契约说明。

### 3.2 Service 接口：写调用方可依赖的行为

公开 Service 方法的 Javadoc 必须说明用途、关键入参和权限。对写命令或具有副作用的操作，还必须覆盖下列相关内容；只读查询明确范围、空结果、排序/分页等实际语义即可。

| 契约要素 | 需要回答的问题 |
| --- | --- |
| 用途与范围 | 操作哪些对象？是整 PI、整来源订单、固定成员还是单对象？ |
| 前置条件与权限 | 主体从哪里取得？需要什么操作权限、工厂/对象资格和状态？哪些结构校验在入口，哪些业务校验由用例保证？ |
| 后置条件与副作用 | 成功后哪些状态、额度、水位、批次、任务和审计发生变化？返回的是完成结果还是持久任务？ |
| 事务与并发 | 哪些变化原子提交？失败保留什么？哪些对象需要互斥或条件更新？冲突如何反馈？ |
| 幂等与恢复 | 唯一范围、同号同载荷、异载荷和进行中请求分别如何处理？超时后如何查询原结果？重放如何复核授权？ |
| 失败语义 | 调用方应识别哪些拒绝、冲突、部分结果或依赖故障？引用所属模块的实际错误码，说明重试条件 |

具体锁 SQL、索引名、锁顺序和异常翻译位置主要写在 ServiceImpl、Mapper 或 SQL 附近；接口保留对调用方有意义的并发保证。不能要求调用方依赖某一条 WHERE 子句，也不能把条件更新描述成“数据库无锁”。

下面是**领取用例接口的注释写法示例**。`AcquireService`、`AcquireCommandDTO`、`AcquireResultVO` 为示意类型名，正式接口须与已确定的 DTO/VO、同步或任务契约一致；不据此另建类型或改动接口。示例使用业务拒绝语义，实际实现还须对齐已登记的错误码。

```java
/**
 * 按工厂与 PI 领取 SN；业务依据见《SN项目迁移方案》6.1 的领取规则。
 */
public interface AcquireService {

    /**
     * 领取指定工厂、指定 PI 下全部符合资格的待领取 SN。
     *
     * <p>权限：主体来自可信认证上下文；用例核验当前操作权限与目标工厂资格。
     * 物料筛选不缩小领取范围，待分配号不参加领取。
     *
     * <p>结果：返回可领、被阻止数量及分类原因；零可领也返回明确结果。
     * 有实际领取时保存固定成员和领取时展示快照，后续查询不按当前号池重建批次。
     *
     * <p>事务与并发：本次领取的状态、固定成员、成功结果和业务审计原子提交；
     * 并发领取不能使同一成员重复进入新的有效领取结果，失败不留下部分领取。
     *
     * <p>幂等：主体 + 动作 + operationId 唯一；同号同载荷复用原结果，
     * 同号异载荷报冲突；进行中请求返回原任务或处理中状态。
     * 重放前重新核验当前授权，超时后按原操作查询，不换号重新领取。
     *
     * @param command 工厂、PI 及操作号等命令参数；不包含可自行声明的角色或总部身份
     * @return 完成结果或处理中信息，具体分支以已发布接口契约为准
     * @throws BusinessException 当前主体无权执行、命令业务条件不合法或操作号载荷冲突
     */
    AcquireResultVO acquire(AcquireCommandDTO command);
}
```

实际业务代码使用 `BusinessException` 及所属模块的 `ErrorCodeConstants`，不沿用 `BizException`，不把旧 `SnException` 的字符串码直接当作新接口错误码。`@throws` 写调用方需要识别的业务语义，不机械罗列所有底层运行时异常或泄露 SQL。

调用前置条件必须由真实调用路径保证。不能因为 HTTP 入口使用了 Jakarta Validation，就假定工作器或集成调用也已完成相同校验；需要在用例边界保持一致的校验和授权能力。

### 3.3 ServiceImpl：说明机制、理由和失败边界

实现类简述职责并指向接口。覆写方法可继承文档；生成工具确有需要时使用 `{@inheritDoc}`，不要求为每个覆写方法添加空壳注释。

应在最接近关键代码的位置说明：

- **业务理由**：为何整 PI 领取、为何转厂不退历史额度、为何空物料不能丢弃等，必要时引用有效条款。
- **权限执行**：当前主体及对象范围在哪里核验，为什么重放、工作器或下载还需要重新检查。
- **事务机制**：实际代理入口、事务覆盖对象、异步边界、异常回滚传播；不能只看到 `@Transactional` 就写“保证原子性”。
- **并发机制**：锁定对象与顺序、条件更新及影响行数的含义、唯一约束、可识别的冲突和重试条件。
- **外部副作用**：数据库提交、Redis 失效、文件发布、ERP 请求之间的边界及失败恢复，不能合称“同一事务”。

以下仅示范局部注释内容，放入源码前必须确认邻近代码确实执行了相应机制：

```java
// CONCURRENCY: 同 PI 生成在同一数据库事务内串行；SQL 分块仅控制发送规模，
// 不能分块提交，否则后续冲突会留下已推进的水位和历史额度。

// SAFETY: 幂等结果重放仍核验当前工厂权限；原操作成功不代表主体现在仍可访问。

// 预检查用于提前解释目标 PI 冲突，最终唯一性由数据库护栏保证；
// 仅将能够识别的对应约束冲突映射为业务防重错误，其他数据库错误继续交由统一入口处理。
```

禁止只写“转换为实体”“保存用户”“遍历列表”等没有附加信息的注释。禁止虚构“待激活”账号流程，或把停用改成删除历史身份；账号状态、首次改密及会话失效语义以已确定模型为准。

### 3.4 Mapper、XML 与 JDBC：意图、范围和数据一致性

自定义数据库访问方法应说明查询/更新用途、授权范围、关键筛选和排序、空集合语义，以及结果/影响行数的含义。涉及锁、批量操作或条件更新时，还要说明调用事务前提和并发作用。

索引说明区分两种事实：

- **正确性依赖**：引用实际存在的唯一约束或护栏及其迁移/数据模型来源，说明保护的业务维度。发现缺失先修复或报告，不能用注释假装存在。
- **性能预期**：说明谓词、排序与候选索引的关系；执行计划和实测放到报告中。不能仅凭索引存在就写“必走索引”“无全表扫描”“毫秒级”。

复杂 SQL 的注释由理解成本决定，不以“超过 20 行”作为唯一门槛。CTE、子查询、窗口函数、锁和授权条件说明各自作用，避免逐列翻译 SQL。MyBatis-Plus 继承的标准方法不为补注释而重复声明。

MyBatis 数据权限拦截器不自动保护 JDBC。JDBC 注释必须对应实际传入的类型化范围及绑定条件；值参数绑定、动态列名白名单、空范围与缺失上下文分别按有效契约处理，不写“空列表表示全部”。

### 3.5 Entity、DTO、Query、VO 与 MapStruct：字段语义和转换边界

| 对象 | 必须明确的语义 |
| --- | --- |
| Entity（`domain`） | 持久化字段含义与列 COMMENT、数据字典一致；枚举引用实际枚举；关键字段说明单位、精度、空值及不可变性质。不臆造枚举数值 |
| DTO | 写命令的业务含义；未提供、null、空字符串的区别；客户端能写哪些字段。结构校验引用 Jakarta Validation，跨字段和业务资格说明在用例契约中 |
| Query | 筛选组合、授权范围、稳定排序和分页/游标语义；特别区分“全部物料”与“仅空物料” |
| VO | 派生、聚合、快照和脱敏字段注明含义及来源；来源是当前关联数据还是历史固定快照必须清楚。复杂装配引用实际查询/用例位置 |
| `convert` | MapStruct 新增/更新映射、null 策略、忽略字段及理由；主键、审计字段、额度、水位、状态由谁控制 |

DTO→Entity、Entity→VO 使用 MapStruct。需要关联查询或业务计算时，由 Service 组织数据，再按明确映射输出；不能为了写“装配来源”另建一套手工复制或反射拷贝规范。

**减少重复，不禁止必要数字。**长度等可从校验注解和 OpenAPI 自动导出的约束，不在多处手写同一数值；业务单位、时区、容量含义、状态机边界等不能由类型表达的内容仍须说明，并与权威定义同步。不能把“校验注解是唯一事实源”扩大到数据库唯一性、权限和业务不变量。

ID、完整 SN、十进制流水在 JSON 和前端是字符串；`Result.code` 则是 int32 数字，二者不能混淆。“无 N+1”属于查询行为，需要核对实际访问路径，不能仅凭一个 VO 字段注释下结论。

采用 `record` 的 DTO、Query 或 VO 时，在类型 Javadoc 中用 `@param` 说明重要组成字段的业务含义、单位、来源、可空性及精度；不只重复字段名，也不因没有普通字段声明而遗漏字段契约。已由校验注解或生成契约准确表达的内容避免重复维护。

跨系统映射至少说明**来源字段 → 目标字段、来源/目标类型、单位、可空性及转换规则**，并标明可能的精度、时区、长度或枚举信息损失。完整映射表放在数据模型/接口正文，转换代码仅解释非显然的取舍并引用实际位置。原始标识与本地身份的映射、空快照与缺字段的区别要可核对；发现损失必须按契约拒绝或采用已确定的处理方式，不能只写一条注释就静默截断、舍入或更改业务含义。

### 3.6 框架与集成端口：标清保证的范围

- `@DataScope/@OperLog/@Idempotent/@RateLimiter` 的声明注释说明用途、参数与启用前提；执行保证写在对应实现和契约中，不把纯声明当作已执行逻辑。
- 会话组件说明 JWT 校验、Redis 会话/权限版本检查、撤销与依赖故障语义；不称为“完全无状态 JWT”。
- 审计实现区分管理字段 diff、成功业务审计及回滚后的失败事件；脱敏白名单和提交时机可定位。
- `service.port` 说明外部数据的稳定身份、完整性、分页/空快照和失败语义；integration 说明协议映射、超时和重试边界，不能绕过 SN 用例写关键状态。
- 持久任务说明领取锁/租约、主体、重复执行防护、结果恢复及授权复核；`@Async` 不等于可靠队列。

外部调用的注释说明连接/读取/整体超时各自作用、配置来源、可重试错误、最大次数与总预算、负责重试的层次和终止后的状态。数值由配置统一维护，注释不复制会漂移的阈值。超时后的结果核对、补偿或降级只描述实际实现的机制，明确触发条件、防重复措施、最终状态及人工处理入口；不能将依赖故障描述为正常空结果。

任务与资源相关注释说明取消等待和业务取消的区别、工作器停止领取/在途处理、租约失效后的提交保护，以及连接、流和临时文件的释放责任。后台中断不自动代表事务回滚或业务撤销，注释应指向实际持久状态与恢复依据。

## 五、React / TypeScript 注释要求

前端使用函数组件、Hooks、TypeScript strict、TanStack Query、Zustand 和统一 typed API，具体版本仅由技术基线与锁文件维护。不能把后端 Javadoc 规则原样套到所有组件。

### 5.1 组件、Hooks 与状态

- 可复用组件和 Hooks 说明类型无法表达的受控/非受控约定、状态归属、副作用、取消/清理、返回状态和错误行为；不逐条复述 Props 的类型。
- TanStack Query key 及失效逻辑说明主体、权限范围和业务筛选维度；注销、切换身份、权限收缩时清除哪些数据。缓存键和注释不包含 token。
- Zustand 说明保留的最小客户端状态；不通过注释为复制服务端全量列表或持久保存长期 bearer token 背书。
- 写命令说明何时创建和复用 `operationId`、超时后如何恢复原任务；不能把查询重试直接套到生成、领取或打印。
- 路由/按钮权限注释说明其界面作用，不写“已防止越权”；服务端仍负责强制授权。
- 复杂 effect 说明同步对象、依赖和清理原因；不能用注释代替正确依赖，也不能靠关闭检查掩盖状态问题。

### 5.2 API、精度、空值与语言

API 包装只补充传输类型无法表达的语义，包括业务拒绝、取消、文件流错误、任务恢复以及 401/403/429/503 的不同处理。生成的 OpenAPI TS 类型不手改；修正源契约后重新生成。

下面仅示范**页面筛选状态**的表达方式，不定义后端参数格式。实际项目优先复用已存在的类型，并在 API 边界按已发布契约映射：

```ts
/**
 * 保留“全部物料”与“仅空物料”的区别；
 * 不用 truthy/falsy 归一化，否则会改变查询和导出的范围。
 */
type MaterialFilter =
  | { kind: 'all' }
  | { kind: 'empty' }
  | { kind: 'value'; code: string };
```

精确 ID、SN 和流水保持字符串，需要运算时使用已确定的精确整数方案，注释不得宣称经过 `Number` 转换后仍保留任意整数精度。日期范围说明 API 时区和边界，与导出一致。

中英越文案维护在 locale 资源中；注释只解释不明显的占位符、业务术语或保留原编码的原因。错误按 `code + params` 处理，不能解析 message；不要把整套三语言文案复制进代码注释。

### 5.3 抑制指令

禁止用 `any`、大范围 `ts-ignore`、关闭 strict 或排除启用源码来消除错误。确需局部 lint/类型抑制时，必须说明具体原因、影响范围、可核实依据和移除条件，并按既有质量规则处理；注释本身不构成豁免。不能为完成注释任务新增抑制指令。

## 七、特殊标记与未完成项

### 7.1 SAFETY 与 CONCURRENCY

- `// SAFETY:` 标记需要解释的安全边界，例如当前授权复核、可信主体来源、SQL 白名单、敏感字段脱敏。
- `// CONCURRENCY:` 标记并发正确性的关键依赖，例如锁顺序、唯一约束、条件更新、幂等持久化和工作器竞争。
- 在 SQL/XML 等文件中使用该语言的合法注释语法承载相同标记。

标记后必须写具体约束及其原因，不只写“安全检查”“防并发”。标记用于定位审查重点，不要求给每个 if、每个鉴权注解都贴标签。**没有标记也不能豁免关键路径审查；存在标记也不证明实现正确。**人的关键审查范围仍按架构正文 9.3 和迁移方案第 13 节执行，Agent 不自称已经替代人工审查。

### 7.2 TODO / FIXME

TODO 表示有明确跟踪的待办，FIXME 表示已知缺陷。两者必须有**真实可访问的跟踪位置、具体问题和完成/移除条件**。可引用真实 issue，也可引用仓库中已有的计划条目；未建立 issue 系统时不虚构编号。

格式示意如下，其中占位符必须替换为真实内容后才能进入代码：

```text
TODO(<真实 issue 或计划条目>): <待完成事项>；<完成或移除条件>
FIXME(<真实 issue 或计划条目>): <已知缺陷及影响>；<修复完成条件>
```

本次新增、修改或发现的任务相关 TODO/FIXME，在交付说明中列出位置、影响和未完成原因。当前授权范围内必须完成的功能，不能用 TODO、空实现、模拟成功或“后续优化”冒充完成；能够在当前任务中修复的应直接修复。范围外事项按已有计划/缺陷流程记录，不因格式规则制造无意义 issue。

### 8.2 Agent 每次改代码的步骤

1. 按 `AGENTS → 项目状态 → docs 导航 → 任务正文` 读取已采用版本的有效规则，再查看所改代码、调用路径、迁移、样板和相关测试；命中哪些专题就读取哪些，已掌握且未变化的内容无需重复加载。
2. 判断本次修改涉及的契约、权限、事务、并发、幂等、精度、状态或文件边界；只补充相关且可核实的注释。
3. 对公开 Service/端口更新契约；在实现和 SQL 处记录机制与理由；前端补充状态、重试、缓存、空值等非显然语义。
4. 核对注释引用的符号、错误码、索引、计划和决定真实存在；确认示例中的名字没有被误当成既有实现。
5. 同步相关 OpenAPI、数据模型和必要的 docs/memory；涉及三份基线变更时另存版本并更新配套引用，避免注释、类型和有效文档各说一套。
6. 按当前任务执行适当检查并如实交付。未执行记为未执行，剩余问题明确列出，不把“写了注释”当作安全、并发或验收证据。

已授权的常规修改持续推进；关键业务信息缺失或规范冲突时指出依据和影响，继续不依赖该信息的工作。本文不增加逐方法、逐阶段的重复确认流程。

以下为后续工程可落地的门禁要求，**本次文档修订未配置这些工具**：

- Java 可用 Checkstyle/Javadoc 检查选定的手写 Service、端口和公共契约；排除生成代码和第三方源码，避免全仓 public 方法注释率考核。
- 前端沿用 strict、类型检查和 ESLint；注释检查关注有意义的契约及局部抑制理由，不为简单组件制造填充注释。
- 脚本可检查新增 TODO/FIXME 的跟踪格式、明显会话式文本、链接和可解析的符号；扫描排除规范示例、历史参考和生成目录，并人工确认误报。
- 格式检查不能证明事务有效、索引被采用、权限完整或注释真实。正确性由代码审查及适当测试核对，性能由实际执行计划和报告支持。
- 不因改进注释门禁而重写已应用迁移、生成文件或历史资产；存量治理单独确定范围，不阻塞无关的低风险改动。

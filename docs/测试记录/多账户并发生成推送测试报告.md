## 1. 结论

| 项 | 结果 |
| --- | --- |
| 100 个账户同时生成 500 枚，再同时分配 | 100 户全部成功 |
| 生成耗时 | 中位 6.0 秒，最慢 7.5 秒 |
| 分配耗时 | 中位 1.6 秒 |
| 5 万枚从开始到全部推送完成 | 33.5 秒（生成加分配 18.3 秒，推送 15.2 秒） |
| 数据库连接峰值 | 77 条（上限 151） |
| 正确性 | SN 互不重复，流水不缺号，没有一枚号被交付两次 |

- 「同一张 PI 同时只能有一个操作」「同一组织的推送并发不超过上限」这两条并发规则都按设计生效。
- 首轮测试发现了死锁和连接不够用的问题，已全部修正（第 5 节）。修正只改了后端内部的加锁和调度，**页面接口和 MES 接口都没有变**。

## 2. 环境

| 项 | 取值 |
| --- | --- |
| 后端 | 1 个进程；连接池 20；同时写号池的生成最多 4 个；推送线程 8 个 |
| 生成 | 不超过 5,000 枚在请求里当场写完；超过的转到后台任务 |
| 推送 | 每批 5,000 枚，同一组织同时最多推 2 批 |
| 推送调度 | 测试时每 1 秒检查一次（正式环境默认 5 秒），以免结果被等待间隔拉长 |
| 数据库 | 缓冲池 8 GB，每次提交都写盘，redo 100 MB，隔离级别 `REPEATABLE-READ`，最大连接数 151 |
| 压测机 | Windows，20 个逻辑处理器，内存 15.6 GB |
| 其他 | 订单同步、每日维护关闭，避免连接公司金蝶 |

## 3. 100 个账户同时操作

**做法：**
- 准备 100 个生产组织、100 个账户，每个账户一张 PI；
- 100 个账户在同一时刻各生成 500 枚；
- 全部返回后，再在同一时刻分配；
- 分配后自动推送到模拟 MES。

| 检查 | 结果 |
| --- | --- |
| 生成成功 | 100 / 100 |
| 生成耗时 | 最快 1.7 秒，中位 6.0 秒，最慢 7.5 秒（含排队等写号名额的时间） |
| 分配成功 | 100 / 100 |
| 分配耗时 | 最快 1.3 秒，中位 1.6 秒，最慢 2.2 秒 |
| 生成加分配 | 18.3 秒 |
| 推送 | 之后 15.2 秒，5 万枚全部推送完成，100 个推送任务全部完成 |
| 号池 | 100 张 PI 各 500 枚，共 5 万枚，去重后仍是 5 万 |
| 流水 | 每张 PI 都是 1 到 500，不缺号 |
| 交付批次 | 100 批全部成功，没有一枚号进了两个批次 |
| 死锁 | 0 次，没有自动重做 |
| 同时写号池 | 最多 4 笔，等于设定的上限 |
| 同时推送 | 最多 8 个，等于推送线程数 |
| 数据库连接 | 峰值 77 条 |

## 4. 并发规则验证

以下 4 组在修正前的代码上测试，全部通过。之后的修正只改加锁和调度，不影响这些规则。

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| 16 个组织同时当场生成 | 16 个账户各 2,000 枚，同时生成再同时分配 | 全部成功；生成中位 3.7 秒，分配中位 0.29 秒；3.2 万枚全部推送，无重复 |
| 同一张 PI 两个人同时操作 | 一个账户生成时，另一个账户对同一张 PI 生成、分配 | 第二个账户收到「PI 正忙」，不执行 |
| 同一组织多张 PI 同时推送 | 一个组织 6 张 PI 各 5,000 枚，同时分配 | 同时推送最多 2 批，没有超过该组织的上限；3 万枚全部推送，无重复 |
| 推送与 MES 拉取同时进行 | 分配后，两个模拟 MES 线程每 0.2 秒拉取一次 | 拉到的就是推送建的批次，没有另建一批；8,000 枚无重复 |
| 两个后端实例同时认领推送 | 两个实例同时运行，4 张 PI 同时分配 | 同一组织同时推送不超过 2 批；2 万枚全部推送，无重复交付 |

## 5. 发现的问题与修正

### 5.1 首轮测试的现象

| 测试 | 现象 |
| --- | --- |
| 8 个账户同时各生成 1 万枚 | 6 个任务死锁失败，整批回滚（没有留下半截数据） |
| 每次只让 2 个账户同时生成 | 每组仍有 1 个死锁 |
| 推送认领下一批时 | 遇到死锁，任务停止，要人工点「继续推送」 |
| 100 个账户同时生成（修正前） | 99 户成功，生成中位 32.2 秒；分配后 15 户没有推完；需要约 200 条连接，超过上限 151 |
| 首页看板 | 每次约 3.4 秒 |

### 5.2 原因与修正

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 同时首次生成时死锁 | 检查新前缀时锁住了索引上的一段区间，几张 PI 的新前缀落在同一区间，互相等待 | 改为按前缀加命名锁，不再锁区间；仍撞上死锁时自动重做，最多 3 次 |
| 生成末尾、计数更新时死锁 | 按整张单据范围更新暂停标记；计数行「不存在就插入」的写法也会锁住区间 | 暂停标记没有变化时不更新；计数行先查再插入，按主键加锁 |
| 建第一个推送任务时死锁 | 对还不存在的任务行加锁再插入，多个组织同时建时互相等待 | 先插入再加锁；遇到死锁自动重做 |
| 推送遇到锁冲突就停止 | 推送中的任何数据库异常都按停止处理 | 遇到锁冲突时等 10 秒自动继续，连续 5 次仍冲突才停止 |
| 推送任务被提前标为运行中 | 一次认领全部任务再排队，排队期间还占着组织的推送名额 | 只认领空闲线程数那么多个任务 |
| 连接不够用、生成要等 32 秒 | 每个生成占一条连接，又要另开连接写进度；线程都在生成时，新连接要等满 30 秒超时 | 写进度等改用备用连接；同时写号池的生成数限制为每进程 4 个，其余排队 |
| 首页看板慢 | 「暂停交付」按没有索引的字段统计，相当于扫描整个号池 | 只统计在途的号，走状态索引 |

### 5.3 修正后的复测

| 测试 | 修正前 | 修正后 |
| --- | --- | --- |
| 8 张 PI 同时首次生成（各 2,000 枚）再分配、推送 | 3 次都失败，共 25 次死锁 | 连跑 6 次通过，死锁 0 次 |
| 12 个新组织同时建第一个推送任务 | 3 次都失败 | 通过 |
| 16 张 PI 各 4,000 枚（后台任务）同时生成再推送 | — | 连跑 3 次通过，6.4 万枚全部推送，流水不缺号 |
| 100 个账户同时操作 | 85 / 100 推完 | 100 / 100（第 3 节） |

- 前两项已写成自动化测试（`tests/test_concurrency.py`），之后每次改代码都会重跑。
- 第三项是临时把同一用例的规模加大后跑的。

## 1. 结论

| 项 | 结果 |
| --- | --- |
| 写入速度 | 每秒 29,743 行；从第 1 个百万到第 10 个百万，速度不变 |
| 号池每行 | 524 字节（含全部索引） |
| 交付记录每行 | 约为号池的 40% |
| 按 SN、按流水查一枚号 | p95 约 0.65 毫秒 |
| 8 GB 缓冲池能装下 | 约 4 个月的号池（按每月 400 万枚） |

- **写入**：保留全部索引、每次提交都写盘时，写入速度不随行数增加而下降。
- **查询**：按 SN、按流水查号都走唯一索引，不到 1 毫秒。
- **体积**：索引比数据本身还大。
- **需要注意的操作**：对整个号池或整张大 PI 做统计（`COUNT`、`GROUP BY`）的耗时随行数线性增长，页面不应直接这样统计。

## 2. 环境与方法

| 项 | 取值 |
| --- | --- |
| 缓冲池 | 8 GB |
| 写盘 | `innodb_flush_log_at_trx_commit = 1`，`sync_binlog = 1`（每次提交都写盘） |
| redo | 100 MB |
| 隔离级别 | `REPEATABLE-READ` |
| 压测机 | Windows，20 个逻辑处理器，经内网连接数据库 |

**方法：**
- **写入方式**：两条连接各写一半，区间互不重叠，每 2,000 行提交一次。用的是号池的真实表结构和全部索引，唯一性检查开启。
- **测试数据**：PI 为 `PI-STORE`，流水 1 到 10,000,000，SN 为 `W` 加 10 位序号，状态均为已推送。
- **测的是什么**：这是直接批量写入，测的是表本身的写入能力。页面生成还要计算规则、加锁，速度另测。

## 3. 写入

| 进度 | 用时 |
| --- | ---: |
| 100 万行 | 32 秒 |
| 500 万行 | 2 分 45 秒 |
| 1,000 万行 | 5 分 36 秒 |

| 指标 | 结果 |
| --- | ---: |
| 平均吞吐 | 29,743 行/秒 |
| 每批 2,000 行提交耗时（中位） | 128 毫秒 |
| 每批提交耗时（p95） | 177 毫秒 |
| 每批提交耗时（最慢） | 279 毫秒 |

每 20 万行抽查一批，耗时始终在 103–173 毫秒之间，没有随行数升高。

## 4. 体积

### 4.1 号池

2026-11-09 复测，全表 1,022 万行。其中 1,000 万行为本次写入，22 万行为并发测试留下的数据。

| 项 | 结果 |
| --- | ---: |
| 数据 | 2.24 GB |
| 索引 | 2.75 GB |
| 合计 | 4.99 GB |
| 每行 | 524 字节 |

- 只算 2026-11-06 写入的 1,000 万行时，每行 503 字节。之后按全表平均值 524 字节计算。
- 索引包括：2 个唯一索引（完整 SN、PI 内流水），5 个普通索引（取号、状态、单据、批次、MES 持有组织）。
- 按每月 400 万枚折算，号池每月约增长 2.0 GB。

### 4.2 交付记录

本地 MySQL 8.0 补测。两张表各写 100 万行，字段内容相同：SN 16 位，单据号 16 位，物料、客户为常见长度。

| 表 | 文件大小 | 每行 |
| --- | ---: | ---: |
| 号池 | 667 MB | 667 字节 |
| 交付记录 | 268 MB | 268 字节 |

- **为什么小**：交付记录只存交付需要的字段，索引也只有 3 个，每行约为号池的 40%。
- **行数**：每枚号至少交付一次；转单、转组织后再交付，会再多一行。
- **单行比 4.1 大的原因**：本地补测用的字段内容比 4.1 长，所以号池每行是 667 字节，不是 524 字节。

## 5. 查询

2026-11-09 复测。数据都在缓冲池里，在同一条连接上连续查询 400 次，耗时含压测机到数据库的网络往返。

| 查询 | 走的索引 | p50 | p95 | p99 |
| --- | --- | ---: | ---: | ---: |
| 按完整 SN 查一枚 | SN 唯一索引 | 0.44 毫秒 | 0.65 毫秒 | 0.85 毫秒 |
| 按 PI + 流水查一枚 | 流水唯一索引 | 0.44 毫秒 | 0.66 毫秒 | 0.83 毫秒 |

| 查询 | 耗时 | 说明 |
| --- | ---: | --- |
| 认领待推送的号（每次 5,000） | 0.60 毫秒 | 走取号索引 |
| 统计在途数量（待分配、待推送、已分配） | 41 毫秒 | 走状态索引，不随累计枚数增长 |
| 全表计数（1,022 万行） | 1.26 秒 | 随行数线性增长 |
| 一张 PI 按状态汇总（1,000 万行） | 3.66 秒 | 随这张 PI 的行数线性增长 |

后两项说明：对整个号池或整张大 PI 做统计会越来越慢，页面上的数字要改从汇总表读取。

## 6. 测试数据

测试数据留在 `sn_dev`：

| 数据 | 行数 | 说明 |
| --- | ---: | --- |
| PI `PI-STORE`（组织 `ZSTORE`） | 1,000 万 | 本次写入，约 4.7 GB |
| 并发测试留下的数据 | 22 万 | PI 前缀 `PIZT`、`PA`、`PB20`、`ZP`、`PD22`、`PC21` |

这批数据会占用共用实例的缓冲池。确认不再需要后，按下面两步在 `sn_dev` 清理。要在低峰时执行。

1. **分批删除**：每次删 10 万行，反复执行，直到影响行数为 0。一次删 1,000 万行会形成一个超大事务。

   ```sql
   DELETE FROM sn_item WHERE seq_pi_no = 'PI-STORE' LIMIT 100000;
   ```

2. **重建单据汇总**：数据是直接在库里删的，没有经过程序，删完要按号池重建一次单据汇总：

   ```bash
   uv run python -m devtools.rebuild_bill_stat --rebuild
   ```

组织 `ZSTORE` 只是一行主数据，可以保留。

# 容量与扩展规划

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.1（2026-11-09：增补第 7 节「3 年合理性评估」；阶段 2.1 单据汇总表已实现） |
| 依据 | 《数据库存储压测报告》《多账户并发生成推送测试报告》（含末尾「报告之后的修正」）、当前代码 |
| 适用 | 并发增长、号池与交付明细增大后，怎样保证查询不变慢 |

本文只写规划：分几步做、什么时候做、改不改表结构和接口。配置项、部署步骤以[运维手册](运维手册.md)为准。

## 1. 目标与约束

**不变的：**

- MES 接口（请求、应答、错误码）不变；
- SN 全局不重复、同一枚号不重复交付；
- 同一 PI 的操作串行（`PI_BUSY`），这是业务规则，不当作性能问题处理。

**性能目标（p95）：**

| 场景 | 目标 |
| --- | --- |
| 按 SN、按流水点查 | ≤ 50 毫秒 |
| 页面列表（分配页、SN 查询、交付批次、首页看板） | ≤ 1 秒，且不随累计枚数增长 |
| MES 取批、回执 | ≤ 2 秒 |

**容量假设**：需求写的每月约 400 万枚；压测实测每行约 503 字节（含全部索引）；交付明细 `sn_delivery_item` 每次交付一行，与号池量级相当。号池不分区、不归档时累计如下：

| 期限 | 号池行数 | 号池 | 号池 + 一次交付 |
| --- | ---: | ---: | ---: |
| 1 年 | 4,800 万 | 22 GB | 45 GB |
| 3 年 | 1.44 亿 | 67 GB | 135 GB |
| 5 年 | 2.4 亿 | 112 GB | 225 GB |

按这个量级，**单台 MySQL 加冷热分离足够，不分库分表**（见第 4 节）。

## 2. 现状

### 2.1 部署

一台机器，Docker 两个容器：

| 容器 | 内容 |
| --- | --- |
| `api` | uvicorn + FastAPI。进程数由 `SN_WORKERS` 决定（默认 1） |
| `web` | nginx，托管前端页面，`/api` 转发给 `api:8000` |

MySQL 在 `10.0.200.125`，目前与 `sn_dev`、`sn_test`、`sn_local` 共用一个实例。

每个 `api` 进程内部：

- 外层是 uvicorn 的异步事件循环，负责收发请求；
- 页面接口是同步函数，在线程池里执行（约 40 个线程）；
- MES 接口是 `async`，内部经 `run_sync` 转到线程里执行；
- 数据库驱动是同步的 PyMySQL；
- 后台另有生成线程 4 个（同时写号池不超过 `SN_GEN_CONCURRENCY`）、推送线程 8 个，以及订单同步、每日维护、生成任务回收的定时线程。

### 2.2 为什么用多进程、不改全异步

异步和线程解决的是**等待**：一个请求在等 MySQL 或 MES 时，别的请求可以接着处理。它们解决不了**计算**：Python 有全局解释器锁，同一进程里的线程同一时刻只能有一个在执行 Python 代码，所以一个进程最多用满 1 个 CPU 核。

改成全异步（换 aiomysql、asyncmy 等驱动）不划算：

1. 要重写连接池、事务（当前用 contextvar 跟踪当前事务）、命名锁，services 里约 1.8 万行同步代码几乎都要改，与 MES 联调通过的行为要整体重测；
2. 仍是单进程、单核，拼 SN、gzip 报文、生成 xlsx、口令哈希照样只能用一个核；
3. 压测暴露的瓶颈在数据库的锁、死锁和连接数，异步只是让更多请求同时去等数据库。

所以**用上多核靠多进程**（`SN_WORKERS`）。代码本来就按多实例设计：
- 生成、分配用 MySQL 命名锁；
- 推送任务有租约和认领互斥；
- 订单同步、每日维护有锁，并按间隔只执行一次；
- 启动初始化在命名锁内依次进行。

### 2.3 会随累计枚数变慢的查询

| 位置 | 问题 |
| --- | --- |
| ~~SN 分配页左侧单据列表（`allocation.bills`，不带页签、「已分配」页签）~~ | ~~按 PI + 单据对整个号池 `GROUP BY`~~ → 已改查单据汇总（2.1） |
| ~~SN 导出单据列表（`sn_export.py`）~~ | 同上，已改查单据汇总 |
| SN 查询的状态汇总（`query.py`） | 筛选条件宽时扫描范围大（总数已有上限，不受影响） |
| 各列表的 `LIMIT 偏移, 条数` 分页 | 翻得越深越慢 |
| 操作痕迹关键字搜索（`LIKE '%x%'`） | 只能扫描，靠时间范围收窄 |
| 号池、交付明细 | 不分区、不归档，一年约 45 GB，是当前 8 GB 缓冲池的 5 倍多 |

已处理的：
- 首页「暂停交付」的全表扫描；
- 并发生成、分配、推送的死锁与连接互等（见《多账户并发生成推送测试报告》末尾）；
- SN 查询总数有上限；
- 按单据下载用键集翻页；
- 操作痕迹按月分区并归档；
- 分配页、SN 导出页的单据列表改查单据汇总表（2.1，2026-11-09）；
- 规则前缀「不能一个是另一个的开头」的检查改走前缀索引，不再整表扫描规则版本（第 7.2 节）。

## 3. 分阶段方案

### 阶段 0：上线前（运维，不改代码）

| 项 | 内容 | 落实 |
| --- | --- | --- |
| 0.1 正式库独立实例 | `sn_prod` 不与开发、测试库共用 MySQL。压测时 1,000 万行就占住约 4.7 GB 缓冲池，影响同实例的其他库 | 待 DBA 提供 |
| 0.2 数据库资源 | SSD；`innodb_buffer_pool_size` 取内存的 60–70%，按「最近 3–6 个月的号池 + 交付明细能放进去」来定；redo 从 100 MB 调到 1–2 GB | 待 DBA 提供 |
| 0.3 打开观测 | 慢查询日志 `long_query_time=0.5`；`innodb_print_all_deadlocks=ON`；每周看一次第 5 节的指标 | 上线前 |
| 0.4 增量迁移 | 正式上线后不再改 V1 后重建库，表结构变更一律写 `V2__…sql` 这样的增量脚本（`app/db/migrate.py` 已兼容 Flyway 的版本顺序与校验）。阶段 2、3 依赖这一条 | 已确认 |

### 阶段 1：CPU 或接口排队成为瓶颈时（只改配置）

**已具备，不用改代码。**

- **触发**：`api` 容器 CPU 长时间接近 100%（单核），数据库却不忙；或接口在线程池里排队。
- **做法**：`.env` 设 `SN_WORKERS=2`～`4`（不超过 CPU 核数），执行 `docker compose up -d --force-recreate api`。步骤见运维手册第 2 节「多进程」。
- **连接预算**：每个进程最多约 `2 × DB_POOL_SIZE` 条池内连接，另加命名锁各一条，所有进程合计须低于 MySQL `max_connections`（默认 151）。例如 3 个进程、`DB_POOL_SIZE=15`，约 135 条。
- **生成并发**：`SN_GEN_CONCURRENCY` 是每个进程各自的上限，3 个进程时每个设 2。
- **已知限制**：订单同步进度只记在执行它的进程内存里，页面请求落到别的进程时只显示「同步进行中」。
- **再往后**：同样的配置可以放到多台机器上，前面用 nginx 分发；实例多了用连接池代理（如 ProxySQL），或请 DBA 调大 `max_connections`。

### 阶段 2：号池过 1,000 万（约上线后 3 个月）

改表结构和后端代码（增量迁移），MES 接口不变。

**2.1 单据汇总表**（收益最大）——**已实现（2026-11-09）**，实现见 `app/services/bill_stats.py`，表 `sn_bill_stat`、`sn_bill_stat_dirty`。
与下面的设计相比的差别：列表查询前先把待重算的单据同步重算完（最多 3 秒，超出的留给后台），所以通常读到的就是最新值，
不是「秒级延迟」；每个（PI，单据，号上的生产组织）一行，导出页按组织列出、分配页按 PI + 单据再相加，两页共用一张表。

- 新表：每个（PI，单据）一行，记枚数、待分配、待推送、未入批、暂停、最近处理时间。
- 维护方式：「标脏 + 后台重算」。号的状态一变，就把所在单据标为待重算；后台每几秒按单据重算。
  - 号的状态在生成、删号、分配、建批、回执、人工确认或作废、转移、导入、暂停等多处变化，逐处精确加减容易漏；
  - 标脏只要求「改了就标」，即使出错，下一次重算也会纠正。
- 页面数字有秒级延迟（**已确认可接受**）。分配、转移等操作照旧在事务内重新检查，不受影响。
- 分配页左侧列表、SN 导出单据列表、首页各状态枚数、各 PI 统计改查这张表，耗时只与单据数有关。
- 每日交付自检加一项对账：汇总表与号池不一致时，自动重算该单据并产生告警。另配一个整表重建工具（`devtools/`）。

**2.2 精简索引**

- 号池索引（2.56 GB）比数据（2.19 GB）还大，取号组合索引 `ix_item_claim` 有 7 列。
- 上线 1–2 个月后，用 `sys.schema_unused_indexes` 和慢查询日志找出不用或重复的索引，删掉或合并。写入与缓存占用都会下降。

**2.3 只读从库**（待 DBA 提供从库）

- 走从库，接受秒级延迟：SN 查询、导出、操作痕迹、交付批次列表、首页看板；
- 留在主库：生成、分配、推送、MES 接口、转移；
- 代码改动：新增一个只读连接（单独的连接目标与连接池），只读接口指定走它；从库不可用或延迟过大时自动回主库。

**2.4 深分页**

- SN 查询、交付批次列表改为「从上一页最后一条往后取」（键集分页）。
- 这会改页面接口的分页参数，前后端一起改（**已确认**），不影响 MES 接口。
- 页面保留「上一页 / 下一页」和总数（总数照旧有上限），不再支持跳到任意页。
- **2026-11-09 暂缓**：本轮要求接口一律不动（含页面接口的分页参数），所以没有做。深分页只在往后翻很多页时变慢，
  默认按时间倒序、首屏和前几页不受影响；要做时须前后端一起改，届时再确认。

### 阶段 3：号池过 1 亿（约 2 年）或超过缓冲池 3 倍：冷热分离

MySQL 分区要求唯一键包含分区字段，而「完整 SN 全局唯一」的唯一键只有 SN 一列，所以号池不能直接按时间分区。拆成三张：

| 表 | 内容 | 规模 |
| --- | --- | --- |
| SN 唯一登记表（新） | 只有 SN 一列做主键；生成、导入时先登记，删号时同时删除（删号腾出 SN 的规则不变） | 每行约 40 字节，10 年 4.8 亿行约 20 GB，永久在线 |
| 号池（热，现有 `sn_item`） | 在途的号，加还没归档的 PI | 保持几个月的量，放得进缓冲池 |
| 历史号池（冷，新） | 已归档 PI 的号，按归档月份分区；交付明细同步归档 | 只供查询、追溯 |

**归档规则：**

- **按整张 PI 归档，不按单枚号**：空号段、最大流水、接续编号都按 PI 在号池里统计（`generate.gap_segments` 等），只搬走一部分号会凭空多出空号段。
- **归档条件**：PI 的号全部已交付；没有未确认或失败的批次；没有进行中的转移或订单变更提醒；且 **6 个月**无变动（已确认）。
- **保留期限**：冷数据与操作痕迹一致，在线 3 年、总共 5 年；超过的按年导出备份后删除（届时再确认）。

**归档后：**

- **查询**：先查热表，查不到再查冷表，结果标「已归档」。做法与现在操作痕迹查归档相同。
- **MES 取批、回执**：只涉及在途批次，不碰冷表。
- **对已归档 PI 再生成、转移、删号**：先把整张 PI 恢复到热表再操作。频率很低，接受慢一点。

### 不做的事

- **分库分表、换分布式数据库**：按需求量级（3 年 1.5 亿、5 年 2.4 亿），单台 MySQL 加冷热分离足够。SN 全局唯一、不重复交付、PI 串行都靠单库事务保证，分库后会复杂很多。业务量到现在的 10 倍以上时再评估。
- **缓存层（如 Redis）**：看板、列表改查汇总表后已经够快，多一个组件就多一个数据不一致的来源。
- **全异步改造**：见 2.2。

## 5. 监控指标与触发阈值

| 指标 | 看哪里 | 触发 |
| --- | --- | --- |
| 号池行数、表大小 | `information_schema.tables` | 过 1,000 万 → 阶段 2；过 1 亿或超过缓冲池 3 倍 → 阶段 3 |
| 缓冲池命中率 | `Innodb_buffer_pool_reads` / `Innodb_buffer_pool_read_requests` | 命中率低于 99% → 加内存或提前做阶段 3 |
| 慢查询 | 慢查询日志 | 同一类查询每天超过 100 次 → 针对性优化 |
| 接口 p95 | nginx 访问日志按路径统计 | 超过第 1 节目标 → 按原因进入相应阶段 |
| `api` CPU | `docker stats` | 长时间高于 80%（单核）→ 阶段 1 |
| 连接数 | `Threads_connected`、日志 `db_pool_exhausted` | 超过 `max_connections` 的 70% → 调整连接预算 |
| 死锁、锁等待 | `innodb_print_all_deadlocks`、日志 `gen_deadlock_retry`、`push_task_conflict` | 每天持续出现 → 排查 |

## 7. 3 年合理性评估（2026-11-09）

按需求量级（每月约 400 万枚、3 年约 1.5 亿枚）逐项看容量、编码规则、性能能不能撑过 3 年；**MES 接口、页面接口都不改**。
本轮改了两处（单据汇总表、前缀检查走索引），其余是评估结论与建议。

### 7.1 容量

| 表 | 3 年规模 | 体积 | 依据 |
| --- | ---: | ---: | --- |
| `sn_item` 号池 | 1.5 亿行 | 约 73 GB | 实测全表 524 字节/行（含全部索引，《数据库存储压测报告》千万行复测） |
| `sn_delivery_item` 交付明细 | ≥ 1.5 亿行（每次交付一行，转移、改挂后再交付另加） | 与号池相当 | 第 1 节估算，未单独实测 |
| `sn_delivery_batch` 交付批次 | 约 3 万批（5000 枚/批） | 估几 GB（每批存一份 gzip 报文） | 估算 |
| `sn_audit` 操作痕迹 | 按操作计，不按枚数 | 小 | 按月分区，在线 3 年后归档 |
| `sn_bill_stat` 单据汇总（新） | ≈ 单据数 × 组织数 | 30 万行 65 MB | 本轮实测 |
| `sn_bill_stat_dirty` 待重算 | 常态接近 0 | 可忽略 | 每 2 秒处理一次 |

- **数值与编号不会用完**：各表主键、流水都是 BIGINT；流水最多 12 位（36 进制 12 位约 4.7×10¹⁸，小于 BIGINT 上限 9.2×10¹⁸）；SN 最长 64 字符；
  批次号每组织每天 6 位序号；业务单号按秒加 4 位随机数。时间字段 DATETIME 到 9999 年。
- **3 年资源建议**（阶段 0，待 DBA）：号池与交付明细合计约 150 GB，加 binlog、备份，磁盘按 ≥ 500 GB SSD 准备；
  缓冲池按「最近 3–6 个月的号池与交付明细 + 各唯一索引」定，约 32–64 GB。
- **冷热分离（阶段 3）**：原定号池过 1 亿（约 2 年）触发，落在 3 年之内。单据列表改查汇总表后，随累计枚数变慢的查询只剩
  深分页与宽条件查询（7.3），按 SN、按流水点查走唯一索引，数据超过缓冲池也只多几次读盘。**建议**：触发条件改为
  「缓冲池命中率持续低于 99% 且加内存不划算」，不按行数；PRD 写的是「SN 不分区、不归档、不删除」，届时须与业务确认（待确认）。

### 7.2 编码规则

**流水容量**：一张 PI 一套流水（`sn_pi_counter`），PI 下所有物料行、所有规则共用；每条规则能写到的最大流水是 `进制^位数 − 1`。
超出时预演就报 `GEN_RULE_EXHAUSTED`、不会写号，不会撞号。

| 规则 | 一张 PI 最多 |
| --- | ---: |
| 10 进制 4 位（订单数量小时自定义规则的默认值） | 9,999 |
| 10 进制 6 位 | 999,999 |
| 36 进制 4 位 | 1,679,615 |
| 36 进制 6 位 | 约 21.8 亿 |

- **已改（2026-11-09）**：自定义规则的流水位数默认值改为按本 PI 的订单数量给：取装得下「已用到的流水 + 全部物料行还可生成的数量 × 1.2」的最少位数，
  至少 4 位（订单数量小的 PI 与原来相同），最多 12 位；例如 12 万枚的 PI 默认 10 进制 6 位、36 进制 4 位。改进制时没手动改过的位数随之重算；
  本 PI 已用前缀时格式锁定、不变。位数不够装下订单数量时（例如手动改小），流水行下方提示加位数或换进制。只改生成页的默认值与提示（前端），
  页面接口、MES 接口、后台校验都不变；订单之后加量超过 20% 余量时，仍由预演的 `GEN_RULE_EXHAUSTED` 拦下。
- **注意**：不同 PI 的 SN 长度会随订单数量不同，须确认 MES 与标签能接受变长的 SN。规则库新建规则的默认位数（5 位）不变：规则库的规则会被别的 PI 沿用。
- **前缀命名空间**：同一前缀只归属一张 PI，任何两个前缀不能一个是另一个的开头。自定义前缀默认取单据编码后 7 位，长度都是 7，
  互相不会「一个是另一个的开头」；冲突主要来自规则库里长度不一的前缀（例如有人用了 `S`，之后所有 `S` 开头的前缀都不能用）。
  前缀**不定长**（已确认）：现有校验按长度对齐比内容（短的与长的开头那几位比），比出不同就一定不重号，所以不要求定长；只建议规则库少用 1–2 位的短前缀，免得挡住一大片。
- **检查本身的性能**（本轮已改）：前缀检查原来每次整表扫描规则版本（`LEFT(...) = ...` 用不上索引），每张 PI 至少一个版本，
  3 年后上万行，生成时每个前缀要查两次。改为两头都走前缀索引 `ix_rule_prefix`：更长的前缀按 `LIKE '前缀%'` 取索引区间，
  更短的按前缀的各个真前缀等值查。结果与原写法相同（3,000 个含 `%`、`_`、`\`、空格、中文的随机前缀逐个比对，0 处不同；
  报出的冲突前缀仍是最早建的那一版），错误码与提示不变。

### 7.3 性能

**本轮已改：单据汇总表（阶段 2.1）**。分配页左侧单据列表（全部、待分配、已分配）、SN 导出页单据列表改查 `sn_bill_stat`，
耗时只与单据数有关、与累计枚数无关。本地 MySQL 8.0.46（Docker 默认缓冲池 128 MB）实测，一次翻页 = 总数 + 第一页 20 行：

| 场景 | 原：按号池 GROUP BY | 新：查单据汇总 |
| --- | ---: | ---: |
| 号池 500 万枚 / 1 万张单据，分配页 | 21.7 秒 | 22 毫秒 |
| 号池 500 万枚 / 1 万张单据，导出页 | 38.1 秒 | 15 毫秒 |
| 30 万张单据（约 3 年，每单 500 枚），分配页「全部」 | — | 0.72 秒 |
| 30 万张单据，分配页「待分配」页签 | — | 0.45 秒 |
| 30 万张单据，导出页「全部」/ 单个组织 | — | 0.42 / 0.13 秒 |

新旧两种写法返回的单据、数字、排序逐行相同。本地缓冲池小，原写法的绝对耗时比 `sn_dev`（8 GB）慢；按 `sn_dev` 千万行一张 PI
3.7 秒线性推算，1.5 亿枚时原写法一次翻页要 1 分钟以上（总数与当页各汇总一次），超过页面 120 秒超时的一半，新写法不受影响。

**正确性**：
- 号的挂靠或状态一变（生成、导入、删号、分配、建批、回执、人工确认或作废、转单、转组织、订单变更改挂、暂停、对接开关），
  同一事务里标脏，提交前一起写入，回滚就一起撤销（死锁整笔重做时另起一份）。
- 列表打开前先把待重算的单据算完（最多 3 秒），后台每 2 秒也算一次，通常读到的就是最新值；重算全局串行，不会有旧结果覆盖新结果。
- 每日维护抽查最近 2000 张单据对账，不一致的记 `bill_stat_mismatch` 并重算；`devtools.rebuild_bill_stat` 可全量对账或整表重建（运维手册 8.8）。
- 自动化测试每个用例结束时都把汇总表与号池重新汇总的结果整表比对（`tests/conftest.py`），全部 384 个用例通过。

**上线影响**：两张表按 V1 + `ADDED_TABLES` 补建，已建好的库（如 `sn_dev`）启动时自动建表并按号池回填一次（日志 `bill_stat_rebuilt`），
回填是一致性读、不锁号池；本地 500 万枚回填 23 秒，千万行估计一两分钟。V1 校验和变了，已建好的库启动时照常只记 `migration_checksum_mismatch` 警告。

**仍会随数据增长变慢的（未改，原因与触发）**：

| 位置 | 3 年情况 | 处理 |
| --- | --- | --- |
| 单据汇总表本身 | 30 万张单据时分配页「全部」0.72 秒，5 年约 50 万张时约 1.2 秒 | 超过 1 秒目标时给汇总表加按 PI + 单据的一层与 `handled_at` 索引（只改内部） |
| 列表深分页（`LIMIT 偏移`） | 翻到很后面才慢 | 键集分页要改页面接口的分页参数（2.4），本轮不改接口，暂缓 |
| 生成页、分配页的各 PI 统计（`workbench.item_stats`） | 按当页 PI 的号汇总，只与这几张 PI 的枚数有关 | 单张 PI 上百万枚时再改查汇总表 |
| SN 查询 | 必须选 PI，总数上限 10 万 | 不随累计枚数变慢 |
| 操作痕迹关键字 | `LIKE '%x%'`，靠时间范围收窄 | 按月分区，默认最近 30 天 |
| 汇总重算 | 每次按单据重算，耗时与单据枚数成正比；一张 5 万枚的单据推送中每批回执都会重算一次 | 后台合并 2 秒内的改动；单据极大时再改为按物料行重算 |

### 7.4 结论

- **3 年可以撑住**，前提是阶段 0（独立实例、内存、SSD、慢查询日志）落实；单台 MySQL，不分库分表、不加缓存层的判断不变。
- 本轮完成：单据汇总表（原来 3 年内最先失控的两处列表）、前缀检查走索引。
- 已改：自定义规则的流水位数默认值按本 PI 订单数量给（7.2）。
- 待确认：冷热分离的触发条件（7.1）、深分页何时改页面接口（2.4）。

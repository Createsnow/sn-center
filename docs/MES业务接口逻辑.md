## 1. 概述

### 1.1 接口一览

| 接口 | 调用方向 | 地址 | 什么时候调 | 接口文档 |
| --- | --- | --- | --- | --- |
| 推送接口 | SN 系统 → MES | `{MES 地址}`（MES 提供） | 连接测试；分配、转移、续推后推送批次 | 3.1 |
| 回执接口 | MES → SN 系统 | `POST /api/mes/v1/receipts` | 推送来的、拉取到的批次处理完后，每一批都要调 | 3.3 |
| 拉取接口 | MES → SN 系统 | `POST /api/mes/v1/batches/next` | 推送失败后、本地 SN 不够用时、每 5 分钟兜底 | 3.2 |
| 查询接口 | MES → SN 系统 | `POST /api/mes/v1/sn/delivered`、`POST /api/mes/v1/batches/items` | 可选，对账 | 3.4、3.5 |

第 2～5 节每个接口按同一顺序说明：调用说明（触发、调用方发什么、对方回什么、调用方怎么判断、结果的作用）→ 正常流程（步骤 + 时序）→ 各种业务情形 → 没送达的重试 → 直接失败、不原样重试的应答。

### 1.2 两个「OK」的含义

| 出现在 | `code = OK` 的含义 | 不表示 |
| --- | --- | --- |
| 推送接口的应答（MES 回给 SN） | MES **已收到**这一批（连接测试同样回 `OK`） | 不表示已处理、已落库 |
| 回执接口的请求（MES 发给 SN） | MES **已处理**这一批（整批落库） | — |
| 回执接口的响应（SN 回给 MES） | SN **已收到这份回执** | 不表示批次成功；批次结果看 `batchResult` |

### 1.3 总体规则

- **批次确认以回执为准**：推送接口的应答只表示收到。SN 系统收到回执 `OK` 才确认这一批；收到 `NG` 批次记失败。人工确认除外（第 6 节）。
- **串行推送**：同一生产组织、同一 PI 的批次一批一批地推，上一批回执 `OK` 后才推下一批；转出批次单独一个推送任务。
- **批次号是幂等键**：同一批次可能多次送达，也可能经推送接口、拉取接口都到达，MES 按 `batchNo` 只处理一次；同一批次每次送达内容逐字节相同。
- **回执也幂等**：同一份回执可以重复提交，SN 系统按批次号处理，已确认的批次只存档。
- **业务问题不用 4xx**：缺字段、组织不符、本组织没有这张 PI 等，推送接口照常回 `OK`，再用回执 `NG` 整批退回。4xx 只用于认证、地址、报文过大、无法解析。

## 2. 推送接口（SN 系统 → MES）

### 2.1 连接测试

| 步骤 | 说明 |
| --- | --- |
| 触发 | 总部在「生产组织」页填好 MES 对接配置，点「连接测试」 |
| SN 发什么 | 调推送接口，发测试批次：`batchType = PING`、`count = 0`、`items = []`、不带 `pi`，批次号 `PING-` 加时间戳。认证方式、gzip、超时都与真实推送相同 |
| MES 回什么 | 校验身份和 `orgCode`，通过回 HTTP 200 + `code = OK`；`orgCode` 不是本组织回 `NG`。测试批次不落库、不记批次号、**不调回执接口** |
| SN 怎么判断 | 只有 HTTP 200 + `code = OK` 算连接成功，其他一律失败；不核对 `batchNo` |
| 结果的作用 | 测通后记下这份配置的摘要（组织、地址、认证方式、凭证、gzip）。开启「对接 MES」须当前配置已测通；已开启时改了地址、认证、凭证或 gzip，须先用新配置测通才能保存 |

### 2.2 真实推送：正常流程

1. SN 调推送接口，MES 回 HTTP 200 + `code = OK`，`batchNo` 照抄请求体，表示数据已到 MES。
2. SN 把这一批标为「等回执」，推送任务暂停等待，后面的批次先不推。
3. MES 校验、落库后调**回执接口**，报告处理结果（`OK` / `NG`）。
4. MES 检查回执接口的响应：HTTP 200 + `code = OK` 才算回执已送达，否则按 3.4、3.5 重交或处理。
5. SN 收到回执 `OK`：这一批成功，号改为「已推送」，**立即**推下一批。

```
SN 系统 ──推送接口：批次──────────▶ MES      应答 200 + OK（已收到）
                                    MES      校验、落库
SN 系统 ◀──回执接口：OK / NG─────── MES
SN 系统 ──回执接口的响应──────────▶ MES      200 + OK（回执已送达）
SN 系统 ──推送接口：下一批────────▶ MES      ……
```

### 2.3 真实推送：MES 整批退回

| 一方 | 做什么 |
| --- | --- |
| MES | 推送接口照常回 `OK`；处理时发现整批不能接收，调回执接口报 `NG`，`message` 写原因，不写入任何数据，也不登记批次号（修正后同一批次号重送能正常处理） |
| SN 系统 | 批次记失败（失败码 `REJECTED`，可作废），推送任务停止，总部页面显示原因 |
| 总部 / MES | 问题修好后，MES 照常拉取（或带 `batchNo` 取回）拿到这一批重处理并交回执 `OK`，推送任务自动接着推（4.5）；或总部点「继续推送」，用原批次号、原内容重推；或作废这一批，号回到号池重新建批 |

### 2.4 真实推送：MES 已收到但一直没交回执

| 阶段 | 说明 |
| --- | --- |
| 等回执、重推 | 收到 `OK` 后等 1 分钟，没有回执就用原批次号、原内容重推，再等 5 分钟；再重推，再等 10 分钟；再重推，再等 10 分钟。一共重推 3 次 |
| MES 收到重复的同一批 | 照常回 `OK`，并**立即重交第一次的处理结果**（第一次的回执可能没交上来） |
| 仍然没有回执 | 批次推送状态记为「重试用尽」（失败码 `RECEIPT_TIMEOUT`），推送任务停止，后面的批次不推 |
| MES 之后补交回执 | 这一批确认成功，已停止的推送任务自动接着推后面的号，不用点「继续推送」 |

### 2.5 真实推送：没送达，自动重试

| 项目 | 说明 |
| --- | --- |
| 哪些情况 | 超时（默认 60 秒）、断连、5xx、429、503、409 `BATCH_IN_PROGRESS` |
| 怎么重试 | 隔 1、5、15 分钟重送相同内容；MES 带 `Retry-After`（秒）时取两者中较大的 |
| 重试用尽 | 批次推送状态「重试用尽」，推送任务停止 |
| 其实已经送到 | MES 照常交回执，SN 收到即确认，并接着推下一批 |

### 2.6 真实推送：直接失败，不重试

| MES 的应答 | SN 的处理 | 能否作废 |
| --- | --- | --- |
| HTTP 200，但 `code` 不是 `OK`（如 `RECEIVED`、`NG`） | 应答无效（`RESPONSE_INVALID`），批次失败 | 否（MES 可能已处理） |
| HTTP 200，但 `batchNo` 不是这一批 | 应答不符（`RESPONSE_MISMATCH`），批次失败 | 否 |
| 401 / 403 | 认证失败，批次失败；组织配置状态标为「异常」 | 是 |
| 404 | 地址错误，批次失败；组织配置状态标为「异常」 | 是 |
| 413 | 报文过大，批次失败 | 是 |
| 400 | MES 无法解析，批次失败 | 是 |
| 409 `BATCH_CONTENT_MISMATCH` | 同一批次号内容不同，批次失败，需排查 | 否 |
| 其他 4xx | 批次失败 | 否 |

所有情况推送任务都停止，失败原因显示在总部页面。

### 2.7 回执比推送应答先到

MES 可能先调回执接口、后回推送应答（或推送应答在网络上丢失）：

- 回执 `OK` 先到：批次直接确认，推送应答到了也按「已确认」处理，接着推下一批。
- 回执 `NG` 先到（首次推送，或「继续推送」重推失败批次时）：批次记失败，推送应答到了不会改回等回执，推送任务停止并显示原因。
- 推送任务刚进入等待时回执到了：SN 发现批次状态已变，立即再跑一次推送任务。

## 3. 回执接口（MES → SN 系统）

### 3.1 调用说明

| 步骤 | 说明 |
| --- | --- |
| 触发 | 推送来的、拉取到的批次处理完（整批落库，或决定整批退回）后，**每一批都要调**；连接测试批次不调 |
| MES 发什么 | `batchNo`：所回执的批次号，与下发的完全一致（区分大小写、不带空格）；`code`：`OK` 整批已处理（含逐枚跳过的旧版本）/ `NG` 整批退回，只能是这两个值；`message`：处理说明，`NG` 时为退回原因，显示在总部页面；`processedAt`：处理完成时间（UTC+8，`yyyy-MM-dd HH:mm:ss.SSS`）。请求头带 MES 接口账户 `Authorization: Bearer <工号>:<密钥>`，只能回执本组织的批次；请求体必须是原始 JSON，不支持 gzip |
| SN 回什么 | 收下回执回 HTTP 200 + `code = OK`，`batchNo` 照抄请求体；`batchResult` 为批次结果（`SUCCESS` / `FAILED`），`firstConfirmation` 表示这份回执是否改变了批次。出错不返回 200（3.5） |
| MES 怎么判断 | 只有 HTTP 200 + `code = OK` 且 `batchNo` 与提交的一致算**已送达**，`firstConfirmation` 为 `true` 或 `false` 都算；超时、断连、5xx、429 算没送达（3.4）；其他 4xx 算送达失败（3.5）。不要用 `code` 判断批次成败，批次结果看 `batchResult` |
| 结果的作用 | SN 收到 `OK` 确认这一批、推下一批；收到 `NG` 批次记失败、推送任务停止。MES 在本地记下每批回执的提交状态（待提交 / 已送达 / 送达失败 / 已作废） |

### 3.2 回执：正常流程

1. MES 处理完一批，**先把回执写入本地**（待提交），再调回执接口。
2. SN 核对批次号属于本组织、没有作废，按 `code` 处理：
   - `OK`：整批成功，逐枚记为已接收，号改为「已推送」并记 MES 持有组织；转出批次则清除这些号在原组织 MES 的持有记录。
   - `NG`：整批失败（失败码 `REJECTED`，可作废），原因取 `message`。
3. SN 回 HTTP 200 + `code = OK`，带 `batchResult`、`firstConfirmation`；每一份回执（包括只存档的）都留档，可在总部「交付批次」详情里查看。
4. MES 检查响应，记为「已送达」。
5. SN 唤醒正在等这一批的推送任务：`OK` **立即**推下一批；`NG` 推送任务停止，总部页面显示原因（2.3）。

```
MES      处理完一批，回执写入本地（待提交）
MES ──回执接口：OK / NG────────────▶ SN 系统   核对、存档，确认或记失败
MES ◀──200 + OK、batchResult──────── SN 系统   回执已收到
MES      记为「已送达」
                                    SN 系统   OK：推下一批；NG：推送任务停止
```

### 3.3 回执：同一批次再次回执

回执接口按批次号幂等，同一批次可以多次回执：

| 情形 | SN 的处理 | 返回 |
| --- | --- | --- |
| 第一次报 `OK` | 整批成功；唤醒推送任务推下一批 | 200，`code = OK`，`batchResult = SUCCESS`，`firstConfirmation = true` |
| 第一次报 `NG` | 整批失败（`REJECTED`，可作废）；推送任务停止并显示原因 | 200，`code = OK`，`batchResult = FAILED`，`firstConfirmation = true` |
| 已成功的批次再报（`OK` 或 `NG`） | 只存档，不改变批次 | 200，`code = OK`，`batchResult = SUCCESS`，`firstConfirmation = false` |
| 失败的批次修正后报 `OK`（如整批退回后经拉取接口带 `batchNo` 取回重处理） | 改为成功 | 200，`code = OK`，`batchResult = SUCCESS`，`firstConfirmation = true` |
| 失败的批次再报 `NG` | 仍为失败，失败码改为 `REJECTED`（可作废），原因更新为本次 `message` | 200，`code = OK`，`batchResult = FAILED`，`firstConfirmation = true` |

回执比推送应答先到时按回执处理，见 2.7。

### 3.4 回执：没送达，重交

| 项目 | 说明 |
| --- | --- |
| 哪些情况 | 超时、断连、5xx（SN 可能收到也可能没收到）；429 `RATE_LIMITED` |
| 怎么重交 | 用**同一份回执**重交：立即 1 次，之后 10 秒、1 分钟、5 分钟，再每 5 分钟 1 次，直到送达；429 按 `Retry-After`（秒）等待后重交 |
| 拿不准就重交 | 回执接口按批次号幂等，重交不会被重复处理；已确认的批次返回 `firstConfirmation = false`，同样表示已送达 |
| MES 重启 | 继续提交本地没送达的回执（先存后交） |
| SN 还没收到回执的信号 | 同一批又经推送接口送来，或拉取接口仍返回这一批：照常应答已收到 / 照常处理，并**立即重交第一次的回执** |
| 一直送达不了 | SN 等回执超时、重推 3 次后停止推送（2.4）；MES 补交成功后这一批即确认，停止的推送任务自动接着推后面的号（MES 也可用拉取接口去取） |
| 自测 | 契约测试 `devtools/mes_conformance.py` 的 C25 会让回执接收地址先返回 503，检查 MES 是否用同一份回执重交（见 [MES 联调指南](<MES 联调指南.md>) 第 3 节） |

### 3.5 回执：直接失败，不原样重交

| SN 的应答 | 场景 | MES 怎么做 | 批次 |
| --- | --- | --- | --- |
| 400 `INVALID_REQUEST` | `code` 不是 `OK` / `NG`，缺 `batchNo` 或不是字符串，请求体为 gzip 或无法解析 | 记「送达失败」，按 `details` 改正后重交 | 不变 |
| 401 `INVALID_CREDENTIALS`、403 `IP_NOT_ALLOWED` / `ACCOUNT_DISABLED` / `FORBIDDEN`、423 `ACCOUNT_LOCKED` | 认证失败、来源 IP 不允许、账户停用、不是 MES 接口账户、连续认证失败已锁定 | 记「送达失败」并告警，核对 MES 接口账户后重交（423 等 15 分钟） | 不变 |
| 404 `BATCH_NOT_FOUND` | 批次不存在、不属于本组织，或批次号大小写、空格不一致 | 记「送达失败」并告警，人工核对 `batchNo`，不自动重交 | — |
| 409 `BATCH_VOIDED` | 批次已作废（第 6 节） | 记「已作废」，丢弃这批，不再重交，不得用本地缓存处理 | 不变 |

## 4. 拉取接口（MES → SN 系统）

### 4.1 调用说明

| 步骤 | 说明 |
| --- | --- |
| 触发 | 推送失败后、本地 SN 不够用时，以及每 5 分钟兜底拉一次 |
| MES 发什么 | 选填 `pi`、`billNo` 限定范围，都不填表示不限（可发 `{}` 或空请求体）；选填 `batchNo` 取回指定批次，填了 `pi`、`billNo` 不生效。三者须为字符串。请求头带 MES 接口账户 `Authorization: Bearer <工号>:<密钥>`；请求体可为 gzip |
| SN 回什么 | HTTP 200 + `code = OK`：`batch` 为一个批次（结构与推送接口请求体相同）；没有可拉的回 HTTP 200 + `code = NO_BATCH`，`batch`、`batchNo` 为 `null`；`batchNo` 为返回的批次号；`remaining` 为范围内剩余可拉枚数，`paused` 为暂停下发的枚数。出错不返回 200（4.8） |
| MES 怎么判断 | HTTP 200 + `code = OK` 算拉取到一批，处理 `batch`；HTTP 200 + `code = NO_BATCH` 表示暂时没有可拉的（不是错误），停止拉取；超时、断连、5xx、429 算没拉到（4.7）；其他 4xx 按 4.8 处理 |
| 结果的作用 | 拉取到的批次与推送的批次结构相同、处理相同，按 `batchNo` 去重，处理完同样调回执接口；`remaining > 0` 时交完回执接着拉 |

### 4.2 拉取：正常流程

1. MES 调拉取接口，可按 `pi`、`billNo` 限定范围。
2. SN 返回范围内最早一批未确认的批次，没有才从号池认领新号建一批（4.3）。
3. MES 按 `batchNo` 去重：没处理过的校验、落库；处理过的不再处理，直接重交第一次的回执。
4. MES 调回执接口报告处理结果（第 3 节）；交了回执，SN 才把这一批从「未确认」中移出。
5. `remaining > 0` 时接着拉下一批；`code = NO_BATCH` 时停止，等下次触发。

```
MES ──拉取接口：pi / billNo──────────▶ SN 系统   取最早一批未确认的，没有才建批
MES ◀──200 + OK、batch、remaining───── SN 系统
MES      按 batchNo 去重、校验、落库
MES ──回执接口：OK / NG──────────────▶ SN 系统   确认或记失败
MES ◀──200 + OK（回执已收到）────────── SN 系统
MES ──拉取接口：下一批───────────────▶ SN 系统   remaining > 0 时
```

### 4.3 拉取：返回哪一批

| 项目 | 说明 |
| --- | --- |
| 返回哪一批 | **从失败处开始**，范围内依次：① **最早一批未确认或推送失败的批次**，按建立先后（未确认：推送中正在等回执或等重试的、拉取后还没回执的、转出批次；推送失败：没送到或被拒，MES 没有登记批次号，如跨 PI 转移后首次推送就失败。不限范围时只含 MES 还没拉取过的失败批次）；② 从号池认领新号建一批，**有失败批次的 PI 不建**（限定的 PI 有失败批次时返回它最早的失败批次）；③ 不限范围时，最后给 MES 拉取过后仍失败的批次（如 MES 又整批退回），按上次拉取时间轮流。失败批次只挡它所在的 PI，别的 PI 照常拉取 |
| 怎么拿下一批 | 交回执之前，每次拉都返回同一批；交了回执才轮到下一批 |
| 剩余数量 | `remaining` 为范围内剩余可拉枚数（未入批的号 + 其他未确认批次、推送失败还没拉取过的批次的枚数；MES 拉取过后仍失败的批次及其所在 PI 的号不计，避免退回后被引着反复拉），`> 0` 时继续拉；`paused` 为暂停下发的枚数 |
| 没有可拉的 | HTTP 200 + `code = NO_BATCH`，`batch = null`，`message` 为「暂无可拉取批次」（有暂停时注明枚数）；MES 停止拉取，`remaining` 不为 0 也不再接着拉 |
| 未开启「对接 MES」的组织 | 只返回转出批次，不建新批 |

### 4.4 拉取：取回指定批次（带 batchNo）

| 批次状态 | 返回 |
| --- | --- |
| 未确认、已失败（如整批退回后修正重处理） | 返回该批次（只读取回，不新建批次；`pi`、`billNo` 不生效） |
| 已确认 | 409 `BATCH_CONFIRMED`，无需再处理 |
| 已作废 | 409 `BATCH_VOIDED`，丢弃这批内容 |
| 不存在或不属于本组织 | 404 `BATCH_NOT_FOUND` |

### 4.5 拉取：MES 整批退回

| 一方 | 做什么 |
| --- | --- |
| MES | 调回执接口报 `NG`，`message` 写原因，不写入任何数据，也不登记批次号 |
| SN 系统 | 这一批记失败（`REJECTED`，可作废）；之后该 PI 的拉取一直先返回它、不再建新批，它和该 PI 的号不计入 `remaining`（4.3）；别的 PI 照常拉取；同一 PI 的推送任务遇到这个失败批次也会停止 |
| 总部 / MES | 问题修好后，MES 带 `batchNo` 取回，或照常拉取（不需要批次号）重处理并交回执 `OK`（3.3），该 PI 接着拉，停止的推送任务也自动接着推；或总部「继续推送」、作废这一批（第 6 节） |

### 4.6 拉取：推送与拉取同时进行

- 同一批可能经推送接口、拉取接口都到达 MES，MES 按 `batchNo` 只处理一次，回执按首次结果提交。
- MES 拉走、还没回执的批次，推送任务自动运行时不会抢着发，只有「继续推送」时才重推。
- 推送任务正在等回执的批次被 MES 拉走并交了回执：同样唤醒推送任务（`OK` 推下一批，`NG` 停止）。

### 4.7 拉取：没拉到，重试

| 项目 | 说明 |
| --- | --- |
| 哪些情况 | 超时、断连、5xx（SN 可能已建批）；429 `RATE_LIMITED` |
| 怎么重试 | 超时、断连、5xx 直接重拉，参数不变；429 按 `Retry-After`（秒）等待后重拉 |
| 不会多建批 | SN 已建的批次在交回执前一直是「最早一批未确认」，重拉返回同一批 |
| 限流 | 拉取接口、回执接口、查询接口合计，每个生产组织每分钟 60 次 |

### 4.8 拉取：直接失败，不原样重试

| SN 的应答 | 场景 | MES 怎么做 |
| --- | --- | --- |
| 400 `INVALID_REQUEST` | 请求体不是合法 JSON / gzip，或 `pi`、`billNo`、`batchNo` 不是字符串 | 按 `details` 修正请求 |
| 401 `INVALID_CREDENTIALS`、403 `IP_NOT_ALLOWED` / `ACCOUNT_DISABLED` / `FORBIDDEN`、423 `ACCOUNT_LOCKED` | 认证失败、来源 IP 不允许、账户停用、不是 MES 接口账户、连续认证失败已锁定 | 告警，核对 MES 接口账户后再拉（423 等 15 分钟） |
| 403 `ORG_NOT_ALLOWED` | 指定的 PI 下没有本组织的号，也没有本组织的转出批次 | 检查 `pi` |
| 404 `BATCH_NOT_FOUND` | 带 `batchNo`：批次不存在，或不属于本组织 | 人工核对 `batchNo` |
| 409 `BATCH_CONFIRMED` | 带 `batchNo`：批次已确认 | 无需再处理 |
| 409 `BATCH_VOIDED` | 带 `batchNo`：批次已作废 | 丢弃这批内容，不得用本地缓存处理，不再交回执 |

## 5. 查询接口（MES → SN 系统，只读）

### 5.1 调用说明

| 步骤 | 说明 |
| --- | --- |
| 触发 | 可选，对账时调 |
| MES 发什么 | 查询已下发 SN（`/api/mes/v1/sn/delivered`）：选填 `pi`；查询批次明细（`/api/mes/v1/batches/items`）：必填 `batchNo`。都可带 `cursor`（首页不带）、`pageSize`（默认 1000，最大 5000）。请求头带 MES 接口账户 `Authorization: Bearer <工号>:<密钥>`；请求体可为 gzip |
| SN 回什么 | HTTP 200 + `code = OK`：`items` 为本页的号，没有数据为 `[]`；`nextCursor` 为下一页游标，`null` 表示最后一页。出错不返回 200（5.5） |
| MES 怎么判断 | 只有 HTTP 200 + `code = OK` 算本页查询成功；`nextCursor = null` 才算查完；超时、断连、5xx、429 算没查到（5.4）；其他 4xx 按 5.5 处理 |
| 结果的作用 | 只用于对账，**不得据此入库、打标或删除**；发现差异人工核对 |

### 5.2 查询：正常流程

1. MES 不带 `cursor` 查首页。
2. SN 返回一页，`nextCursor` 不为 `null` 表示还有下一页。
3. MES 把 `nextCursor` 原样填入 `cursor` 查下一页，直到 `nextCursor = null`。
4. MES 用查到的号与本地核对，只记录差异，不改本地数据。

```
MES ──查询接口：首页（不带 cursor）──────▶ SN 系统
MES ◀──200 + OK、items、nextCursor────── SN 系统
MES ──查询接口：cursor = nextCursor─────▶ SN 系统   直到 nextCursor = null
MES      与本地核对，只记录差异
```

### 5.3 查询：返回哪些号

| 接口 | 返回 |
| --- | --- |
| 查询已下发 SN | 已交付给本组织 MES 的号（已推送，含拉取），可按 `pi` 限定；已转到别的组织的不返回 |
| 查询批次明细 | 某个批次里仍在该批次中的号；已转到别的组织的不返回 |

### 5.4 查询：没查到，重试

| 项目 | 说明 |
| --- | --- |
| 哪些情况 | 超时、断连、5xx；429 `RATE_LIMITED` |
| 怎么重试 | 超时、断连、5xx 用**同一 `cursor`** 重查；429 按 `Retry-After`（秒）等待后重查 |
| 限流 | 与拉取接口、回执接口合计，每个生产组织每分钟 60 次，每页算一次 |

### 5.5 查询：直接失败，不原样重试

| SN 的应答 | 场景 | MES 怎么做 |
| --- | --- | --- |
| 400 `INVALID_REQUEST` | `cursor` 不是上一页返回的 `nextCursor`（不会当作首页）、`pageSize` 不是整数、查询批次明细缺 `batchNo`，或请求体无法解析 | 修正请求；`cursor` 错误时从首页重新查 |
| 401 `INVALID_CREDENTIALS`、403 `IP_NOT_ALLOWED` / `ACCOUNT_DISABLED`、423 `ACCOUNT_LOCKED` | 认证失败、来源 IP 不允许、账户停用、连续认证失败已锁定 | 告警，核对 MES 接口账户后再查（423 等 15 分钟） |
| 404 `BATCH_NOT_FOUND` | 查询批次明细：批次不存在，或不属于本组织 | 人工核对 `batchNo` |

## 6. 总部人工操作

| 操作 | 什么时候用 | 结果 |
| --- | --- | --- |
| 继续推送 | 推送任务停止后（整批退回已修正、重试用尽、回执晚到等） | 清零重试与等回执次数，先用原批次号、原内容重推未确认或失败的批次（含 MES 拉取建立的），再认领新号建批 |
| 人工确认 | MES 方确认这一批已全部入库，但回执交不上来（未确认或失败的批次） | 批次成功，号改为「已推送」；推送任务正在等这一批的、因失败或重试用尽已停止的，都自动接着推下一批；原因、依据必填 |
| 作废 | MES 确实没有处理的批次：失败中可作废的（整批退回、认证 / 地址错误、报文过大、无法解析），或 MES 书面确认未处理的未确认批次 | 首次下发（`NEW`）的号回到号池重新建批；转移、改挂类的号按原号当场重建同类型新批次，转出批次按原明细重建，都自动推送；作废后 MES 再交回执或带 `batchNo` 拉取，返回 409 `BATCH_VOIDED`；原因、依据必填 |
| 转出批次 | 跨组织转移时自动建立，发给原组织 MES | 由单独的推送任务发送；回执 `OK` 后清除这些号在原组织 MES 的持有记录 |

## 7. SN 系统侧的状态

**批次结果**（`sn_delivery_batch.result`）

| 取值 | 含义 |
| --- | --- |
| `UNCONFIRMED` | 未确认：已建批，还没有回执 |
| `SUCCESS` | 成功：回执 `OK` 或人工确认 |
| `FAILED` | 失败：回执 `NG`、应答无效或不符、不重试的错误 |
| `VOIDED` | 已作废 |

**批次推送状态**（`sn_delivery_batch.push_state`）

| 取值 | 含义 |
| --- | --- |
| `IDLE` | 空闲：待发送，或已确认 / 已失败 |
| `WAIT_RECEIPT` | 等回执：MES 已应答收到，等回执接口 |
| `WAIT_RETRY` | 等重试：没送达，等下次自动重试 |
| `EXHAUSTED` | 重试用尽：自动重试或等回执重推已用完 |

**推送任务**（`sn_push_task.state`，每个「生产组织 + PI」一个，转出批次为 `#XO`）

| 取值 | 含义 |
| --- | --- |
| `QUEUED` | 排队，等调度器执行 |
| `RUNNING` | 运行中（带租约，实例宕机后由其他实例接手） |
| `WAITING` | 等待：等回执或等重试到期；回执到了立即转为排队 |
| `DONE` | 已完成：没有可推的号 |
| `STOPPED` | 已停止：失败或用尽，原因显示在页面；挡住的批次经 MES 回执 `OK` 或人工确认成功后自动转为排队，也可点「继续推送」 |

## 8. 默认参数

| 参数 | 默认值 | 配置 |
| --- | --- | --- |
| 单批枚数 | 5000 | 「生产组织」页，1–50000 |
| 推送超时 | 60 秒 | 「生产组织」页，5–600 秒 |
| 同组织同时运行的推送任务数 | 2 | 「生产组织」页，1–20 |
| 没送达的重试间隔 | 1、5、15 分钟 | `SN_PUSH_RETRY_INTERVALS_MINUTES` |
| 等回执时长（个数即重推次数） | 1、5、10 分钟 | `SN_PUSH_RECEIPT_WAIT_MINUTES` |
| MES 调用限流 | 每组织每分钟 60 次 | `SN_MES_PULL_RATE_PER_MINUTE` |
| 回执重交（MES 侧） | 立即、10 秒、1 分钟、5 分钟，之后每 5 分钟 | MES 实现 |

## 9. 已知待改进

| 问题 | 现状 | 影响 |
| --- | --- | --- |
| 回执晚到后不自动续推 | 等回执重推用尽、推送任务已停止后，MES 补交 `OK` 只确认这一批 | 后面的号要总部点「继续推送」，或 MES 用拉取接口去取 |
| 拉取批次没有超时 | MES 拉走后一直不交回执，拉取接口会一直先返回这一批 | 需人工确认、作废或继续推送 |

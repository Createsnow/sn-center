本文安排三项工作的落地顺序：将 Python 原型的新增能力同步到 SN 新工程，形成 Adtek 后续项目使用的开发框架与学习资料，以及在迁移完成后归档历史资料、规范 SN 日常开发工程。

## 一 工作目标与适用范围

### 1.1 最终目标

1. `adtek-platform-sn` 覆盖确认纳入范围的 Python 原型功能，保留原有页面操作和业务逻辑，并具备相应测试。
2. 后续 Adtek 新项目使用统一的 React、Spring Boot、MySQL 技术栈及配套工程约定，能够从经过验证的模板开始开发。
3. 新开发人员可以依据规范、学习指引和样例，独立完成环境启动、功能开发、测试及代码交付。
4. SN 项目以当前产品和日常开发为主要入口，迁移历史集中保存且可追溯。
5. 完成迁移后，SN 新需求、缺陷修复和回归测试统一进入 `adtek-platform-sn`。

### 第一步 梳理原型更新差异

**目的。**先明确需要补什么，以及哪些已有实现已经满足要求，为补迁提供可以逐项关闭的清单。

**具体工作。**

1. 固定本次核对的两端提交、配置模板和测试范围。如果实施期间原型继续更新，登记新的增量，保持本轮受检范围可追溯。
2. 对照原型的路由、服务、数据库结构、Vue 页面、错误提示及新增测试，定位新工程对应实现。
3. 核对页面入口、输入校验、权限、返回数据、状态变化、事务、幂等、异常、三语及导出内容。
4. 将每项标记为“已等价覆盖”“需要补迁”“需要调整既有实现”“需要业务决定”或“经确认不适用”。
5. 识别新原型行为与既有 v1.1 约束之间的差异，记录最终采用的业务规则与理由。不能仅因原型代码更新就覆盖既有约束。
6. 明确旧数据处置范围：仅使用新测试数据、保留指定主数据，或者迁移库存与完整历史。范围未确认前，相关事项保持待定。

差异清单至少包含以下字段：

| 字段 | 填写要求 |
| --- | --- |
| 功能及来源 | 原型页面、接口、代码或测试的具体位置及来源提交 |
| 目标实现 | 对应 React 页面、Java 用例、表结构或接口契约 |
| 行为差异 | 正常、异常、权限、并发及页面操作的差别 |
| 处理结论 | 补迁、复用、调整、待决定或不适用及理由 |
| 验收场景 | 可实际执行的输入、操作、预期结果和数据状态 |
| 状态与证据 | 当前进度、受检提交、验证结果及未完成原因 |

**交付物。**《SN 原型更新差异清单》《SN 补迁范围与规则决定》《旧数据处置范围说明》。这些文件是后续交付要求，本文不将其列为已经完成。

**完成条件。**所有识别出的原型更新均有归属；可以区分实际缺口与已覆盖能力；影响功能实现的数据和规则问题已明确，或列出清晰的阻塞范围。

### 第二步 完成 SN 增量迁移

**目的。**依据差异清单补齐新工程，并保留原有页面操作和业务结果。

建议按以下业务顺序实施，每一组都同时处理后端、前端、权限、数据库、契约和必要测试。

| 顺序 | 功能组 | 重点核对与实现内容 |
| --- | --- | --- |
| 1 | 订单与同步 | 定时全量同步开关和间隔、下次执行和最近结果、执行资格、重复触发与失败记录；订单及客户筛选的数据范围 |
| 2 | 规则与生成 | 未绑定 PI 首次选择规则、规则沿用、预演失效、转入 SN 与后续起号关系、完整 SN 冲突及整批回滚 |
| 3 | 领取打印与转厂 | 整批操作、固定成员、打印重放、回调、转厂前后状态和目标提示、文件内容与导出安全 |
| 4 | 登录与作业恢复 | 登录失败锁定、成功后计数处理、失败审计、中断作业恢复、迟到执行者不能继续写入 |
| 5 | 页面与整体流程 | 菜单、筛选、主从表、按钮禁用、等待反馈、错误提示、三语及下载行为 |

表中列出的是核对重点，不代表每一项都已确认为缺失。第一步判定已经等价覆盖的能力，复用实现并补足必要证据。

实施时遵守以下要求：

- 使用既有模块和分层，保留 Controller、Service、Mapper、Entity、DTO、Query、VO 和 MapStruct 的职责边界。
- 保持页面流程、输入输出及业务规则；确有变化时同步记录原因和验收口径。
- MySQL 继续承担 SN 唯一性、额度和事务的最终约束；Redis 的使用不能替代业务提交与持久状态。
- 定时同步、任务恢复等能力需要验证执行权、重复触发、失败和当前权限，不能只验证正常执行一次。
- 检查原型新增表和字段是否改变旧库版本识别、快照字段及转换规则。既有“19 表来源版本”的工具不能默认兼容所有新原型结构。
- 当前已应用的 V1—V17 保持原样；后续变更从新的可用版本继续，实施前再次核对版本占用。
- 代码注释、格式、Mapper 行宽及生成契约继续执行现有检查。

**交付物。**各功能组的实现、增量数据库脚本、更新的接口和页面说明、对应测试及差异清单状态。

**完成条件。**确认纳入范围的功能差异均已落实，既有功能没有因补迁退化；待决定事项不能标为实现完成。

### 第三步 完成迁移验收

**目的。**以明确版本和实际场景证明补迁结果，并决定原型何时退出新功能开发流程。

**具体工作。**

1. 在隔离环境执行完整业务链路：订单同步、规则选择、预演、生成、分配、领取、打印、转厂、查询及审计。
2. 验证原型有效回归场景及本次差异场景，覆盖权限越界、重复提交、并发冲突、事务回滚、任务中断和恢复。
3. 检查 React 页面的实际操作、三语提示、下载文件和错误反馈，不能只以接口通过代替页面验收。
4. 对需要保留的旧数据进行迁移演练，核对身份、主数据、库存、来源额度、固定成员、历史记录及文件；不在范围的内容记录理由。
5. 分别记录编译、单元、真实 MySQL/Redis 集成、浏览器、外部联调、性能和业务验收结果。未执行、失败或阻塞项目单列。
6. 汇总剩余事项及其对功能交付、数据保留和生产切换的影响。阻塞已约定范围的事项关闭后，才能确认该范围验收完成。
7. 固定受检提交和本地验收标签，形成《SN 迁移总结与验收记录》。现有“第一个迁移版本”标签保留，不移动到新提交。

涉及真实 ERP、MES 或业务环境且当前不可连接的项目，保留未完成状态。是否将某项移出本轮范围，需要有明确的范围决定和后续安排。

**交付物。**功能对照结果、测试报告、数据处置或迁移核对结果、差异决定、未完成事项和准确的验收版本。

**完成条件。**已确认范围内的验收项全部关闭；历史数据有明确结论；生产切换就绪程度单独说明。不得把过去阶段的测试数量直接视为本次最终版本的验证结果。

### 第四步 整理 Adtek 通用开发框架

**目的。**从经过验证的工程中整理可复用能力，形成后续项目可以独立使用的模板。

建议在 `adtek-platform-sn` 之外创建独立的 `adtek-platform-template`。模板名称、模块命名和版本在实施时固定；SN 工程继续保留业务实现，不能通过整体移动现有代码使 SN 无法独立构建。

**技术栈范围。**沿用当前批准并落锁的 React、TypeScript strict、Spring Boot、Java 21、MySQL 8.4，以及现有 Redis、MyBatis、MapStruct、OpenAPI、构建和测试工具。具体版本以 POM、package.json、锁文件及镜像记录为准。框架整理不隐含一次依赖升级；升级需要单独验证。

| 能力类别 | 拟纳入模板的内容 | 需要明确的边界 |
| --- | --- | --- |
| 工程底座 | 模块结构、配置模板、统一结果、异常、日志、构建、格式与架构检查 | 通用模块不依赖 SN 业务实现 |
| 身份与权限 | 登录、会话、用户、角色、部门、菜单、按钮权限及数据范围 | 工厂资格等业务范围需经过拆分和扩展点核验 |
| 审计与公共功能 | 操作审计、字典、任务、文件、下载和错误处理 | 各业务仍负责自身权限、事务、固定成员及状态规则 |
| React 基础 | 布局、路由、菜单、请求封装、Query 状态、表单和三语 | 不携带 SN 菜单、状态机和业务接口作为必选项 |
| 开发与运维工具 | 启动、构建、测试、健康检查、容器模板及配置指引 | 不复制已有账号、密钥、业务数据或本机绝对路径 |
| 外部集成 | 通用端口与适配器组织方式 | K3、MES 等具体协议由需要它们的业务项目引入 |

**具体工作。**

1. 盘点 `common`、`framework`、`system`、前端基础组件及工具脚本，识别其中对 SN、工厂和旧迁移流程的依赖。
2. 确定通用能力和业务扩展边界，并通过编译、架构和行为测试验证拆分结果。
3. 建立独立配置和数据库初始化方式。模板使用自己的空库初始化历史，不能替换 SN 已应用的 Flyway 历史。
4. 提供一个非 SN 的完整业务样板，例如设备台账，覆盖列表、详情、增改、权限、审计及测试。
5. 提供工程复制、项目命名替换和配置检查步骤，采用既有技术与样板风格。
6. 为模板分配版本，记录后续项目采用的版本以及接收公共修复的方式。
7. 补齐面向 GitLab 的检查配置，覆盖后端、前端、格式、契约及测试；远程不可用时仅验证本地可验证部分，保留 CI 待执行状态。

**交付物。**独立模板、公共能力清单、业务扩展边界、可运行样板、配置和初始化脚本、版本说明及检查配置。

**完成条件。**从全新目录和独立空数据库可以完成初始化、启动、登录、样板操作及测试；模板不依赖相邻 Python 项目、SN 数据库或已有本机秘密。整理影响 SN 公共代码时，SN 对应回归同时通过。

| 3 完整功能开发 | 依据样板完成一个列表、详情及增改功能 | 前后端和数据库形成可用功能 |
| 4 关键约束 | 增加权限、数据范围、校验、事务、审计及异常测试 | 能解释业务正确性与访问边界 |
| 5 测试与交付 | 执行检查、整理变更说明、准备提交和评审材料 | 能交付可验证且符合规范的修改 |

**交付物。**上述规范和指南、对应样板位置、练习任务、检查清单及文档版本说明。通用规范以模板工程为统一来源，SN 文档引用所采用版本并补充业务差异，避免维护两份相互漂移的规范。

**完成条件。**未参与 SN 迁移的接手者能够按资料在新环境完成一次功能练习，并通过规定检查。文档命令需实际验证，文档存在不能单独代表新人上手验收通过。

### 第六步 归档迁移资料并精简 SN 项目

**目的。**在迁移结论明确、框架规范可引用后，让 SN 工程面向长期开发，同时保留历史追溯能力。

**具体工作。**

1. 汇总迁移资料，形成来源版本、目标版本、功能对应、数据处置、差异决定、验收结果和遗留事项的统一索引。
2. 重新编写 README、文档导航、AGENTS 和当前状态入口，突出项目用途、日常启动、开发测试、架构、业务和运维说明。
3. 将仍然有效的业务规则、接口、数据库说明、用户手册和运维步骤整理为日常文档。
4. 将迁移方案、旧来源快照、阶段工作包、历史报告和证据集中归档；保留原始内容，更新指向归档位置的引用。
5. 将未完成事项放入当前待办，保留验收条件及影响范围，不随历史报告一起隐藏。
6. 盘点迁移专用 CLI、脚本、兼容代码和依赖，结合数据迁移及恢复安排决定保留、隔离或移除。功能清理与文档移动分别记录和验证。
7. 检查文档链接、命令、配置加载、数据库校验、构建、启动及受影响业务回归，固定整理后的版本。

建议采用以下文档组织，实施时可根据现有文件映射调整：

```text
adtek-platform-sn/
├─ README.md
├─ AGENTS.md
├─ backend/
├─ frontend/
├─ deploy/
├─ tools/
├─ memory/                     当前工作状态和接续信息
└─ docs/
   ├─ architecture/            当前架构、数据与设计决定
   ├─ development/             框架版本引用和 SN 开发约定
   ├─ business/                SN 业务规则、接口与用户说明
   ├─ testing/                 测试策略、场景与执行方式
   ├─ operations/              部署、备份、恢复与排障
   ├─ releases/                版本变更和发布记录
   └─ archive/
      └─ python-migration/     迁移总结、基线、阶段报告及证据
```

归档和精简遵守以下边界：

| 对象 | 处理原则 |
| --- | --- |
| 已应用的 Flyway 脚本 | 保留内容及校验和，不因“迁移结束”删除或重排 |
| 历史报告和证据 | 原文保留；移动时核对文件清单和内容摘要，不改历史测试结论 |
| 业务兼容逻辑 | 按当前使用情况处理，不能仅凭 `legacy` 名称删除 |
| 迁移工具 | 数据迁移和恢复需求明确后决定去留，保留受检版本和使用说明 |
| 备份恢复与运行维护 | 作为长期运维能力维护，不按迁移临时文件清理 |
| 秘密、真实数据和备份文件 | 继续留在受保护位置，不复制进文档归档或模板 |
| Python 原型 | 保留用于追溯；迁移验收后新的 SN 开发统一进入新工程 |

**交付物。**迁移归档索引、文件位置映射、精简后的日常文档、工具处置清单、清理后的工程和回归记录。

**完成条件。**开发人员可以从 README 进入日常开发，不依赖迁移历史才能理解项目；历史资料可定位、引用可用；有效规则和未完成事项没有丢失；工程在整理后仍可构建、启动、升级和测试。

## 四 实施前需要明确的范围事项

以下事项在对应步骤中落实即可，不要求现在同时给出全部答案。本文不代替业务决定，也不预先指定具体负责人或承诺工期。

| 原型数据是否保留，保留哪些数据和文件 | 第一步 | 决定历史数据工作量及第三步验收范围 |

| 模板名称、维护方式和通用能力边界 | 第四步 | 决定新项目创建方式及公共修复的接收方式 |
| 迁移工具与兼容代码是否仍用于数据恢复或外部调用 | 第六步清理前 | 决定保留、隔离还是移除 |

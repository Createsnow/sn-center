## 1. 概述

总部按金蝶生产订单的**物料行**（单据编号 + 序号）统一生成 SN，分配到订单上的生产组织：对接 MES 的生产组织由本系统分批推送（MES 也可主动取批），未对接的在页面领取；订单变更、转单、转组织都只在本系统改挂，号本身（完整 SN）写出后不再改变。**完整 SN 全局唯一**，同一张 PI 的流水不重复。

业务规则以 [需求文档（PRD）](需求文档（PRD）.md)（V30）为准，业务视角的流程见 [业务流程说明](业务流程说明.md)，与 MES 的接口契约见 [MES 对接说明](MES对接说明.md)。本文从开发角度说明代码结构、权限、状态机、关键时序、接口清单和需求落地方式。

后台任务都在应用进程内（`app/main.py` 的 lifespan 启动）：

| 任务 | 入口 | 周期 | 多实例 |
| --- | --- | --- | --- |
| 每日维护 | `partitions.maintain`（`scheduler.start_daily`） | `SN_PARTITION_CRON`（默认每天 02:10） | 命名锁 `sn_partition`，只有一个实例做 |
| 比对同步 | `orders.run_scheduled`（`scheduler.start_every`） | `SN_SYNC_INTERVAL_MINUTES`（默认 10 分钟）；`SN_SYNC_ENABLED=false` 关闭 | 订单同步锁，只跑一份 |
| 推送调度 | `delivery.start_scheduler` → `run_pending` | `SN_PUSH_POLL_SECONDS`（默认 5 秒）；`SN_PUSH_ENABLED=false` 关闭 | 任务租约（300 秒），宕机后由别的实例接手 |
| 生成后台任务 | `generate._run` 线程 | 一次生成超过 `SN_GEN_SYNC_THRESHOLD` 时 | PI 操作锁交给后台线程，结束时释放 |

每日维护依次：建未来月分区 → 归档过期分区 → 清理过期归档 → 清理限流计数 → 从金蝶同步生产组织（失败只记日志）→ 每日交付自检（`dashboard.self_check`）。启动时另回收中断的生成任务（`generate.recover_interrupted`）。

部署形态（单端口 / Docker Compose / 前后端分离开发）见 [运维手册](运维手册.md)。

## 5. SN 组成与状态机

### 5.1 SN 组成（`app/core/encoding.py`）

完整 SN = **前缀 + 长度 + 定长进制流水 + 后缀**（5.2.2）：

- 前缀必填（字母、数字），后缀选填（字母、数字、`_`）；任何两条规则（含各版本）的前缀不能相同或互为开头，区分大小写。
- 长度取所属物料行的长度，按「长度写法」规范化（`normalize_length`：去首尾空格；整数部分去前导零，小数去末尾 0，全为 0 时连小数点去掉）后写入；规则 `with_length = false` 时不写。不是数字时该行不能生成（`LENGTH_INVALID`），为空时 `LENGTH_EMPTY`。
- 进制 10 / 16 / 32 / 36，流水位数 1–12，左侧用字符表首字符补齐；32 进制默认字符表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（去掉易混的 I L O U）；超出位数拒绝（`GEN_RULE_EXHAUSTED`），不自动加宽。总长不超过 64。
- 同一版本的前缀、位数、后缀固定，`parse` 可把 SN 反解为（长度，流水），用于按完整 SN 查流水范围。

### 5.2 号的状态（`sn_item.status`）

```mermaid
stateDiagram-v2
    [*] --> 待分配: 生成（总部）
    待分配 --> [*]: 撤销 / 取消生成（号删除）
    待分配 --> 待推送: 分配到对接 MES 的组织（未入批）
    待分配 --> 待领取: 分配到未对接的组织
    待推送 --> 待推送: 推送 / 拉取建批（入批，批次未确认）
    待推送 --> 已推送: 批次回执确认 / 人工确认
    待推送 --> 已领取: 对接 MES 组织页面领取（只取未入批）
    待领取 --> 已领取: 页面领取
    待推送 --> 申请中: 操作员提交转组织申请
    待领取 --> 申请中
    已推送 --> 申请中
    已领取 --> 申请中
    申请中 --> 原状态: 驳回 / 撤回
    申请中 --> 待推送: 确认（转入组织对接 MES）
    申请中 --> 待领取: 确认（转入组织未对接）
    待领取 --> 待推送: 开启「对接 MES」
    待推送 --> 待领取: 关闭「对接 MES」（未入批的）
```

号上另有几项与交付相关的属性：

| 字段 | 含义 |
| --- | --- |
| `rev` | 挂靠版本号：每次转单、转组织、确认对应改挂时 + 1；推送报文和回执逐枚带 `rev`，MES 据此判断新增、改挂或过期 |
| `mes_holder` | MES 持有组织：批次确认后记为该批次的组织；转出批次确认后清除。决定转移后是推「改挂」还是「新增」、要不要向来源 MES 推「转出」 |
| `push_type` | 下次推送类型 `NEW` / `REASSIGN`（转出批次的明细类型为 `TRANSFER_OUT`） |
| `delivery_batch_no` / `acquire_batch_no` | 所在交付批次 / 领取批次；入批后号不再被别的通道认领 |
| `delivery_mode` | `PUSH` 推送 / `PULL` 拉取 / `PAGE` 页面领取 |
| `suspend` | 暂停交付：`REVERSAL`（单据反审核中）/ `CHANGE`（订单变更待确认）；只作用于未交付的号（待分配、待推送未入批、待领取） |
| `transfer_id` / `applying_from` | 未完成的转组织申请与申请前状态 |
| `seq_pi_no` / `seq_dec` | 流水归属 PI 与十进制流水（转组织改 PI 不改流水归属） |

- 撤销生成只删除仍待分配、没转过单的号，且只能撤这张 PI 流水排在最后的一次生成。
- 申请中、所在批次未确认或失败、所在转出批次未确认或失败、领取未完成的号不能转移；转组织另不能转待分配的号。
- 同一枚号同时只能有一张未完成的转组织申请。

### 5.3 计数口径（5.2.7，`sn_line_count`）

按物料行（单据编号 + 序号）记三项：

| 列 | 含义 | 变化 |
| --- | --- | --- |
| `own_generated` | 本单生成数：在该物料行上生成的号数 | 生成 + / 撤销、取消 −；转单不动（额度不变） |
| `gen_count` | 已生成数：当前挂在该物料行上的号数 | 生成 + / 撤销 −；转单从来源行移到目标行；确认对应并入新行 |
| `alloc_count` | 已分配数 | 分配 +；转单随号移动 |

- **可生成额度 = 物料行数量（整数部分）− 本单生成数**，转单、转组织都不改额度；
- 转组织不改来源单据和序号，三项计数都不变；
- 生成起点 = 本 PI 自己生成的最大流水 + 1（`sn_pi_counter.last_seq_dec`），转入的号不抬高起点。

## 7. 关键时序

### 7.1 登录、改密与 MES 换令牌

```mermaid
sequenceDiagram
    participant U as 浏览器
    participant API as /api/auth
    participant MES as MES
    participant M as /api/mes/v1/auth/token
    participant DB as MySQL
    U->>API: POST /login（X-SN-Client: web）
    API->>DB: 查账户、校验口令（工号不存在也做一次校验）
    alt MES 接口账户
        API-->>U: 403 MES_NO_PAGE_LOGIN
    else 页面账户
        API->>DB: 记页面登录版本、LOGIN 痕迹
        API-->>U: token（含 must_change_pwd）
    end
    MES->>M: {empNo, secret}
    M->>DB: 锁定中？来源地址在白名单？
    alt 连续失败 ≥ SN_MES_AUTH_MAX_FAILURES
        M->>DB: 锁定 SN_MES_AUTH_LOCK_MINUTES、MES_AUTH_LOCK 痕迹
        M-->>MES: 423 ACCOUNT_LOCKED
    else 校验通过
        M-->>MES: accessToken、expiresIn 43200、expiresAt
    end
```

令牌为 HMAC 签名的无状态令牌，载荷含口令版本：改密、重置密码、重置密钥都会让旧令牌失效；MES 换新令牌不使旧令牌失效（多台服务器可各持一个）。

### 7.2 订单同步（F-05）与订单变更（F-06、5.2.10）

四种同步共用订单同步锁（`locks.sync_lock`）：按单据同步排队等待，比对同步和进页同步拿不到锁直接跳过（`skipped`）。

| 方式 | 入口 | 做法 |
| --- | --- | --- |
| 比对同步 | 定时 / `POST /api/orders/compare` | 只拉已审核单据的编号与修改时间（`k3.fetch_approved_heads`），与快照比对：新出现、修改时间不同的整单替换，快照有、金蝶没有的移出；同周期对反审核中的已出号单据按单号复查。任一页拉取失败（重试 `K3_PAGE_RETRIES` 次后）本周期不改快照 |
| 进页同步 | `POST /api/orders/page-sync` | 进入订单页时后台触发一次比对同步，立即返回 |
| 按单据同步 | `POST /api/orders/sync` | 不带单据状态条件按单号查：已审核 → 替换（`REPLACED`）；不是已审核 → 移出（`NOT_APPROVED`，快照里原本没有时 `NOT_APPROVED_NEW`）；查无此单 → 移出（`NOT_FOUND`） |
| 全量重建 | `POST /api/orders/rebuild` | 完整拉取写入新表，`RENAME` 原子换表；失败旧快照完整保留；完成后对全部已出号单据比对 |

```mermaid
sequenceDiagram
    participant S as 比对同步
    participant K as 金蝶
    participant O as orders
    participant C as changes
    participant DB as MySQL
    S->>O: compare_sync（拿同步锁）
    O->>K: 已审核单据编号 + 修改时间（分页）
    O->>K: 变动单据明细（FBillNo IN …）
    O->>DB: 整单替换 / 移出快照
    O->>C: after_sync（变动单据）
    C->>DB: 与单据台账比对（PI / 组织 / 客户 / 物料行 / 数量 / 附件项次）
    alt PI 变了
        C->>DB: 提醒 PI，冻结生成与分配，未交付的号 suspend = CHANGE
    else 组织 / 客户变了、物料行失去对应
        C->>DB: 提醒，未交付的号 suspend = CHANGE
    else 数量下调到本单生成数以下 / 附件项次金蝶后来有值
        C->>DB: 只提醒
    end
    O->>C: after_removed（离开快照的已出号单据）
    C->>K: 按单号查看（View）
    alt 单据仍在、不是已审核（含查询失败）
        C->>DB: 反审核中 suspend = REVERSAL，之后每周期复查
    else 查无此单（已删除）
        C->>DB: 不暂停，已暂停的解除
    end
```

- **单据台账**（`sn_bill_ledger` + `_line`）在单据第一次生成号时建立，表头只在总部「确认变更」时改为新值，所以反审核修改后再重新审核回来仍能发现其间的变化；重新审核回来没有变化或只有数量变化时自动解除暂停。
- **处理提醒**（`POST /api/orders/alerts/{id}/handle`）：`CONFIRM` 确认变更 / `MAP` 确认对应（`target_seq`，计数与号并入新行，已交付给 MES 的号 rev + 1 改挂重推，`transfers.map_material`）/ `UNRELATED` 确认无关 / `VOID` 确认已作废（须填原因）/ `ACK` 知道了。解除暂停后 `delivery.kick_bill` 启动可推送的号。
- **附件项次**：金蝶为空时总部可补填（`sn_line_attach`，只用于本系统生成前的校验，不写回金蝶、不进推送报文和领取文件）；金蝶后来有值时以金蝶为准并提醒。

### 7.3 规则选取（F-08）

```mermaid
sequenceDiagram
    participant U as 总部（生成页）
    participant R as rules
    participant DB as MySQL
    U->>R: GET /rules/options?pi=…（推荐的排前面）
    R->>R: resolve(规则, PI)：当前版本尚无 PI 或已归属本 PI → USE / CLAIM<br/>已归属别的 PI → 已为本 PI 另出过 → USE，否则 PREFIX（须填新前缀）

    alt plan = PREFIX 且没填 new_prefix
        R-->>U: 409 RULE_PREFIX_CHANGE_REQUIRED
    else
        R->>DB: check_prefix（不同、不互为开头）；另出属于本 PI 的版本（derived_from）
        R->>DB: sn_line_rule 记物料行选定（自定义规则只记 custom_json，plan = NEW）
```

- 物料行生效规则：**物料行已选 ＞ PI 绑定（`sn_pi_rule`）＞ 客户绑定（`sn_customer_rule`，作模板）**（`rules.effective`）；都没有时该行 `NO_RULE`，客户模板首次用于本 PI 须换前缀（`RULE_PREFIX`）。

- 按客户绑定只能经 `POST /api/rules/customer-binding` 设置（F-22），每个客户一条；生成页可解绑（规则转为通用模板）。

### 7.4 预演、生成、进度 / 取消、撤销（F-09）

```mermaid
sequenceDiagram
    participant U as 总部
    participant G as generate
    participant L as PI 操作锁
    participant DB as MySQL
    U->>G: POST /generate/preview {pi_no, scope BILLS|LINES, bills|lines, qty?}
    G->>DB: 逐行检查（客户、PI 冻结、物料、规则、前缀、长度、附件项次、额度）
    alt 有不能生成的行
        G-->>U: generatable = false，issues 逐行列出
    else
        G->>DB: 计划写入 sn_gen_preview（发起人、范围、基准最大号、规则版本、各行号段）
        G-->>U: token、各物料行起止号、整体起止号、expires_at
    end
    U->>G: POST /generate/run {token}
    G->>L: GET_LOCK(PI)；拿不到 → 409 PI_BUSY
    G->>DB: 核对令牌（发起人、未用过、未过期、范围与条件、PI 最大号、规则版本未被别的 PI 先用）
    alt qty ≤ SN_GEN_SYNC_THRESHOLD
        G->>DB: 一个事务：realize 规则版本 → 批量写号（待分配）→ 计数 → 台账 → 痕迹
        G-->>U: SUCCESS
    else
        G-->>U: RUNNING（锁交给后台线程）
        loop 每块
            G->>DB: 写号、更新 done_qty / current_sn；检查取消请求
        end
        U->>G: GET /generate/batches/{batch}（百分比、速度、预计剩余）
        U->>G: POST …/cancel → 整批回滚，任务 CANCELED
    end
    G->>L: RELEASE_LOCK
```

- 一次生成共用一个生成批次（`gen_batch`），所有物料行排在该 PI 的一套流水上，各行按自己的规则写出；BILLS 按勾选单据顺序、单据内按序号，LINES 按点选顺序。
- 预演只对发起人有效、默认 30 分钟（`SN_PREVIEW_TTL_MINUTES`）、只能生成一次（`GEN_PREVIEW_USED`）；PI 最大号变化 → `GEN_PREVIEW_STALE`，条件改变 → `GEN_PREVIEW_CHANGED`。
- 撞号（`ux_item_sn` / `ux_item_seq`）整次回滚报 `GEN_DUPLICATE_SN`，不跳号；单次上限 `SN_GEN_MAX_PER_RUN`，默认填入数量取额度与 `SN_GEN_DEFAULT_LIMIT` 的较小值。
- 服务重启时仍是 `RUNNING` 的任务（事务已随进程退出回滚）标为失败并释放 `running_pi`。
- 撤销（`POST /generate/batches/{batch}/revoke`，原因必填）：只能撤这张 PI 流水排在最后的一次（`GEN_REVOKE_NOT_LAST`），号全部仍待分配且都没转过单（`GEN_REVOKE_ALLOCATED`）；号删除，最大号与三项计数一并退回。

### 7.6 推送任务与重试（F-11 推送部分、接口 ①）

```mermaid
sequenceDiagram
    participant T as 推送调度
    participant D as delivery
    participant DB as MySQL
    participant MES as MES 接收推送 ①
    T->>D: run_pending：取可运行任务（QUEUED / 到点的 WAITING / 租约过期的 RUNNING）
    D->>DB: 组织并发 < push_concurrency 且同 PI 无运行中任务 → RUNNING + 租约
    loop 一批成功再发下一批
        alt 有未确认 / 失败的批次（含拉取建立的）
            D->>MES: 原批次号、原内容（body_gz 逐字节相同）
        else
            D->>DB: claim：待推送 · 未入批 · 未暂停，SKIP LOCKED，按流水顺序取 batch_size 枚
            D->>DB: 建批 PS-组织-日期-序号，写定 body_gz、items_digest
            D->>MES: POST（gzip，Bearer 或 HMAC，X-Sn-Batch-No / X-Sn-Attempt / X-Request-Id）
        end
        alt 200 + 回执
            D->>D: apply_receipt（见 7.7）
        else 超时、5xx、断连、409 BATCH_IN_PROGRESS、429、503
            D->>DB: push_state = WAIT_RETRY，next_retry_at = +1 / 5 / 15 分钟；任务 WAITING
        else 4xx 等不可重试 / 重试用尽
            D->>DB: 批次 FAILED（认证、地址、过大、请求错、整批拒收可作废）；任务 STOPPED「推送中断」
        end
    end
```

- 同组织 + 同一 PI 一个任务（`sn_push_task`，转出批次用键 `#XO`）；期间后续批次等待。
- 「继续推送」（`POST /api/delivery/resume`）：重置未确认、失败批次的自动重试，按原批次号、原内容先重推，再认领后续的号。`GET /api/delivery/remaining` 给出「剩余 N 次」（未入批未暂停的号按单批枚数折算 + 未确认或失败的批次数）。
- 连接测试（`POST /api/factories/{code}/mes-test`）发 `batchType = PING`、`items = []` 的批次，认证与压缩同正式推送；通过时记下配置摘要，开启「对接 MES」须配置与测试通过时的摘要一致（`MES_TEST_REQUIRED`）。
- HMAC 签名串 = `timestamp + "\n" + batchNo + "\n" + hex(SHA256(原始请求体))`，放 `X-Sn-Timestamp` / `X-Sn-Signature`；凭证用 `SN_SECRET` 派生的密钥 AES-GCM 加密保存，不回显。

### 7.7 MES 取批与回执（F-12、接口 ③④）

```mermaid
sequenceDiagram
    participant MES as MES
    participant API as /api/mes/v1
    participant D as delivery
    participant L as 组织建批锁
    participant DB as MySQL
    MES->>API: POST /batches/next {schemaVersion, pi?, billNo?, batchNo?}
    API->>DB: 限流（每组织每分钟 SN_MES_PULL_RATE_PER_MINUTE）→ 429 RATE_LIMITED
    alt 带 batchNo
        D-->>MES: 只读取回该批（已确认 409 BATCH_CONFIRMED / 已作废 409 BATCH_VOIDED）
    else
        D->>L: GET_LOCK(组织)
        D->>DB: 范围内最早的未确认批次（推送卡住的、取走没回执的、转出批次）
        opt 没有
            D->>DB: claim + 建批 PL-…（source = PULL）
        end
        D-->>MES: batch、batchSource、newlyCreated、batchResult、remaining、paused
    end
    MES->>API: POST /batches/{batchNo}/receipt
    API->>D: submit_receipt → apply_receipt（独立事务、锁批次）
    alt 已作废
        D-->>MES: 409 BATCH_VOIDED（回执存档）
    else 已确认
        D-->>MES: 200 firstConfirmation = false（只存档）
    else outcome = REJECTED
        D->>DB: 批次 FAILED（可作废），号冻结，首页告警
    else 核对不符（批次号、条数、每枚一次且属于本批、rev、summary）
        D->>DB: 批次 FAILED（RECEIPT_MISMATCH，不可作废）
        D-->>MES: 422 RECEIPT_MISMATCH + details
    else 核对通过
        D->>DB: 逐枚回执 ACCEPTED / DUPLICATE / CONFLICT / STALE；批次 SUCCESS（有冲突 SUCCESS_CONFLICT）
        D->>DB: 交付批次的号 → 已推送、mes_holder = 本组织、delivery_mode = PUSH / PULL
        D->>DB: CONFLICT / STALE 写交付告警
        D-->>MES: 200 firstConfirmation = true
    end
```

- 交付批次（含转出批次）只由本系统建立；批次号、所含 SN 及其挂靠和 rev 建立后不再改变，推送与拉取送达的内容相同。**先到的回执生效，后到的只存档**（`sn_delivery_receipt`，`verdict` = CONFIRMED / REJECTED / MISMATCH / ARCHIVED / VOIDED）。
- 只读接口 ⑤ `GET /sn/delivered`（MES 账户只得到已交付给本组织 MES 的号）、⑥ `GET /batches/{batchNo}/items`（仍在该批次中的号）用游标翻页，默认 1000 条、最多 5000 条。
- 请求体可 gzip（`Content-Encoding: gzip`）；`/api/mes` 上的所有错误（含业务错误、参数错误）都用 MES 错误体（§10）。

- 转出号清单（`GET /transfers/org/{id}/out-list`）：完整 SN、流水、原批次，来源现场据此作废旧标签。

### 7.11 每日交付自检（5.2.5 第 5 条）

`dashboard.self_check`（每日维护调用）核对近 2 天：成功批次的回执枚数是否等于批次枚数（人工确认的单列）；未经转移，同一 SN 是否在两个成功交付批次、或交付批次与页面领取中；当天的冲突、过期回执；未确认超过 `SN_BATCH_UNCONFIRMED_ALERT_MINUTES` 的批次。问题写入 `CHECK` 交付告警并留痕 `SELF_CHECK`。

### 7.12 分区维护与痕迹归档

```mermaid
sequenceDiagram
    participant S as 每日维护
    participant P as partitions
    participant DB as MySQL
    S->>P: maintain()
    P->>DB: GET_LOCK('sn_partition')
    P->>DB: REORGANIZE pmax：补足未来 SN_PARTITION_AHEAD_MONTHS 个月分区
    P->>DB: 超过 SN_AUDIT_RETENTION_DAYS 的整月分区：拷入 sn_audit_archive 后 DROP PARTITION
    P->>DB: 删除超过 SN_AUDIT_ARCHIVE_RETENTION_DAYS 的归档痕迹（AUDIT_ARCHIVE_PURGE）
    P->>DB: 清理一天前的限流计数
    P->>P: 金蝶同步生产组织；每日交付自检
    P->>DB: RELEASE_LOCK
```

痕迹查询的时间范围覆盖到已归档的痕迹时同时查归档表，结果标 `archived`。

## 10. 错误码与多语言

- 页面接口的业务拒绝都抛 `biz(ErrorCode.X, **params)`（`BizError`），响应体 `{code, message, params}`；`ErrorCode`（`app/core/errors.py`）集中定义 HTTP 状态与中文模板，`message` 为中文渲染结果，前端按 `code` + `params` 渲染当前语言。
- MES 接口（`/api/mes/v1`）的错误用 `MesError`，响应体 `{schemaVersion, code, message, batchNo?, details?}`，出错不返回 200；限流时带 `Retry-After`。`/api/mes` 上抛出的 `BizError` 与参数错误也转成该格式。错误码有 `INVALID_REQUEST`、`INVALID_CREDENTIALS`、`ACCOUNT_LOCKED`、`TOKEN_EXPIRED`、`TOKEN_INVALID`、`ACCOUNT_DISABLED`、`IP_NOT_ALLOWED`、`FORBIDDEN`、`ORG_NOT_ALLOWED`、`BATCH_NOT_FOUND`、`BATCH_CONFIRMED`、`BATCH_VOIDED`、`RECEIPT_MISMATCH`、`RATE_LIMITED`；含义见 [MES 对接说明](MES对接说明.md)。被拒绝的 MES 请求留失败痕迹（回执不符在处理时已留痕）。
- 前端 `locales/errors.{zh-CN,en,vi}.json` 按错误码渲染；UI 词条来自 `frontend/scripts/ui_messages.py`（公共）与 `frontend/scripts/ui/*.py`（各页面，键不能重复），错误码英 / 越译文来自 `error_messages.py`，由 `python3 frontend/scripts/gen_locales.py` 生成（缺译、占位符不一致或键重复会直接报错）。
- 契约测试：`tests/test_unit.py::test_every_error_code_translated`（每个错误码三语齐全、占位符一致、没有多余的码）、`frontend/src/locales.test.js`（三语键一致，源码里的静态 `t('…')` 键都存在）。
- 数据库异常统一映射（`app/main.py`）：死锁 / 锁等待超时 / 约束冲突 / 连接池耗尽 → 409 `CONFLICT_RETRY`；字段超长、格式不符 → 422 `VALIDATION`。编码类字段上限 64 位。

新增错误码：在 `ErrorCode` 加一行 → `error_messages.py` 加英 / 越 → 运行 `gen_locales.py` → `uv run pytest`。

## 1. 准备 MySQL

公司 MySQL：`10.0.200.125:3306`，账户 `appuser`。应用首次启动时自动执行建表脚本（`app/db/migration/V*.sql`，按 Flyway 格式记录在 `flyway_schema_history`），**不需要手工执行 SQL**。

连库、备份、删表、删库都以 `SHOW DATABASES` 为准。`SHOW GRANTS` 里多出来的名字只是授权，不代表库还在。2026-10-09 在这台实例上核对：

```sql
SHOW DATABASES;
SHOW GRANTS FOR 'appuser'@'%';
```

| 来源 | 名字 | 处理 |
| --- | --- | --- |
| `SHOW DATABASES` | `sn_dev`、`sn_test`、`sn_prod` | 本系统的三个库，按环境使用（见下表）。`.env` 的 `DB_NAME` 以及下文 SQL 里的 `<库名>` 只填这三个之一 |
| `SHOW DATABASES` | `information_schema`、`mysql`、`performance_schema`、`sys` | 系统库，不配成 `DB_NAME`，也不删除 |
| 只出现在 `SHOW GRANTS` | `sndb` | 库已经不在，只留下 `GRANT ALL PRIVILEGES ON sndb.*`。按库授权不会随删库消失。不对 `sndb` 执行 `USE`、备份或 `DROP DATABASE` |

库名按环境固定：

| 环境 | `DB_NAME` | 说明 |
| --- | --- | --- |
| 开发 | `sn_dev` | 本机开发、联调；`.env.example` 与代码的默认值 |
| 测试 | `sn_test` | 测试环境、业务验收 |
| 正式 | `sn_prod` | 生产环境（Docker 部署）。只按第 7 节上线，不做第 8.1–8.3 节的清库操作 |

自动化测试（`uv run pytest`）另用独立的测试库（默认 `sndb_test_py`，`SN_TEST_DB_NAME` 可改），每次运行都会整库删除重建，**不要把它指向上面三个库**。

`appuser` 在 `sn_dev`、`sn_prod`、`sn_test` 上已是 `ALL PRIVILEGES`，覆盖本系统要的 `SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES`。`ALTER` / `DROP` 用于按月加分区与归档过期痕迹分区。

还要新建库时（名字避开上面的系统库）：

```sql
CREATE DATABASE <库名> CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

新库名不在现有授权里时才需要再授一次（`sn_dev`、`sn_prod`、`sn_test` 以及残留的 `sndb` 都已经授过）：

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES ON <库名>.* TO 'appuser'@'%';
```

不再使用 `sndb` 这个名字时，删掉残留授权，之后 `SHOW GRANTS` 里就不会再出现它：

```sql
REVOKE ALL PRIVILEGES ON sndb.* FROM 'appuser'@'%';
```

连通性自检（`<库名>` 用 `SHOW DATABASES` 里的那个，例如 `sn_dev`）：

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p <库名> -e "SELECT DATABASE(), CURRENT_USER()"
```

### 基线版本

**先理解执行记录**：程序是否执行建表脚本，只看库里的 `flyway_schema_history`（下称"记录表"）：脚本执行完记一笔，下次启动有记录就跳过。程序只看记录，不看库里实际有哪些表。当前只有 `V1__init.sql`（版本 `1`，创建本系统的 `sn_*` 表）。

**基线是什么**：库里已有表、却没有记录表时，程序分不清这些表是不是本系统的，默认拒绝启动。基线就是由人在新记录表里写下的第一笔（类型 `BASELINE`）："版本号小于等于 X 的脚本都当作已执行过，从下一个版本开始执行"。

**两个变量的关系**：`DB_BASELINE_ON_MIGRATE` 决定**要不要**写基线，`DB_BASELINE_VERSION` 决定基线**写成几**。后者只在前者为 `true` 且库处于「有表无记录表」状态时才被读取，其余情况两者都不起作用。

按库的情况选：

| 场景 | `DB_BASELINE_ON_MIGRATE` | `DB_BASELINE_VERSION` | 启动时发生什么 |
| --- | --- | --- | --- |
| A. 空库（一张表都没有） | `false`（默认） | 不写 | 建记录表，执行 V1 |
| B. 共用库：只有其他业务的表，没有 `sn_*` | `true` | `0` | 写基线 0，再执行 V1 建 `sn_*` 表 |
| C. `sn_*` 表已在且与 V1 一致，只缺记录表（如记录表被误删） | `true` | `1`（默认，可不写） | 写基线 1，跳过 V1，不建表 |
| D. 已有 `flyway_schema_history`（已启动过） | 任意 | 任意 | 只执行记录里没有的版本；两个变量都被忽略 |

`.env` 写法：

```bash
# 场景 A：空库
DB_BASELINE_ON_MIGRATE=false

# 场景 B：共用库（库里已有其他业务的表）
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=0

# 场景 C：补记录表
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=1
```

常见错配：

| 错误配置 | 结果 |
| --- | --- |
| 场景 B 没设 `ON_MIGRATE=true` | 拒绝启动，报「已有表但没有 flyway_schema_history」 |
| 场景 B 设了 `true` 但漏了 `VERSION=0` | 按默认 `1` 跳过 V1，启动报表不存在 |
| 场景 C 写成 `0` | 重新执行 V1，报「表已存在」 |

错配后已启动过一次：停服务，删掉 `flyway_schema_history`（及可能已建出的 `sn_*` 表），改好 `.env` 再启动。

首次在共用库上启动前，先查一下：

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
```

| 查询结果 | 处理 |
| --- | --- |
| 没有结果 | 按场景 B 启动 |
| 有同名 `sn_*` 表（不是本系统建的） | V1 会报「表已存在」，只能换库 |
| 有 `flyway_schema_history`（其他系统的记录） | 程序会沿用对方的记录，可能跳过本系统的 V1。只能换库 |

注意：

- 基线只在「有表但没有记录表」的那一次启动写入；之后再改这两个变量无效，要改须先删掉记录表。
- 首次建表中途失败会留下记录表和部分 `sn_*` 表，之后每次启动都报「表已存在」。按 [8.1](#81-删除本系统的表并重建) 删掉 `sn_*` 表与 `flyway_schema_history` 后重启。
- 版本号须为数字（可带点分，如 `1.2`）。无法解析时按 `1` 处理。

## 2. 配置 `.env`

在仓库根目录：

```bash
cp .env.example .env
```

至少填写：

| 变量 | 说明 |
| --- | --- |
| `DB_HOST` / `DB_PORT` / `DB_NAME` | 数据库地址、端口、库名。地址默认 `10.0.200.125:3306`。库名按环境：开发 `sn_dev`（`.env.example` 默认）、测试 `sn_test`、正式 `sn_prod`；换库只改对应一项，重启后端生效 |
| `DB_USER` / `DB_PASSWORD` | 数据库账户（密码原样读取，可含 `#`、`=`；首尾有空格时用引号包住） |
| `DB_URL` | 可选，兼容旧的 JDBC 一行写法；上面单独写了的项优先 |
| `DB_BASELINE_ON_MIGRATE` | 库里已有表但没有 `flyway_schema_history` 时，`true` 才允许启动并写入基线。空库保持 `false` |
| `DB_BASELINE_VERSION` | 基线版本。`1` 跳过 V1；`0` 仍执行 V1。见上文「基线版本」 |
| `SN_SECRET` | 令牌签名密钥，同时用于加密保存各生产组织的 MES 凭证和页面上保存的金蝶应用密钥。换成至少 32 位的随机串（`ENVIRONMENT=production` 时为空、为示例值或过短会拒绝启动）。**上线后不要随意更换**：更换后所有人须重新登录，已保存的 MES 凭证无法解密，须在「生产组织」页逐个重新填写并连接测试；页面保存过金蝶连接的，还须在生产订单页「金蝶连接」重新填写应用密钥（之前调用金蝶报 `K3_SECRET_UNREADABLE`） |
| `SN_INIT_ADMIN_EMP_NO` / `SN_INIT_ADMIN_PASSWORD` | 空库首次启动自动建的系统管理员的工号、密码（直接可用；`ENVIRONMENT=production` 时密码仍为 `Admin@123` 会拒绝启动） |
| `K3_ACCT_ID` / `K3_APP_ID` / `K3_APP_SECRET` / `K3_USERNAME` | 金蝶账套、第三方应用、用户名（向金蝶管理员获取）。也可以留空，启动后由系统管理员在生产订单页「金蝶连接」填写；页面保存过后以页面为准，`.env` 的 `K3_*`（含下面的重试参数）不再使用，见 [8.6](#86-金蝶连接页面配置) |
| `NPM_REGISTRY` | 可选，只在构建 `web` 镜像时传给 `npm ci`。国内访问 `registry.npmjs.org` 中断时设为 `https://registry.npmmirror.com`。见 [4.5](#45-前端依赖安装失败) |

`.env` 含密码，已在 `.gitignore` 中，**不要提交**。进程环境变量优先于 `.env`。

按需调整（默认值即 `.env.example` 里的值，完整清单见 `.env.example` 与 `app/core/config.py`）：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SN_SYNC_ENABLED` | `true` | 定时比对同步开关：按修改时间增量拉取已审核单据并与快照比对（反审核、删除、变更都在这一步发现） |
| `SN_SYNC_INTERVAL_MINUTES` | `10` | 比对同步间隔（分钟）。距上次比对同步（含页面、手动触发，成功失败都算）不到一个间隔的定时触发跳过 |
| `SN_MAINTAIN_ENABLED` | `true` | 每日维护开关（痕迹归档与清理、从金蝶同步生产组织、交付自检，执行时间 `SN_PARTITION_CRON`）。1 小时内已有实例做完的跳过（启动时那次也一样）；`false` = 本实例只在启动时建月分区 |
| `SN_PUSH_ENABLED` | `true` | MES 推送调度开关；关闭后只能由 MES 拉取（SN 分配页「已分配」页签仍可下载） |
| `SN_PUSH_POLL_SECONDS` | `5` | 推送调度轮询间隔（秒） |
| `SN_PUSH_RETRY_INTERVALS_MINUTES` | `1,5,15` | 推送没送达（超时、5xx、断连等）时的自动重试间隔（分钟，逗号分隔，个数即次数）。用尽后推送中断，由总部「继续推送」 |
| `SN_PUSH_RECEIPT_WAIT_MINUTES` | `1,5,10` | MES 应答「已收到」后等 ③ 回执的时长（分钟，逗号分隔）：送达后等第 1 个，超时按原批次重推、再等第 2 个，依次类推，个数即重推次数（最后一次重推后按最后一个时长等）。仍没有回执即推送中断，由总部「继续推送」或人工处理 |
| `SN_BATCH_UNCONFIRMED_ALERT_MINUTES` | `30` | 拉取的批次超过该时长仍未回执时产生交付告警 |
| `SN_MES_AUTH_MAX_FAILURES` / `SN_MES_AUTH_LOCK_MINUTES` | `10` / `15` | MES 接口账户密钥认证连续失败该次数后锁定该时长（423 `ACCOUNT_LOCKED`） |
| `SN_MES_PULL_RATE_PER_MINUTE` | `60` | 每个生产组织每分钟最多取批次数，超过返回 429 `RATE_LIMITED`（带 `Retry-After`） |
| `K3_PAGE_RETRIES` / `K3_PAGE_RETRY_SECONDS` | `3` / `10` | 金蝶分页查询失败时的重试次数与间隔（秒） |
| `SN_GEN_SYNC_THRESHOLD` / `SN_GEN_DEFAULT_LIMIT` / `SN_GEN_MAX_PER_RUN` | `5000` / `10000` / `500000` | 生成：超过阈值转后台任务；生成窗口默认单次上限；单次硬上限 |
| `SN_GEN_CONCURRENCY` | `4` | 一个实例同时写号池的生成数（当场与后台合计）。其余在任务里排队（页面照常显示生成中，同一 PI 照常提示正在生成）；当场生成排队超过 60 秒返回「稍后重试」，任务记为失败、不留号。见下文「并发与连接数」 |
| `SN_WORKERS` | `1` | 后端进程数。`1` 即单进程（与之前相同）；大于 1 时 uvicorn 起一个守护进程管理 N 个工作进程，共用同一端口，工作进程挂掉自动拉起。Docker 与 `start.py` 都读它。见下文「多进程」 |
| `DB_POOL_SIZE` | `20` | 连接池大小（每个进程各一个）。见下文「并发与连接数」 |
| `TZ` | `Asia/Shanghai` | 服务器时区：只用于月分区与每日维护任务（`SN_PARTITION_CRON`）的执行时间。业务时间一律按 UTC 存储，页面按各生产组织配置的时区显示 |
| `LOG_MAX_SIZE` / `LOG_MAX_FILE` | `50m` / `10` | 仅 Docker 部署：每个容器日志单个文件上限与保留个数（见 [4.6](#46-日志与轮转)） |

已删除的配置项：`SN_ACQUIRE_REQUIRE_SNAPSHOT`、`SN_CALLBACK_MAX`（不再有打印回调与页面领取）。旧 `.env` 里留着也不会读取，可以删掉。

**多实例部署**：推送调度、订单比对同步、每日维护、中断生成任务回收都在进程内运行，各实例配置相同即可，不会重复执行：

- 推送任务有租约（运行期间续租）且认领互斥：不会重复推送、不会超出推送并发上限；
- 订单比对同步：同步锁防同时执行，且距上次比对同步不到 `SN_SYNC_INTERVAL_MINUTES` 的定时触发跳过，多个实例合起来仍是每个间隔一次；
- 每日维护：命名锁防同时执行，且 1 小时内已有实例做完的跳过（各实例都在 02:10 触发、滚动发布时相继启动，都只做一次）；
- 中断生成任务：执行后台生成的实例被停止或进程退出（滚动发布、缩容、崩溃）后，其他实例 1 分钟内把该任务标为失败并释放 PI（号已随事务回滚），不必等下次重启；整机断电、断网时要等 MySQL 判定该连接断开（`wait_timeout`）后才回收。

**并发与连接数**（《[多账户并发生成推送测试报告](测试记录/多账户并发生成推送测试报告.md)》之后的修正，接口不变）：

- 连接：一个实例最多占 `2 × DB_POOL_SIZE` 条池内连接（请求、后台任务的第一条连接占主名额；已经拿着一条、又要另开独立事务写失败痕迹、生成进度、取消检查的，占同样多的备用名额，不会因主名额被占满而互相等满 30 秒），另加命名锁（PI 操作锁、前缀锁等）各一条独立连接，最多约为同时在做的生成、分配、转移数。**所有实例合计须低于 MySQL `max_connections`（默认 151）**：例如 2 个实例、`DB_POOL_SIZE=20` 约需 2 × (40 + 20) = 120 条；不够时调小 `DB_POOL_SIZE`、减少实例，或请 DBA 调大 `max_connections`。
- 生成：同时写号池的生成每个实例不超过 `SN_GEN_CONCURRENCY`；号池写入、计数行、新前缀判断都避开了可重复读下的间隙锁，几张 PI 同时生成、同时分配不再互相死锁。万一仍撞上死锁（MySQL 1213，整笔已回滚），生成与分配都自动整笔重做，最多 3 次；日志 `gen_deadlock_retry`。
- 推送：一个实例同时执行的推送任务不超过 8 个（推送线程数），调度只认领空闲线程数那么多个，其余留在排队；执行中遇数据库锁冲突（死锁、锁等待超时、连接池满）不再停止，任务转为等待、10 秒后自动接着推（日志 `push_task_conflict`），连续 5 次仍冲突才停止、由「继续推送」处理。
- 首页看板的「暂停交付」只数在途的号（待分配、待推送、已分配），不再整个号池全表扫描。

**多进程（`SN_WORKERS`）**：

- 为什么要开：接口、生成、推送虽然是异步收请求、线程里执行，但 Python 一个进程同一时刻只能用满 1 个 CPU 核（全局解释器锁）。`api` 容器 CPU 长时间接近 100%（单核）、数据库却不忙时，在 `.env` 设 `SN_WORKERS=2`～`4`（不超过 CPU 核数），`docker compose up -d --force-recreate api` 生效（本版本改了 `Dockerfile` 的启动命令，更新到本版本时照常 `docker compose up -d --build`）。
- 为什么能开：代码按多实例设计，多进程与多台机器上的多实例一样——生成、分配用 MySQL 命名锁，推送任务有租约与认领互斥，订单同步、每日维护有锁且按间隔只做一次；建表、建首个管理员、演示数据在启动时按命名锁依次做，几个进程同时启动也只做一次。
- 连接预算按进程数算：每个进程最多 `2 × DB_POOL_SIZE` 条池内连接，加命名锁各一条。例如 `SN_WORKERS=3`、`DB_POOL_SIZE=15`：约 3 × (30 + 15) = 135 条，须低于 MySQL `max_connections`（默认 151）。
- `SN_GEN_CONCURRENCY` 是每个进程各自的上限：3 个进程时建议每个设 `2`，合计同时写号池的生成数不至于翻倍。
- 日志（JSON）每行带 `pid`，可看出是哪个工作进程；推送任务的 `runner` 也带进程号。
- 已知限制：订单同步的进度只记在执行它的进程内存里，页面请求落到别的进程时只显示「同步进行中」，看不到步骤与行数（不影响同步本身）。
- 进程数再多瓶颈会回到数据库（连接、锁、磁盘），查询随数据量变慢也不靠加进程解决，见[容量、性能与扩展评估报告](容量性能与扩展评估报告.md)。

只想让固定实例跑后台任务时，其他实例设 `SN_PUSH_ENABLED=false`、`SN_SYNC_ENABLED=false`、`SN_MAINTAIN_ENABLED=false`（中断生成任务回收始终开启，开销是每分钟一次查询）。所有实例的 `SN_SECRET` 必须相同。

本机没有金蝶也想试用：`SN_DEMO_SEED=true`，空库启动时会灌入 3 个演示生产组织（`110` 越南、`120` 大磡、`130` 泗洪，均未开启对接 MES）、2 条规则、若干生产订单物料行和演示账户 `vn01 / dk01 / sh01`（普通操作员，各授权一个组织）、`query01`（审计员，授权全部 3 个组织），密码 `SN_DEMO_PASSWORD`（默认 `Demo@1234`）。**连公司库时务必为 false。**

## 3. 方式 A：本机一键启动

> 只用于本机开发、演示。**生产环境只允许方式 B（Docker Compose：nginx + api）**：后端端口不对外暴露，来源地址（`X-Real-IP`）与请求号（`X-Request-ID`）由 nginx 填写；直连 8000 端口时这两个请求头由客户端自报，登录留痕里的来源地址不可信。

要求：Python 3.12+（`python` 在 PATH）、Node.js 20+。

```bash
python start.py             # Linux / macOS / Windows（Windows 也可双击 start.bat）
python start.py --rebuild   # 强制重新构建前端
python start.py --port 8001
```

首次会建 `.venv` 并安装后端依赖、`npm install` 并构建前端；之后只有前端源码变化才重新构建。启动后浏览器打开 `http://127.0.0.1:8000`，用 `SN_INIT_ADMIN_EMP_NO` + `SN_INIT_ADMIN_PASSWORD`（默认 `admin` / `Admin@123`）登录；不强制改密，建议登录后在左下角账户菜单里改掉初始密码。

关闭：本窗口 `Ctrl+C`，或 `python start.py --stop` / `stop.bat`（按 `tools/runtime.json` 与端口找进程）。

## 4. 方式 B：Docker Compose

服务器部署使用分支 `sn-center-python`，克隆时只取这一支。仓库：`https://github.com/Createsnow/sn-center.git`。`Dockerfile` 与 `docker-compose.yml` 在仓库根目录。

### 4.1 服务器首次拉取

```bash
git clone -b sn-center-python --single-branch https://github.com/Createsnow/sn-center.git
cd sn-center
cp .env.example .env    # 按第 2 节填好 DB_*（正式环境 DB_NAME=sn_prod）、SN_SECRET、SN_INIT_ADMIN_EMP_NO / SN_INIT_ADMIN_PASSWORD、K3_*
docker compose up -d --build
```

仓库为私有时，`git clone` 需要登录：HTTPS 使用有读权限的 Personal Access Token；已配置 SSH 密钥时改用 `git@github.com:Createsnow/sn-center.git`。

- `api`：FastAPI（Uvicorn），`ENVIRONMENT=production`（日志为单行 JSON，按 [4.6](#46-日志与轮转) 轮转），健康检查 `/health/ready`（含数据库连通）；
- `web`：nginx 托管前端，反代 `/api`、`/health`、`/docs`（含 `/openapi.json`）；读超时 600 秒（全量同步、大导出），请求体上限 50 MB（MES 回执、大批量请求）；直连 8000 端口（方式 A）时后端同样只收 50 MB 以内的写请求，超出页面接口返回 413、MES 接口返回 400。

Compose 不随附 MySQL，数据库按 `.env` 的 `DB_*` 连接已有库。`.env` 只留在服务器上，更新代码时保留原文件，也不要提交进 Git。

浏览器打开 `http://<IP>`（`WEB_PORT`，默认 80）。停止：`docker compose down`（不要加 `-v`）。

### 4.2 更新代码后重新构建

在部署目录执行，只更新 `sn-center-python`：

```bash
cd sn-center
git pull origin sn-center-python
docker compose up -d --build
```

切换过分支（见 4.3）后，把命令里的 `sn-center-python` 换成当前分支名；当前分支用 `git branch --show-current` 查看。

### 4.3 切换分支

4.1 克隆时用了 `--single-branch`，本地只有 `sn-center-python`，直接 `git checkout 其他分支` 会报 `pathspec ... did not match`，须先把目标分支取下来。以切到 `sn-center-python-v2` 为例，在部署目录执行：

```bash
cd sn-center
git status                                                  # 确认没有本地改动（.env 不在 Git 里，不受影响）
git remote set-branches --add origin sn-center-python-v2    # 登记要拉的分支，每个分支只需做一次
git fetch origin sn-center-python-v2
git diff --stat HEAD origin/sn-center-python-v2 -- app/db/migration .env.example   # 看表结构、配置项有没有变化
git checkout sn-center-python-v2                            # 首次切换会自动跟踪 origin/sn-center-python-v2
docker compose up -d --build
```

- 上面 `git diff` 列出 `app/db/migration/` 有变化：两个分支的表结构不同，按第 8 节「改表」一行处理后再启动；列出 `.env.example` 有变化：对照补齐服务器 `.env` 里的新配置项。
- 之后更新：`git pull origin sn-center-python-v2`，再 `docker compose up -d --build`。
- 切回原分支：`git checkout sn-center-python`，再 `docker compose up -d --build`（同样先看表结构是否一致）。

### 4.4 基础镜像拉取失败

构建停在 `load metadata`，报 `failed to resolve source metadata` 或 `failed size validation`（例如 `nginx:1.27-alpine` 报 `28445 != 27783`）时，先失败的那一个会把同一次构建里的其他基础镜像取消。涉及的镜像是 `python:3.12-slim`、`node:22-alpine`、`nginx:1.27-alpine`（`web` 的 Dockerfile 第 9 行）。本地已有的镜像会显示 `0.0s`，不必重新拉。先清掉构建缓存再构建：

```bash
docker builder prune -af
docker compose up -d --build
```

`docker builder prune -af` 会删掉本机全部构建缓存，下次构建会重新拉取基础镜像并重装依赖。

仍是同一报错时，先单独拉三个基础镜像，再构建：

```bash
docker pull python:3.12-slim
docker pull node:22-alpine
docker pull nginx:1.27-alpine
docker compose up -d --build
```

`docker pull` 也报 `failed size validation` 时，多半是 `/etc/docker/daemon.json` 里的 `registry-mirrors`，或 HTTP 代理改写了响应（清单声明的大小和实际字节数不一致）。把镜像加速配置挪走或换成可用的源后执行 `sudo systemctl restart docker`，再重复上面的 `docker pull`。怀疑代理时，去掉代理再拉一次：

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY docker pull nginx:1.27-alpine
```

### 4.5 前端依赖安装失败

`api` 镜像可以已经构建成功，`web` 停在 `frontend/Dockerfile` 的 `npm ci`：

```text
npm error Exit handler never called!
target web: failed to solve: process "/bin/sh -c npm ci --registry=..." did not complete successfully: exit code: 1
```

这是安装过程中连 `https://registry.npmjs.org` 中断后，npm 自身崩溃，不是 `package.json` 或 lock 文件写错。`package-lock.json` 里的地址仍是官方源；`npm ci --registry=...` 会把这些地址改写到下面配置的源，不用改 lock 文件。

在服务器的 `sn-center/.env` 增加（该文件不提交）：

```bash
NPM_REGISTRY=https://registry.npmmirror.com
```

然后重新构建。`api` 层会走缓存，主要重跑 `web`：

```bash
docker compose up -d --build
```

不想写入 `.env` 时，只对这一次生效：

```bash
NPM_REGISTRY=https://registry.npmmirror.com docker compose up -d --build
```

### 4.6 日志与轮转

程序不写日志文件，所有日志写标准输出，由运行环境保存和轮转：

- **格式**：`ENVIRONMENT=production` 时每行一条 JSON，本系统的事件与 Uvicorn 的启动、错误、访问日志格式相同，都带 `timestamp`（UTC）、`level`、`logger`；请求内产生的日志带 `request_id`。访问日志另拆出 `client`、`method`、`path`、`status`。成功的健康检查（`/health/*`，探针每几秒一次）不记访问日志，httpx 只记告警以上。
- **Docker 部署**：`docker-compose.yml` 给 `api`、`web` 都配了 json-file 轮转，每个容器最多 `LOG_MAX_FILE` 个文件、每个 `LOG_MAX_SIZE`（默认 10 × 50 MB，单容器最多约 500 MB）。在 `.env` 里改这两项后需重建容器生效：

  ```bash
  docker compose up -d --force-recreate
  ```

  只轮转、不归档：超出的旧日志直接丢弃；**删除或重建容器（`docker compose down`、改代码后 `up -d --build`）时该容器的日志一并删除**，需要留存的先导出（见 [4.7](#47-在-linux-上查看日志)）。要长期留存或集中检索，接入公司的日志平台（采集 Docker 容器日志即可）。查看命令见 [4.7](#47-在-linux-上查看日志)。
- **K8s 部署**：kubelet 按节点配置轮转容器日志（默认单文件 10 MiB、保留 5 个），长期留存同样交给日志采集。
- **本机启动（方式 A）**：日志只打在启动窗口，关掉即没有；只用于开发、演示。

业务操作痕迹不在日志里，存在 `sn_audit`，按 `SN_AUDIT_RETENTION_DAYS` / `SN_AUDIT_ARCHIVE_RETENTION_DAYS` 自动归档和清理（见第 8 节）。

### 4.7 在 Linux 上查看日志

以下以方式 B（Docker Compose）为准，命令在**部署目录**（`docker-compose.yml` 所在的 `sn-center` 目录）执行；当前账户不在 `docker` 组时，命令前加 `sudo`。容器名默认为 `sn-center-api-1`、`sn-center-web-1`（`docker compose ps` 查看），不在部署目录时把 `docker compose logs api` 换成 `docker logs sn-center-api-1`，参数相同（`docker logs` 没有每行前缀，去掉 `--no-log-prefix`、`--no-color` 即可）。

**1. 常用查看**

```bash
# 容器状态与健康（STATUS 列 healthy / unhealthy）
docker compose ps

# 最近 200 行
docker compose logs --tail=200 api

# 实时跟踪（Ctrl+C 退出，不影响服务）
docker compose logs -f --tail=50 api

# 按时间范围：相对时间（单位 s / m / h，不支持 d，7 天写 168h），或带 Z 的 UTC 时间（不带 Z 按服务器本地时间算）
docker compose logs --since 30m api
docker compose logs --since 2026-11-02T01:00:00Z --until 2026-11-02T02:00:00Z api

# nginx（web）：访问日志与错误日志，普通文本格式
docker compose logs --tail=200 web
docker compose logs --since 1h web | grep -E '" 5[0-9]{2} '
```

日志里的 `timestamp` 一律是 UTC，北京时间 = UTC + 8 小时。

**2. 按关键字查找（grep）**

`api` 的日志每行一条 JSON，中文在原始行里是 `\uXXXX` 转义，**grep 直接搜中文搜不到**；按事件名、请求号、批次号、PI 等英文 / 数字内容搜即可：

```bash
# 只看告警和错误
docker compose logs --since 24h api | grep -E '"level": "(warning|error)"'

# 按请求号查一次请求的全部日志（请求号见响应头 X-Request-ID，或痕迹的 trace_id）
docker compose logs api | grep 8187641e-e27f-40eb-be01-46cb1ab2de5f

# 按事件名（事件名见下面第 5 条）
docker compose logs --since 168h api | grep -E 'unhandled_error|db_error|db_pool_exhausted'

# 统计最近 24 小时各类错误次数
docker compose logs --since 24h api | grep -oE '"event": "[a-z_]+"[^}]*"level": "error"' | grep -oE '"event": "[a-z_]+"' | sort | uniq -c | sort -rn
```

**3. 用 jq 筛选、格式化（推荐）**

jq 会把 `\uXXXX` 还原成中文，异常堆栈也按原样换行显示。先安装：Ubuntu / Debian `sudo apt install -y jq`，CentOS / 麒麟等 `sudo yum install -y jq`。下面的 `--no-log-prefix` 去掉每行前的 `api-1  |` 前缀；`fromjson?` 跳过非 JSON 行，不会报错中断：

```bash
# 告警和错误，每条一行
docker compose logs --no-log-prefix --since 24h api | jq -cR 'fromjson? | select(.level == "warning" or .level == "error")'

# 简洁格式：时间 级别 事件
docker compose logs --no-log-prefix --tail=500 api | jq -rR 'fromjson? | "\(.timestamp)  \(.level)  \(.event)"'

# 带异常堆栈的错误（500 等），堆栈原样换行
docker compose logs --no-log-prefix --since 24h api | jq -rR 'fromjson? | select(.exception) | "==== \(.timestamp) \(.event) \(.path // "") \(.request_id // "")\n\(.exception)"'

# 访问日志：时间 状态码 方法 路径 请求号
docker compose logs --no-log-prefix --since 1h api | jq -rR 'fromjson? | select(.logger == "uvicorn.access") | "\(.timestamp)  \(.status)  \(.method) \(.path)  \(.request_id // "-")"'

# 4xx / 5xx 按路径统计次数
docker compose logs --no-log-prefix --since 24h api | jq -rR 'fromjson? | select(.logger == "uvicorn.access" and .status >= 400) | "\(.status) \(.path)"' | sort | uniq -c | sort -rn | head -20

# 实时跟踪，只看告警和错误
docker compose logs -f --no-log-prefix --tail=0 api | jq --unbuffered -cR 'fromjson? | select(.level == "warning" or .level == "error")'
```

**4. 导出、留存与磁盘占用**

```bash
# 导出（升级、重建容器前先导出，否则日志随旧容器删除）；不要加 -t，否则每行前多出时间戳、不再是 JSON
mkdir -p ~/sn-logs
docker compose logs --no-color --no-log-prefix api | gzip > ~/sn-logs/api-$(date +%Y%m%d-%H%M).log.gz
docker compose logs --no-color --no-log-prefix web | gzip > ~/sn-logs/web-$(date +%Y%m%d-%H%M).log.gz

# 查看导出的文件
zcat ~/sn-logs/api-20261102-1000.log.gz | jq -cR 'fromjson? | select(.level == "error")'

# 宿主机上的日志文件位置与占用（轮转后的旧文件为 *-json.log.1、.2 …；需要 root）
sudo ls -lh $(dirname $(docker inspect --format '{{.LogPath}}' sn-center-api-1))
sudo du -ch $(dirname $(docker inspect --format '{{.LogPath}}' sn-center-api-1))/*-json.log* | tail -1

# 直接读宿主机文件：每行外面包了一层 Docker 的 JSON，先取 .log 再解析
sudo cat $(docker inspect --format '{{.LogPath}}' sn-center-api-1) | jq -r .log | jq -cR 'fromjson? | select(.level == "error")'
```

**5. 健康检查与常见事件**

成功的健康检查不记访问日志。容器显示 `unhealthy` 时看最近几次探测结果：

```bash
docker inspect --format '{{json .State.Health}}' sn-center-api-1 | jq
```

`api` 日志里常用的事件名（`event` 字段）：

| 事件 | 级别 | 含义与处理 |
| --- | --- | --- |
| `sn_center_ready` | info | 启动完成。之前应有 `partition_added`（首次建分区）、`bootstrap_admin`（空库建管理员）等 |
| `unhandled_error` / `db_error` | error | 接口返回 500，带 `exception` 堆栈与 `request_id`，按上面第 3 条查堆栈 |
| `db_pool_exhausted` | error | 连接池满，接口返回 409 让调用方重试；频繁出现时调大 `DB_POOL_SIZE` 并核对 MySQL `max_connections` |
| `db_conflict` | warning | 死锁 / 锁等待 / 约束冲突，接口返回 409 让调用方重试；偶发正常，持续出现需排查 |
| `compare_sync_failed` / `daily_factory_sync_failed` | warning | 订单比对同步、生产组织同步失败（多为金蝶不可达或 `K3_*` 配置不对），下个周期自动重试 |
| `push_task_failed` / `push_scheduler_failed` / `push_lease_renew_failed` | error / warning | 推送任务或调度异常，带堆栈；结合首页「推送中断」处理 |
| `push_task_conflict` | warning | 推送任务遇数据库锁冲突，已转为等待、10 秒后自动接着推（`attempt` 为连续第几次）；连续 5 次后停止并记 `push_task_failed` |
| `gen_failed` | error | 生成失败（已整批回滚），带堆栈；`deadlock=true` 为死锁自动重做 3 次仍失败 |
| `gen_deadlock_retry` | warning | 生成撞上死锁（已整笔回滚），自动整笔重做（`attempt` 为第几次）；偶发正常，频繁出现时调小 `SN_GEN_CONCURRENCY` |
| `gen_jobs_recovered` | warning | 回收了执行实例已退出的生成任务（重启、滚动发布后出现属正常） |
| `scheduled_job_failed` / `daily_self_check_failed` | error | 定时任务本次执行失败，下次照常执行 |
| `migration_checksum_mismatch` | warning | 已执行的建表脚本被改过，见第 9 节 |
| `weak_secret` / `weak_admin_password` | warning | 非生产环境用了弱密钥 / 默认密码（生产环境会直接拒绝启动） |
| `daily_maintain_skipped` / `partition_maintain_skipped` | info | 每日维护已由本实例或别的实例做过 / 正在做，属正常 |

## 6. 账户与权限

系统有三种页面账户（系统管理员、普通操作员、审计员）和一种接口账户。系统管理员只有一个（工号 `SN_INIT_ADMIN_EMP_NO`），只有它能在「账户」页创建、修改、停用账户、重置密码或密钥、授权生产组织，不能再建第二个系统管理员。账户只停用、不删除，停用后可重新启用。工号 3–32 位字母、数字和 `-`，唯一，区分大小写；页面账户密码 4–64 位，同时含字母和数字，只能用字母、数字和 `! @ # $ & * -`。新建页面账户用创建时设定的密码直接登录，任何时候都不强制改密；本人改密或系统管理员重置密码后，该账户已登录的页面全部退出，用新密码重新登录。同一账户只在最后登录的那个页面有效。

| 角色 | 角色值 | 授权生产组织 | 登录方式 |
| --- | --- | --- | --- |
| 系统管理员 | `admin`（工号 = `SN_INIT_ADMIN_EMP_NO`，唯一） | 不绑定（全部组织） | 页面 |
| 普通操作员 | `operator` | 多选，**至少一个** | 页面 |
| 审计员 | `auditor` | 多选，**至少一个**（只读） | 页面（也可调用 MES 只读接口④⑤核对） |
| MES 接口账户 | `mes` | 必须绑一个生产组织（不要求已开启「对接 MES」） | **不能登录页面**，只能调 `/api/mes/v1` |

普通操作员、审计员没有任何授权组织时不能登录（提示「账户未授权任何生产组织」）。从金蝶同步新增的生产组织**不会自动授权**给任何账户，需要时由系统管理员在「账户」页加上。

系统管理员由首次启动按 `.env` 的 `SN_INIT_ADMIN_EMP_NO` / `SN_INIT_ADMIN_PASSWORD` 自动创建，直接可用；之后若在页面上改过密码，以新密码为准（改 `.env` 不会改库里已有账户，见第 9 节「忘记系统管理员密码」）。密码不写在本文。

**MES 接口账户**（F-01、MES 对接接口文档 2.1）：

- 在「账户」页「MES 接口账户」页签创建，系统生成密钥，当场复制交给 MES 方。密钥用 `SN_SECRET` 派生的密钥加密保存，列表不显示；之后需要时点「查看密钥」再看（每次查看都留痕）。泄露或想换新时点「重置密钥」：旧密钥立即失效，须把新密钥交给 MES 方更新。更换 `SN_SECRET` 后旧密钥无法查看（认证不受影响），需要时重置即可。
- 可填来源地址白名单（IP 或 CIDR，逗号分隔，空 = 不限）。白名单按 nginx 写入的 `X-Real-IP` 判断，生产须走方式 B。
- MES 每次请求带 `Authorization: Bearer <工号>:<密钥>`，不换令牌；连续失败 `SN_MES_AUTH_MAX_FAILURES`（默认 10）次锁定 `SN_MES_AUTH_LOCK_MINUTES`（默认 15）分钟，锁定、解锁都留痕。
- 停用账户后所有请求返回 403 `ACCOUNT_DISABLED`。所绑组织关闭「对接 MES」后，取批不再新建批次，只能取回已有的未确认批次（含转出批次）并回执。

## 7. 上线步骤建议

1. 确认库（正式 `sn_prod`、测试 `sn_test`）、配 `.env`（`K3_*` 连接参数可在这里填，也可启动后在生产订单页「金蝶连接」填写，见 [8.6](#86-金蝶连接页面配置)），启动一次（自动建表、建 `admin`、建月分区）。从旧版本升级的库须先按 8.1–8.3 之一重建（见第 8 节的「PRD V30 版本说明」）。
2. `admin` 登录（建议先在左下角账户菜单里改掉初始密码）→「生产组织」页 **从金蝶同步**（之后每天 02:10 自动同步一次；名称、启用状态随金蝶更新）。
3. 对接 MES 的生产组织：在「生产组织」页逐个填写 MES 对接配置（接收推送的地址、认证方式与凭证（与 MES 方约定为 TOKEN，凭证填 `工号:密钥`，见《MES 对接接口文档》2.1；HMAC 为备用方式；MES 在内网按来源 IP 等自行限制访问时可选「无认证」，不填凭证）、gzip 压缩（默认关）、单批枚数、推送超时、推送并发、时区），点 **连接测试**（发 `PING` 批次）通过后才能开启「对接 MES」（正式环境建议第 7 步联调通过后再开启）。开启前已分配的已分配号会转为待推送，但不会自动推送，需在 SN 分配页「继续推送」。
4. 「账户」页为每个对接 MES 的组织建 **MES 接口账户**（记下密钥，按需填来源地址白名单；不要求该组织已开启「对接 MES」，未开启时 MES 只能取转出批次、提交回执和只读查询），连同 [MES 对接接口文档](MES对接接口文档.md)、[MES 对接说明](MES对接说明.md) 交给 MES 方；再按需建普通操作员、审计员并授权生产组织。
5. 「生产订单」页 **全量重建** 一次快照（首次上线导入；之后靠定时比对同步与按单据同步），检查附件项次待填写、无客户编码的单据。
6. 「规则库」新建规则（前缀必填且不能与别的规则相同；按需带米数）；给 PI 或物料行选规则在「SN 生成」页做。
7. **MES 联调**：按 PRD 9.2「上线准入：MES 异常场景联调」逐项验证（推送超时重试、同一批重发、回执不符、整批拒收、推送与取批撞车、转出批次、限流、令牌过期等），全部通过后再在正式环境开启对接。MES 方未接入前可先用模拟 MES 演练、用契约测试验收 MES 的接收接口，方法和场景对照表见 [MES 联调指南](<MES 联调指南.md>)。
8. 小范围试产：选一张 PI 走完 生成 → 分配 → 推送 / 拉取 → 回执确认（未对接 MES 的组织在 SN 分配页「已分配」页签下载），核对首页看板、交付批次与操作痕迹。

**清库重建：三种做法**

三种做法都只用于开发库 `sn_dev`、测试库 `sn_test`；**正式库 `sn_prod` 不做**。按库里有没有别的系统的表、手上有没有 root 选一种：

| 做法 | 删掉什么 | 保留什么 | 执行账户 | 适用 |
| --- | --- | --- | --- | --- |
| [8.1 删除本系统的表并重建](#81-删除本系统的表并重建) | `sn_` 开头的表和 `flyway_schema_history` | 库、授权、其他系统的表和视图 | `appuser` | 库里还有其他系统的表（共用库）；或只想重建本系统的表 |
| [8.2 清空整库并重建](#82-清空整库并重建) | 库里所有表、视图、存储过程、函数、事件 | 库、授权 | `appuser` | 库只给本系统用，要一个空库，但没有 root |
| [8.3 删除整库、重建并授权](#83-删除整库重建并授权) | 整个库 | 账户 | `root` | 库只给本系统用，要从建库开始重来（字符集按新建时设定）；或库不再使用，只删不建 |

> **三种做法都会清空本系统的全部数据，只能从备份恢复**：账户（含 MES 接口账户）、生产组织与 MES 对接配置、页面保存的金蝶连接、规则、订单快照与出号台账、号池、交付批次、转单与转组织记录、操作痕迹。表结构没变、只想清业务数据并保留账户时，用 [8.5 保留账户、清空其他数据](#85-保留账户清空其他数据)。

命令约定（三节通用）：

- 下文的 `10.0.200.125` 是公司 MySQL，`sn_test` 是示例库名：照抄前把 `sn_test` 换成要处理的库（`sn_dev` 或 `sn_test`）。
- `mysql`、`mysqldump` 是 MySQL 客户端命令，Linux / macOS 终端、Windows 命令提示符、PowerShell 都能执行；`-p` 表示回车后输入密码。
- 「登录 MySQL」后出现 `mysql>` 提示符：把 SQL 整段粘贴进去回车执行，做完输入 `exit` 退出。用 Navicat / DBeaver 时，连到同一个库，在查询窗口执行同样的 SQL。
- 8.1、8.2 的删除 SQL 会先检查当前库：不是 `sn_dev` / `sn_test` 时只输出 `REFUSED: current database is not sn_dev / sn_test`，什么也不删。

### 8.1 删除本系统的表并重建

只删本系统的表：`sn_` 开头的表与迁移记录表 `flyway_schema_history`。库里其他系统的表、视图原样保留。删完启动一次，程序按 `V1__init.sql` 重新建表。演示阶段改了 `V1__init.sql` 后用这种做法（已有的库不会重新执行 V1，日志只有 `migration_checksum_mismatch` 警告）。

**第 1 步：停止服务**（所有实例都要停，否则删表会被正在跑的请求或定时任务卡住）

```bash
# 方式 A 本机：启动窗口按 Ctrl+C，或执行
python start.py --stop
# 方式 B Docker：在部署目录执行（不要用 down -v）
docker compose stop api
# 方式 C 开发：在 uvicorn 窗口按 Ctrl+C
```

**第 2 步：备份整个库**

```bash
mysqldump -h 10.0.200.125 -P 3306 -u appuser -p --single-transaction --no-tablespaces --routines --triggers --events --result-file=backup_sn_test.sql sn_test
```

生成 `backup_sn_test.sql`（同名文件会被覆盖）。`--no-tablespaces` 避免 `appuser` 没有 `PROCESS` 权限时报错。要恢复时执行：

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"
```

**第 3 步：登录 MySQL，确认库和连接**

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test
```

```sql
SELECT DATABASE() AS current_db;
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = DATABASE();
```

`current_db` 必须是要处理的库。连接列表里应当只有你自己这一条（`command` 为 `Query`）；还有别的连接说明服务没停干净，回到第 1 步。

**第 4 步：预览要删的表**

```sql
SELECT table_name, table_type,
       IF(table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history', 'DROP', 'KEEP') AS action
FROM information_schema.tables
WHERE table_schema = DATABASE()
ORDER BY action, table_name;
```

- `DROP`：本系统的表，第 5 步会删。当前版本是 40 张 `sn_` 表加 `flyway_schema_history`；旧版本留下的 `sn_` 表（例如 `sn_batch`、`sn_key`、`sn_print`、`sn_customer_rule`）也在其中，一并删除。
- `KEEP`：其他系统的表和视图，不动。
- `DROP` 里出现不是本系统建的表时停下，不要继续。

**第 5 步：删表**

```sql
SET SESSION group_concat_max_len = 1000000;
SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP TABLE IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
SELECT @drop_sql;
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;
```

`SELECT @drop_sql` 显示的就是实际执行的那条 `DROP TABLE`。本系统不建外键，删除顺序无所谓；`sn_audit` 是分区表，连分区一起删掉。

**第 6 步：确认已删干净**

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
-- 应当返回 Empty set

SHOW FULL TABLES;
-- 剩下的都是其他系统的表。记下有没有剩下的表，第 7 步要用
exit
```

**第 7 步：设置 `.env` 的基线**（最容易出错的一步）

| 第 6 步 `SHOW FULL TABLES` 的结果 | `.env` | 原因 |
| --- | --- | --- |
| `Empty set`（库已经空了） | `DB_BASELINE_ON_MIGRATE=false` | 空库直接执行 V1 |
| 还有其他系统的表 | `DB_BASELINE_ON_MIGRATE=true` 和 `DB_BASELINE_VERSION=0` | 不设：拒绝启动，报「已有表但没有 flyway_schema_history」；设成 `1`（默认）：跳过建表，启动报表不存在 |

库里还有其他系统的表时，`.env` 写：

```bash
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=0
```

设错了且已经启动过一次：停服务，从第 3 步重做（会删掉已写入的 `flyway_schema_history` 和已建出的 `sn_` 表），改好 `.env` 再启动。

**第 8 步：启动并检查**

```bash

python start.py
# 方式 B Docker（部署目录）
docker compose up -d
docker compose logs --tail=200 api
```

启动日志里应当依次出现 `partition_added`（建月分区）、`bootstrap_admin`（建系统管理员）、`sn_center_ready`。浏览器打开 `http://<服务器>:8000/health/ready`（方式 A）或 `http://<服务器>/health/ready`（方式 B），应返回 `{"status":"ok","db":"mysql"}`。再登录 MySQL（同第 3 步）确认：

```sql

FROM flyway_schema_history
ORDER BY installed_rank;
-- 空库：1 行      1 | 1 | SQL | V1__init.sql | 1
-- 基线 0：2 行    1 | 0 | BASELINE | << Flyway Baseline >> | 1
--                 2 | 1 | SQL | V1__init.sql | 1

SELECT COUNT(*) AS sn_tables
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_name LIKE 'sn\_%';
-- 38

SELECT emp_no FROM sn_user;
-- 只有 .env 里的 SN_INIT_ADMIN_EMP_NO（默认 admin）
```

**第 9 步：重新初始化数据**

1. 用 `.env` 里的 `SN_INIT_ADMIN_EMP_NO` + `SN_INIT_ADMIN_PASSWORD` 登录（旧账户都已删除），建议先改掉初始密码。
2. 按[第 7 节](#7-上线步骤建议)第 2–6 步重做：同步生产组织、填 MES 对接配置并连接测试、建 MES 接口账户（新密钥要重新交给 MES 方）、全量重建订单快照、配规则库、创建普通操作员和审计员账户并授权生产组织。
3. 只看演示效果时，可在 `.env` 设 `SN_DEMO_SEED=true` 再启动，自动放入演示生产组织、订单和账户（**连公司库时务必为 false**）。

### 8.2 清空整库并重建

删掉库里**所有**表、视图、存储过程、函数、事件，库本身和授权保留，得到一个空库；启动时程序按空库直接建表。用 `appuser` 就能做，不需要 root。

> **会删掉库里所有系统的数据。** 先确认这个库只给本系统用，或库里其他系统的东西确实都不要了。拿不准时用 [8.1](#81-删除本系统的表并重建)。

**第 1 步：停止服务**，命令同 [8.1 第 1 步](#81-删除本系统的表并重建)。库里还有别的系统在用时，也要先停掉它们。

**第 2 步：备份整个库**

```bash
mysqldump -h 10.0.200.125 -P 3306 -u appuser -p --single-transaction --no-tablespaces --routines --triggers --events --result-file=backup_sn_test.sql sn_test
```

要恢复时执行 `mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"`。

**第 3 步：登录 MySQL，确认库和连接**

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test
```

```sql
SELECT DATABASE() AS current_db;
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = DATABASE();
```

`current_db` 必须是要处理的库；连接列表里应当只有你自己这一条。

**第 4 步：预览库里有什么**

```sql
SELECT table_type AS object_type, COUNT(*) AS cnt
FROM information_schema.tables WHERE table_schema = DATABASE() GROUP BY table_type
UNION ALL
SELECT routine_type, COUNT(*)
FROM information_schema.routines WHERE routine_schema = DATABASE() GROUP BY routine_type
UNION ALL
SELECT 'EVENT', COUNT(*)
FROM information_schema.events WHERE event_schema = DATABASE();

SHOW FULL TABLES;
```

第一条按类型计数：`BASE TABLE` 表、`VIEW` 视图、`PROCEDURE` 存储过程、`FUNCTION` 函数、`EVENT` 事件。本系统只有表（40 张 `sn_` 表加 `flyway_schema_history`）；`SHOW FULL TABLES` 里有别的表又不确定能不能删时停下，改用 8.1。

**第 5 步：删除所有表和视图**

```sql
SET SESSION group_concat_max_len = 1000000;
SET FOREIGN_KEY_CHECKS = 0;

SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP VIEW IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_type = 'VIEW';
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP TABLE IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_type = 'BASE TABLE';
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SET FOREIGN_KEY_CHECKS = 1;
```

先删视图、再删表。其他系统的表之间可能有外键，所以先关外键检查，删完再打开（只影响当前连接）。

**第 6 步：删除存储过程、函数、事件**（第 4 步里这三类都没有时跳过）

先生成删除语句：

```sql
SELECT CONCAT('DROP ', routine_type, ' IF EXISTS `', routine_name, '`;') AS drop_sql
FROM information_schema.routines WHERE routine_schema = DATABASE()
UNION ALL
SELECT CONCAT('DROP EVENT IF EXISTS `', event_name, '`;')
FROM information_schema.events WHERE event_schema = DATABASE();
```

把结果里的每一行（形如 ``DROP PROCEDURE IF EXISTS `xxx`;``）复制出来，在同一个连接里粘贴执行。执行前再看一眼 `SELECT DATABASE();`，这些语句不带库检查。

**第 7 步：确认已是空库**

```sql
SHOW FULL TABLES;
-- 应当返回 Empty set
SELECT COUNT(*) AS routines FROM information_schema.routines WHERE routine_schema = DATABASE();
-- 0
SELECT COUNT(*) AS events FROM information_schema.events WHERE event_schema = DATABASE();
-- 0
exit
```

**第 8 步：检查 `.env`**

空库启动时直接执行 `V1__init.sql`，**不读取** `DB_BASELINE_ON_MIGRATE`、`DB_BASELINE_VERSION`（`.env` 里留着也没关系）。`DB_NAME` 仍是这个库，不用改。

**第 9 步：启动并检查**，命令和检查 SQL 同 [8.1 第 8 步](#81-删除本系统的表并重建)。`flyway_schema_history` 应当只有 1 行 `1 | 1 | SQL | V1__init.sql | 1`，`sn_tables` 为 38，`sn_user` 里只有系统管理员。

**第 10 步：重新初始化数据**，同 [8.1 第 9 步](#81-删除本系统的表并重建)。

> 以后这个库里又放进了其他系统的表，再清本系统的表时就要按 8.1 做，并设 `DB_BASELINE_ON_MIGRATE=true`、`DB_BASELINE_VERSION=0`。

### 8.3 删除整库、重建并授权

用 `DROP DATABASE` 删掉整个库，再新建同名空库并给 `appuser` 授权；启动时程序按空库直接建表。比 8.2 更彻底：库里的所有对象一次删掉，字符集和排序规则按新建时设定。删库、建库、授权用 `root`（或有建库、删库和 `GRANT OPTION` 权限的账户）执行。

> **整个库连同其中所有系统的数据一起删除。** 先确认这个库只给本系统用。拿不准时用 [8.1](#81-删除本系统的表并重建)。

**第 1 步：停止服务**，命令同 [8.1 第 1 步](#81-删除本系统的表并重建)。库里还有别的系统在用时，也要先停掉它们。

**第 2 步：备份整个库**

```bash

```

要恢复时，先做完第 5、6 步（建库、授权），再执行 `mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"`。

**第 3 步：用 root 登录 MySQL，确认库、授权和连接**

```bash

```

```sql
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = 'sn_test';
```

- `SHOW DATABASES` 里要有 `sn_test`。系统库 `information_schema`、`mysql`、`performance_schema`、`sys` 和正式库 `sn_prod` 不能删；`sndb` 只剩授权、库已不存在（见第 1 节），不用删。
- 连接列表应当为空。还有连接说明服务没停干净：回到第 1 步，或对列出的连接执行 `KILL <id>;`。

**第 4 步：删库**

```sql
DROP DATABASE IF EXISTS sn_test;
```

**第 5 步：重建空库**

```sql
CREATE DATABASE sn_test CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**第 6 步：给 appuser 授权**

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES ON sn_test.* TO 'appuser'@'%';
```

- 这些是本系统要的权限（`ALTER` / `DROP` 用于按月加分区和归档痕迹分区）。按库授权不随删库消失，原有的 `ALL PRIVILEGES` 还在，再授一次也无妨，只会补上缺的。
- 新的 MySQL 实例上还没有 `appuser` 时，先建账户再授权，密码与 `.env` 的 `DB_PASSWORD` 一致：`CREATE USER 'appuser'@'%' IDENTIFIED BY '<密码>';`

**第 7 步：确认库和授权**

```sql
SHOW CREATE DATABASE sn_test;
-- 应含 utf8mb4 和 utf8mb4_0900_ai_ci
SHOW GRANTS FOR 'appuser'@'%';
-- 应有 sn_test 上的授权

```

再用 `appuser` 连一次，确认能连上、库是空的：


应显示 `sn_test` 和 `appuser@%`，且没有任何表。

**第 9 步：启动并检查**，命令和检查 SQL 同 [8.1 第 8 步](#81-删除本系统的表并重建)。`flyway_schema_history` 应当只有 1 行 `1 | 1 | SQL | V1__init.sql | 1`，`sn_tables` 为 38，`sn_user` 里只有系统管理员。

**第 10 步：重新初始化数据**，同 [8.1 第 9 步](#81-删除本系统的表并重建)。

**只删库、不再使用**（例如废弃的测试库，或本机自动化测试留下的 `sndb_test_py`）：做完第 1–4 步即可，不做第 5 步以后的步骤；`.env` 的 `DB_NAME` 不能再指向这个库。想把残留授权也清掉时，用 root 执行（权限名照 `SHOW GRANTS` 显示的写，显示 `ALL PRIVILEGES` 就写 `ALL PRIVILEGES`）：

### 8.4 只重建 SN 导入表

SN 导入模板改版（加了行号、流水号、进制位数等列）后，已建好的库只需按新结构重建 **`sn_import_item` 这一张表**，号池等其他表、已联调的数据都不动。建表脚本 V1 改过后，已建好的库启动时只在日志里记一条 `migration_checksum_mismatch` 警告，不会重跑 V1，所以要手动重建这张表。

**现象**：更新代码后打开 SN 导入页报错，`docker compose logs api` 里 `/api/sn-import/items` 返回 500，日志有 `db_error` 和 `Unknown column 's.bill_seq' in 'field list'`（或别的 `s.` 开头的列）。

**前提**：

- 号池里没有导入的号（`sn_item.origin = 'IMPORT'` 为 0 枚）。下面的工具会先查，有就不重建、直接退出。号池里已有导入的号时，先在 SN 导入页「整单删除」（须全部待分配）；已交付给 MES 的，须与 MES 方一起处理后再重建。
- 只有导入表落后于 V1。下面第 2 步会检查；其他表也旧时不能只重建导入表，按 8.1–8.3 重建（要保留账户时按 [8.7](#87-保留账户按-v1-重建其他表)）。
- 重建后导入表是空表：原有的导入记录一并删除。

工具 `devtools.rebuild_import_table` 读与服务相同的 `.env`（`DB_*`），**在 Web 服务器上执行即可，不用登录 MySQL**；Web 服务器与数据库服务器不在同一台机器时也一样。开发、测试、正式各库各执行一次（`.env` 指向哪个库就处理哪个库）。

**方式 A：Docker 部署**（在 Web 服务器的部署目录执行）

镜像里只有 `app`，没有 `devtools`，运行时把仓库里的 `devtools` 目录只读挂进容器；代码要已是最新（`git pull` 并 `docker compose up -d --build` 过）。

第 1 步：进入部署目录

```bash
cd ~/sn-center
```

第 2 步：检查哪些表落后于 V1（只读）

```bash
docker compose run --rm -T api python - <<'EOF'

from app.db.session import db
db.configure(settings.db_target(), 1)
s = "table_schema = DATABASE()"
print("库名 =", db.scalar("SELECT DATABASE()"))
print("sn_item.origin 列（应为 1）=", db.count(f"SELECT COUNT(*) FROM information_schema.columns WHERE {s} AND table_name='sn_item' AND column_name='origin'"))
print("sn_item_deleted 表（应为 1）=", db.count(f"SELECT COUNT(*) FROM information_schema.tables WHERE {s} AND table_name='sn_item_deleted'"))
print("sn_rule_version.ix_rule_prefix（应为 1）=", db.count(f"SELECT COUNT(DISTINCT index_name) FROM information_schema.statistics WHERE {s} AND table_name='sn_rule_version' AND index_name='ix_rule_prefix'"))

EOF
```

| 结果 | 处理 |
| --- | --- |
| 前三项为 1，最后一项为 0 | 只有导入表是旧结构，继续第 3 步 |
| 四项都为 1 | 导入表已是新结构，不用重建；SN 导入页仍报错时看日志里缺的是哪一列 |
| 前三项有 0 | 号池、删号存档或规则版本也落后于 V1，不能只重建导入表，按 8.1–8.3 重建 |

前三项对应 V1 在 11-02、11-03 的改动（规则前缀改为非唯一索引、新增删号存档表、号池新增 `origin` 列），最后一项对应 11-05 的导入模板改版。

第 3 步：试运行（只检查，不改）


输出「检查通过」才继续；输出「号池里还有导入的号，不能重建」时，按上面的前提处理后再从第 3 步重来。



输出「已按 V1 重建 sn_import_item（空表）」即完成。

**方式 B：本机启动 / 开发**（在仓库根目录执行）

先停服务（`python start.py --stop`，或在 uvicorn 窗口按 Ctrl+C），再执行：

### 8.5 保留账户、清空其他数据

测试阶段已在「账户」页配好了账户和授权，又要从干净的业务数据重新测试时用这一节：**只保留账户、生产组织（含 MES 对接配置）与金蝶连接**，其余数据全部清空。表结构不动、不重新建表，MES 接口账户的密钥不变，不用重新交给 MES 方。

- 只用于 `sn_dev`、`sn_test`；**正式库 `sn_prod` 不做**。
- 只清数据、不改表结构。`V1__init.sql` 改过表结构时不能用这一节：账户表没改、要保留账户时按 [8.7](#87-保留账户按-v1-重建其他表)，否则按 8.1–8.3 重建。
- 只能从备份恢复，先做第 2 步的备份。

**保留与清空**

| 处理 | 表 | 说明 |
| --- | --- | --- |
| 保留 | `sn_user`、`sn_user_factory` | 页面账户（系统管理员、普通操作员、审计员）、MES 接口账户（密钥、来源地址白名单）、授权的生产组织 |
| 保留 | `sn_factory` | 生产组织与 MES 对接配置（地址、认证方式与凭证、批次大小、超时、并发、时区、连接测试结果）。账户的授权组织、MES 接口账户都按组织编码挂在这里，不能清 |
| 保留 | `sn_k3_config` | 生产订单页「金蝶连接」保存的参数（应用密钥加密）；没在页面保存过时为空表 |

| 重置 | `sn_sync_state` | 清掉后补回建表时的 `id = 1` 一行（订单同步状态只更新这一行） |

```sql
DROP PROCEDURE IF EXISTS sn_clear_keep_accounts;
DELIMITER //
CREATE PROCEDURE sn_clear_keep_accounts()
BEGIN
  DECLARE done INT DEFAULT 0;
  DECLARE t VARCHAR(64);
  DECLARE cur CURSOR FOR
    SELECT table_name FROM information_schema.tables
    WHERE table_schema = DATABASE() AND table_type = 'BASE TABLE' AND table_name LIKE 'sn\_%'
      AND table_name NOT IN ('sn_user', 'sn_user_factory', 'sn_factory', 'sn_k3_config', 'sn_seq', 'sn_sync_state');
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;
  IF IFNULL(DATABASE(), '') NOT IN ('sn_dev', 'sn_test') THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'REFUSED: current database is not sn_dev / sn_test';
  END IF;
  OPEN cur;
  clear_loop: LOOP
    FETCH cur INTO t;
    IF done THEN LEAVE clear_loop; END IF;
    SET @clear_sql = CONCAT('TRUNCATE TABLE `', t, '`');
    PREPARE stmt FROM @clear_sql;
    EXECUTE stmt;
    DEALLOCATE PREPARE stmt;
  END LOOP;
  CLOSE cur;
  DELETE FROM sn_seq WHERE name NOT REGEXP '^(PS|PL|XO)-';
  DELETE FROM sn_sync_state;
  INSERT INTO sn_sync_state (id) VALUES (1);
END //
DELIMITER ;
CALL sn_clear_keep_accounts();
DROP PROCEDURE sn_clear_keep_accounts;
```

- 用一个临时存储过程清空：先检查当前库，不是 `sn_dev` / `sn_test` 时报 `REFUSED: current database is not sn_dev / sn_test`，什么也不清；清空的表按库里实际的 `sn_` 表列出，以后新增业务表不用改这段 SQL；最后删掉这个存储过程。
- 被拒绝时，执行 `DROP PROCEDURE IF EXISTS sn_clear_keep_accounts;` 删掉留下的存储过程，再回第 3 步。
- `DELIMITER` 是 `mysql` 命令行的写法。Navicat 在查询窗口可直接执行；DBeaver 要选中整段用「执行脚本」（Alt + X）。

### 8.6 金蝶连接（页面配置）

金蝶 K3 Cloud 的连接参数可以由系统管理员在页面上维护，不用改 `.env`、不用重启：**生产订单** 页右上角 **金蝶连接**（只有系统管理员看得到这个按钮）。

**参数来源**

| 情况 | 生效的参数 |
| --- | --- |
| 从没在页面保存过（`sn_k3_config` 为空表） | `.env` 的 `K3_*`；页面上带出这些值（应用密钥不回显），来源显示「.env 文件」 |
| 页面保存过 | 页面保存的参数，`.env` 的 `K3_*` 不再使用；来源显示「页面配置」。页面参数失效（金蝶登录失败、密钥解不开）时**不会自动改用 `.env`**，同步报错、旧快照保留，由系统管理员改好参数或「恢复默认」 |

页面可改：服务地址、账套 ID（数据中心 ID）、应用 ID、应用密钥、集成用户、语言；「高级参数」里是登录 / 查询 / 单据查看超时和分页失败重试，对应 `.env` 的 `K3_LOGIN_TIMEOUT` 等，一般不用改。

**规则**

- **保存前先测试**：点「保存」时后端先用新参数登录金蝶并读组织机构，通过才保存；不通过报 `K3_TEST_FAILED`，原参数不变。「连接测试」按钮只测试、不保存。
- **立即生效**：每次调用金蝶（定时比对同步、按单据同步、全量重建、从金蝶同步生产组织）都读当前参数，保存后下一次调用即用新参数。多实例共用同一个库，也都立即生效。
- **应用密钥**：与 MES 凭证一样用 `SN_SECRET` 派生的密钥加密存库，页面不回显、不写进日志和操作痕迹；留空 = 沿用当前的密钥。更换 `SN_SECRET` 后已存的密钥解不开，调用金蝶报 `K3_SECRET_UNREADABLE`，在「金蝶连接」重新填写应用密钥保存即可。
- **留痕**：连接测试记 `K3_CONFIG_TEST`（金蝶连接测试），保存记 `K3_CONFIG`（修改金蝶连接，含改了哪些项）；应用密钥只记是否更换。抽屉底部显示最近 5 次修改，完整记录在「操作日志」按动作筛选。
- **不影响 MES**：只改本系统读取金蝶的参数，MES 推送、拉取、回执接口与「生产组织」页的 MES 对接配置都不变。

**升级到带这个功能的版本**：`sn_k3_config` 在 V1 里，按当前 V1 建的库已有这张表。库里没有这张表（按旧版 V1 建的）时启动报错、不补建，测试库按 [8.7](#87-保留账户按-v1-重建其他表) 保留账户、按 V1 重建其他表（`sn_k3_config` 按 V1 新建）；新建后是空表，仍按 `.env` 连接。

**恢复默认（回到 `.env`）**：「金蝶连接」左下角 **恢复默认**（只在来源为「页面配置」时可点）。确认框列出将改用的 `.env` 参数（应用密钥只显示是否已填）；系统先用这些参数登录金蝶并读组织机构，通过才删掉页面保存的参数，下一次调用金蝶起按 `.env` 的 `K3_*`，不用重启；不通过报 `K3_RESET_FAILED`，页面参数原样保留。恢复默认记痕迹 `K3_CONFIG`（修改记录显示「恢复默认（改用 .env）」）。

不自动切换的原因：`.env` 里可能是旧地址或别的账套，连错账套时比对同步会把快照里查不到的单据当作已删除、产生提醒并暂停交付。

页面打不开时也可以直接删库里的页面参数（不做连接测试、不留痕，只在应急时用）：

```sql
DELETE FROM sn_k3_config;
```

### 8.7 保留账户、按 V1 重建其他表

测试阶段 `V1__init.sql` 改过表结构（账户表没改），已建好的库启动时只记 `migration_checksum_mismatch`、不会重跑 V1，业务表还是旧结构；又不想重建账户（MES 接口账户的密钥已交给 MES 方、联调已通过）时用这一节。与 8.5 的区别：8.5 只清数据、不改表结构；这一节**删表并按当前 V1 重建**。

- 只用于 `sn_dev`、`sn_test`；**正式库 `sn_prod` 不做**（库名含 `prod` 工具一律拒绝；库名不是 `sn_dev` / `sn_test` 时要加 `--allow-db <库名>`）。
- 只改本系统的库表，**MES 接口、推送 / 拉取报文都不变**，MES 方不用改程序。
- 删表不能回滚，只能从备份恢复，先做第 2 步的备份。

**保留与重建**

| 处理 | 表 | 说明 |
| --- | --- | --- |
| 保留 | `sn_user`、`sn_user_factory` | 页面账户、MES 接口账户（密钥、来源地址白名单、令牌版本）、授权的生产组织。MES 方已拿到的密钥继续可用 |
| 保留 | `sn_factory` | 生产组织与 MES 对接配置（地址、凭证、连接测试结果）。账户的授权组织、MES 接口账户都按组织编码挂在这里 |
| 保留 | `sn_k3_config` | 生产订单页「金蝶连接」保存的参数；库里还没有这张表时按 V1 新建 |
| 保留并更新 | `flyway_schema_history` | 只把 V1 的校验和改成当前脚本的，之后启动不再报 `migration_checksum_mismatch` |
| 重建后写回 | `sn_seq` | 批次号的当天序号（`PS-` / `PL-` / `XO-` 开头的行）写回，其余清掉。否则同一天再建批会与 MES 已收过的批次号重复 |
| 删除后按 V1 重建（空表） | 其他所有 V1 里的 `sn_` 表 | 规则、订单快照与补填、出号台账、生成、号池、删号存档、导入、交付、转移、操作痕迹、计数；`sn_sync_state` 按 V1 补回 `id = 1` 一行；`sn_audit` 只有兜底分区，启动时自动建月分区 |
| 删除 | V1 已没有的 `sn_` 旧表 | 例如 `sn_batch`、`sn_print` |
| 不动 | 不是 `sn_` 开头的表 | 其他系统的表、视图 |

**保留的表先与 V1 比对结构**（字段名与顺序、类型、可空、默认值、排序规则、索引；注释不比），有一张不一致就**不执行**、列出差异：

- `sn_factory` 或 `sn_k3_config` 不一致：加 `--keep sn_user,sn_user_factory`（只保留账户，组织与金蝶连接也按 V1 重建，之后重新同步生产组织、重填 MES 对接配置并连接测试、重存金蝶连接；账户的授权组织按组织编码对应，同步回来后仍然有效）。
- `sn_user` 或 `sn_user_factory` 不一致：账户表也改过，不能用这一节，按 8.1 整体重建。

> **与 MES 方的数据**：同 8.5，号池和批次清空后，MES 那边联调时收到的号、批次还在。之后用同样的前缀重新生成，号会从流水 1 开始，与 MES 已收过的号重复。执行前与 MES 方约定：MES 方同步清掉测试数据，或本系统之后一律用**新前缀**。

工具 `devtools.rebuild_keep_accounts` 读与服务相同的 `.env`（`DB_*`），**在 Web 服务器上执行即可，不用登录 MySQL**。`.env` 指向哪个库就处理哪个库，开发、测试库各执行一次。

第 4 步：执行

```bash
docker compose run --rm -T -v "$PWD/devtools:/app/devtools:ro" api python -m devtools.rebuild_keep_accounts --yes
```

输出「已完成：保留 …；重建 N 张表；sn_seq 写回 N 行」即完成。提示「库里还有 N 个其他连接 … 未执行」时什么也没改，断开列出的连接后重新执行。中途报错（网络断开等）时修好原因再执行一次：缺的表照常补建；`sn_seq` 已删时序号写不回，从第 2 步的备份里查出 `PS-` / `PL-` / `XO-` 开头的行手工补回。

第 5 步：启动并检查

```bash
docker compose start api
docker compose logs --tail=100 api | grep -E "migration|bootstrap_admin|partition_added|sn_center_ready"
```

应有 `partition_added`、`sn_center_ready`；**不应有** `migration_checksum_mismatch`（校验和已更新）和 `bootstrap_admin`（账户还在，不会新建管理员）。再执行一次第 1 步，保留的表结构一致，`flyway_schema_history` 显示「已一致」。

第 6 步：重新准备业务数据（同 8.5 第 8 步）

1. 用原来的账户登录，确认授权组织、MES 对接配置与「对接 MES」开关、金蝶连接都在（用 `--keep sn_user,sn_user_factory` 时先同步生产组织、重填 MES 对接配置并连接测试）。
2. 「生产订单」页 **全量重建** 一次快照。
3. 「规则库」重新建规则；按与 MES 方的约定用新前缀，或确认 MES 方已清掉测试数据。
4. 选一张 PI 走一遍 生成 → 分配 → 推送 / 拉取 → 回执确认。

**方式 B：本机启动 / 开发**（在仓库根目录执行）

先停服务（`python start.py --stop`，或在 uvicorn 窗口按 Ctrl+C），备份后执行：

```bash
uv run python -m devtools.rebuild_keep_accounts          # 只检查，列出会做什么
uv run python -m devtools.rebuild_keep_accounts --yes    # 检查通过后执行
```

完成后重新启动服务，按方式 A 第 5、6 步检查。

### 8.8 单据汇总对账与重建

SN 分配页左侧单据列表、SN 导出页单据列表查单据汇总 `sn_bill_stat`（每个 PI + 单据 + 号上的生产组织一行），不再对整个号池汇总，耗时只与单据数有关、不随累计枚数增长。
号变动时程序自动标脏（`sn_bill_stat_dirty`）并按单据重算：列表打开前先算完（最多 3 秒），后台每 2 秒也算一次；每日维护抽查最近 2000 张单据对账。**平时不用管。**

下面几种情况手动对账或重建（只读号池、不锁号池，服务不用停；MES 接口不受影响）：

- 日志出现 `bill_stat_mismatch`（对账发现不一致，已自动重算），想全面核对一遍；
- 直接在库里改过、删过号池 `sn_item`（没走程序），或从备份单独恢复过号池。

```bash
uv run python -m devtools.rebuild_bill_stat              # 抽查最近 2000 张单据对账
uv run python -m devtools.rebuild_bill_stat --all        # 全部单据对账，含号池里有、汇总里缺的
uv run python -m devtools.rebuild_bill_stat --rebuild    # 按号池整表重建
```

Docker 部署：镜像里只有 `app`，把仓库的 `devtools` 只读挂进容器执行（与 8.4、8.7 相同，镜像要已是最新）：

```bash
docker compose run --rm -T -v "$PWD/devtools:/app/devtools:ro" api python -m devtools.rebuild_bill_stat --all
```

## 9. 常见问题

| 现象 | 处理 |
| --- | --- |
| 构建报 `failed size validation` 或 `failed to resolve source metadata` | 见 [4.4 基础镜像拉取失败](#44-基础镜像拉取失败) |
| `web` 构建报 `Exit handler never called!`，停在 `npm ci` | 见 [4.5 前端依赖安装失败](#45-前端依赖安装失败)。在 `.env` 设置 `NPM_REGISTRY=https://registry.npmmirror.com` 后重新 `docker compose up -d --build` |
| 启动报 `Can't connect to MySQL server` | 检查 `DB_HOST` / `DB_PORT`、防火墙、账户密码 |
| 调用金蝶报 `K3_SECRET_UNREADABLE` | `SN_SECRET` 换过，页面保存的金蝶应用密钥解不开。系统管理员在生产订单页「金蝶连接」重新填写应用密钥并保存（见 [8.6](#86-金蝶连接页面配置)） |
| 「金蝶连接」恢复默认报 `K3_RESET_FAILED` | `.env` 的 `K3_*` 连不上金蝶（或没填全），页面参数未变。先改好服务器上的 `.env` 并重启服务，再恢复默认；或继续在页面上维护参数 |
| 「金蝶连接」保存报 `K3_TEST_FAILED` | 用新参数登录金蝶或读组织机构失败，原参数未变。按提示核对服务地址、账套 ID、应用 ID / 密钥、集成用户，或检查本机到金蝶服务器的网络 |
| 启动报「已有表但没有 flyway_schema_history」 | 库里已有其他表。本系统表尚未建立时设 `DB_BASELINE_ON_MIGRATE=true`、`DB_BASELINE_VERSION=0`。表已与 V1 一致、只缺迁移记录时版本设为 `1`。见上文「基线版本」 |
| 升级后报表或列不存在（如 `sn_delivery_batch`、`sn_line_count`、`sn_rule.factory_code`、生产订单快照的 `sn_prd_mo.dept_name`），日志有 `migration_checksum_mismatch` | `V1__init.sql` 已按 PRD V31 重写，旧库不会重跑 V1，也没有就地升级脚本。按 [8.1 删除本系统的表并重建](#81-删除本系统的表并重建) 删掉 `sn_` 表与 `flyway_schema_history`，或按 [8.2 清空整库并重建](#82-清空整库并重建) / [8.3 删除整库、重建并授权](#83-删除整库重建并授权) 得到空库后重新启动 |
| SN 导入页报错，日志有 `Unknown column 's.bill_seq' in 'field list'`（`/api/sn-import/items` 返回 500）、`migration_checksum_mismatch` | 导入表还是改版前的结构。在 Web 服务器上按 [8.4 只重建 SN 导入表](#84-只重建-sn-导入表) 检查并重建这一张表（不用登录 MySQL） |
| 同步报 `金蝶配置缺失` | `.env` 中 `K3_*` 未填 |
| 比对同步显示失败 | 「生产订单」页统计栏看最近一次比对同步的原因（与手动同步的报错相同）；快照未改动，修好后等下个周期或点「立即比对同步」 |
| 订单页附件项次、米数、PO 一直为空 | 系统按固定字段读取：附件项次 `FTERM`、长度 `Flength`（明细）、PO `F_HX_PO`（表头），见 [生产订单查询接口](k3/k3cloud_query.md)。先在金蝶里确认这张单这几个字段确有值；有值仍为空时向金蝶实施方确认字段标识是否变了（改字段名须改代码 `app/services/k3.py`）。附件项次金蝶确实没有时在生成页填写（米数可不填，默认 000） |
| 生成页附件项次、米数输入框置灰 | 该物料行已经生成过号。在生成页勾选这一行，底部「更多 ▾」→「删号」删掉该行的号（号的状态不限，已分配、已推送的也可删；最大流水号不退回，删掉的流水留作空号段）后再改，改完重新生成 |
| 首页「推送中断」有数字 | 某批次自动重试（没送达默认 1、5、15 分钟；已收到没回执默认等 1、5、10、10 分钟并重推 3 次）用尽仍未确认。到「SN 查询 → 交付批次」看失败原因（地址错、认证失败、超时、报文过大、整批拒收、等待 MES 回执超时等），处理后在 SN 分配页或批次详情点「继续推送」：先用原批次号、原内容重推，再推后续的号。MES 方确认已全部入库的可「人工确认」（原因、依据必填）；MES 没处理过的批次可「作废」 |
| 批次失败原因为「应答无效」（`RESPONSE_INVALID`）或「应答不符」（`RESPONSE_MISMATCH`） | 推送时 MES 的应答不是「已收到」（`code` 不是 `OK`，如在应答里直接回 `NG`），或应答的批次号不是这一批，失败原因里写明收到的内容。请 MES 方改为收到即应答 `OK`（已收到）、落库后调 ③ 回执；已处理的批次用同一批次号补交回执（③）即成功。这种批次 MES 可能已处理，不能作废 |
| 分配页推送停在「等待回执」 | MES 已收到这一批，但还没调 ③ 回执；回执到了才推下一批。等待超过 1、5、10 分钟会按原批次自动重推，共 3 次后推送中断。请 MES 方检查回执接口（MES 接口账户、本系统地址、来源 IP 白名单）；MES 方确认已全部入库但回执交不上来时可「人工确认」 |
| MES 取批返回 429 `RATE_LIMITED` | 该组织每分钟取批超过 `SN_MES_PULL_RATE_PER_MINUTE`（默认 60）次。请 MES 方按 `Retry-After` 等待、`remaining = 0` 时停止轮询；确需更高频率时调大该值 |
| MES 调用返回 423 `ACCOUNT_LOCKED` / 403 `IP_NOT_ALLOWED` | 连续认证失败被锁定，等 `SN_MES_AUTH_LOCK_MINUTES` 分钟后自动解锁，或核对密钥（必要时重置密钥）；来源地址不在白名单时在「账户」页修改白名单 |
| 关闭「对接 MES」被拒（`MES_DISABLE_BLOCKED`） | 该组织还有运行中的推送任务或未确认 / 失败的批次：先续推、等待回执，或人工确认 / 作废后再关闭 |
| 换了 `SN_SECRET` 后推送全部认证失败 | 已存的 MES 凭证用旧密钥加密，无法解密：在「生产组织」页逐个重新填写凭证并连接测试 |
| 同步报 `金蝶登录失败` | 账套 / AppId / AppSecret / 用户名不对，或服务器到 `10.0.200.42` 不通 |
| 生成、分配提示生产组织不存在或已禁用 | 「生产组织」页从金蝶同步（生产组织只来自金蝶，不能手工新增）；金蝶里已禁用的组织不能作为分配、转入目标 |
| 生成提示「预演失效」 | 期间有人生成过同一 PI，或数量 / 规则 / 订单变了：重新预演 |
| 生成提示「正在生成，请稍后再试」 | 同一 PI 已有生成任务在跑，等它结束（首页或生成页可见进度）。若是服务在后台生成途中重启过，重启后该任务会自动标为失败（`INTERRUPTED`，号已整批回滚），重新预演后生成即可 |
| 启动报「SN_SECRET 未设置 / 仍是示例值 / 长度不足 32 位」 | `ENVIRONMENT=production`（Docker 方式默认如此）时要求强密钥：在 `.env` 设置 `SN_SECRET`，可用 `python -c "import secrets; print(secrets.token_hex(32))"` 生成；更换后所有人需重新登录 |
| 请求返回「参数不合法」（422 `VALIDATION`） | 参数格式不对，或 PI、SN、生产组织、客户、物料等编码超过 64 位；修正后再提交，重试无效 |
| 多个账户同时生成、分配时提示「数据正被其他操作占用，请稍后重试」（`CONFLICT_RETRY`），日志有 `db_pool_exhausted` 或 MySQL 1040 `Too many connections` | 连接不够：按 [第 2 节「并发与连接数」](#2-配置-env) 核对各实例 `DB_POOL_SIZE` 合计与 MySQL `max_connections`。只有 `gen_deadlock_retry` 没有失败的属正常（已自动重做） |
| 提示「PI 正在进行其他操作」（`PI_BUSY`） | 同一 PI 的生成、撤销、分配、转单、转组织确认同一时刻只能做一个，等前一个结束再试 |
| 忘记系统管理员密码 | 其他管理员不能重置系统管理员。在服务器上以 `SN_RESET_ADMIN=true` 启动一次：工号 `SN_INIT_ADMIN_EMP_NO` 被重置为 `SN_INIT_ADMIN_PASSWORD`、启用并改回管理员（不存在则新建，留痕）；**随后立即去掉该变量再重启** |

## 10. 扩容与迁移

何时做、对 MES 有什么影响，见《[容量、性能与扩展评估报告](容量性能与扩展评估报告.md)》第 6 章；本章只写操作步骤，命令中的 `<...>` 按实际环境替换。

**每次迁移都要做到的三点：**

1. **应用密钥（`SN_SECRET`）原样保留**：推送给 MES 的凭证用它加密保存。换了以后推送会认证失败，所有人也要重新登录。
2. **所有后端进程一起停、一起切**：生成号时靠数据库锁防止重复。如果新旧两个库同时在用，可能产生重复 SN。
3. **字符集和排序规则不变**：SN 区分大小写，靠的是表上的 `utf8mb4_bin`。

### 10.1 上线前：正式库搬到独立实例

正式库还没有业务数据，迁移很简单。如果 `sn_prod` 里还没有准备任何数据（账户、生产组织、规则等），直接跳过第 2 步：后端启动时会自动建表。

1. **新实例准备**：
   - MySQL 版本与现在相同（8.0）；
   - 参数按《容量、性能与扩展评估报告》4.2 设置；
   - 建库和账户：

   ```sql
   CREATE DATABASE sn_prod CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   CREATE USER 'appuser'@'%' IDENTIFIED BY '<口令>';
   GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES ON sn_prod.* TO 'appuser'@'%';
   ```

2. **停后端，导出再导入**：

   ```bash
   docker compose stop api
   mysqldump -h 10.0.200.125 -u root -p --single-transaction --set-gtid-purged=OFF sn_prod > sn_prod.sql
   mysql -h <新库地址> -u root -p sn_prod < sn_prod.sql
   ```

3. **核对**：抽查几张表的行数，与旧库一致；迁移记录完整，且全部成功。

   ```sql
   SELECT COUNT(*) FROM sn_user;
   SELECT COUNT(*) FROM sn_factory;
   SELECT COUNT(*) FROM sn_rule;
   SELECT version, success FROM flyway_schema_history ORDER BY installed_rank;
   ```

4. **切换**：把 `.env` 的 `DB_HOST` 改为新库地址，然后启动后端：

   ```bash
   docker compose up -d --force-recreate api
   curl -fsS http://localhost/health/ready
   ```

5. **回退**：把 `DB_HOST` 改回旧库地址，重启后端即可。

### 10.2 加内存、扩盘

在超融合上调整虚拟机配置，不用换机器。

**加内存：**

1. 停后端：`docker compose stop api`。
2. 在平台上给数据库虚拟机加内存。如果平台支持热添加，就不用关机。
3. 调大缓冲池，取内存的 60–70%。下面的语句立即生效，并写入配置，重启后仍有效：

   ```sql
   SET PERSIST innodb_buffer_pool_size = 22 * 1024 * 1024 * 1024;   -- 32 GB 内存时
   ```

4. 启动后端：`docker compose start api`。

**扩盘（不停机）：**

1. 在平台上扩大虚拟盘。
2. 在数据库服务器上依次执行。执行前先用 `lsblk` 确认 LVM 所在的分区，下面以 `vda3` 为例：

   ```bash
   sudo growpart /dev/vda 3
   sudo pvresize /dev/vda3
   sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
   df -h /
   ```

### 10.3 改表结构

**机制**：后端启动时，按版本号执行 `app/db/migration/V{n}__说明.sql`，执行过的会记入 `flyway_schema_history`，下次启动跳过。上线后：

- 不改已执行过的脚本，每次改动新增一个脚本（V2、V3……）；
- 每个脚本只放一条改表语句。MySQL 的改表语句不能回滚，脚本执行到一半失败时，前面的语句已经生效，下次启动重跑会报错。

**按表的大小分两种做法：**

| 情况 | 做法 |
| --- | --- |
| 新表、小表 | 写进 V{n} 脚本，发版启动时自动执行，几秒完成 |
| 号池、交付记录这类大表 | 不随启动执行。启动会被卡住几十分钟到几小时；多进程时，其他进程等锁 120 秒就报错退出。改由 DBA 先在线执行，见下面的步骤 |

**大表的步骤**（以加索引为例）：

1. **DBA 在线执行**：新索引、可空的新字段对旧代码没有影响，可以在旧版本运行时执行。要避开大批量生成的时段：生成是长事务，会让改表在最后一步等锁。

   ```sql
   SET SESSION lock_wait_timeout = 10;
   ALTER TABLE sn_item ADD KEY ix_item_holder_org (mes_holder, factory_code), ALGORITHM=INPLACE, LOCK=NONE;
   ```

2. **补登记迁移记录**：同样的语句写成 `V2__add_holder_index.sql` 放进代码。DBA 执行完后补登记一行，新版本启动时就会跳过它。先查出校验和：

   ```bash
   docker compose exec api python -c "from app.db.migrate import migrations; [print(m.version, m.description, m.script, m.checksum()) for m in migrations()]"
   ```

   ```sql
   INSERT INTO flyway_schema_history (installed_rank, version, description, type, script, checksum, installed_by, execution_time, success)
   SELECT MAX(installed_rank) + 1, '2', 'add holder index', 'SQL', 'V2__add_holder_index.sql', <校验和>, CURRENT_USER(), 0, 1
   FROM flyway_schema_history;
   ```

3. **发布新版本**。
4. **需要重建表的改动**（改字段类型、删字段等）：用 gh-ost 或 pt-online-schema-change 在线执行，之后同样按第 2 步补登记。

无论哪种改动，都先在一份与正式库同样大小的副本上演练，记下耗时和临时空间。

### 10.4 换数据库服务器（已有大量数据时）

数据多时，用物理备份加主从复制，停机只有切换的几分钟。

1. **旧库建复制账户**，并确认已开启 binlog（MySQL 8.0 默认开启）：

   ```sql
   CREATE USER 'repl'@'<新库地址>' IDENTIFIED BY '<口令>';
   GRANT REPLICATION SLAVE ON *.* TO 'repl'@'<新库地址>';
   ```

2. **旧库做物理备份**（不停服务），拷到新库恢复。新库的 MySQL 要先停止，数据目录为空：

   ```bash
   # 旧库
   xtrabackup --backup --user=root --password=<口令> --target-dir=/backup/full
   xtrabackup --prepare --target-dir=/backup/full
   # 把 /backup/full 拷到新库后，在新库执行
   xtrabackup --copy-back --target-dir=/backup/full
   sudo chown -R mysql:mysql /var/lib/mysql && sudo systemctl start mysql
   cat /backup/full/xtrabackup_binlog_info      # 记下 binlog 文件名和位置
   ```

3. **新库作为从库追平旧库**：

   ```sql
   CHANGE REPLICATION SOURCE TO SOURCE_HOST = '<旧库地址>', SOURCE_USER = 'repl', SOURCE_PASSWORD = '<口令>',
     SOURCE_LOG_FILE = '<文件名>', SOURCE_LOG_POS = <位置>;
   START REPLICA;
   SHOW REPLICA STATUS\G      -- Seconds_Behind_Source 为 0 即已追平
   ```

4. **切换**（几分钟）：
   1. 停后端：`docker compose stop api`。
   2. 旧库设为只读：`SET GLOBAL super_read_only = ON;`。
   3. 确认追平：新库 `SHOW REPLICA STATUS` 的执行位置，与旧库 `SHOW MASTER STATUS` 的位置一致。
   4. 新库断开复制：`STOP REPLICA; RESET REPLICA ALL;`。
   5. 改 `.env` 的 `DB_HOST`，执行 `docker compose up -d --force-recreate api`，再用 `curl -fsS http://localhost/health/ready` 确认正常。
   6. 选一张 PI 走一遍生成、分配、交付。
5. **回退**：
   - 切换后还没有新数据时：旧库执行 `SET GLOBAL super_read_only = OFF;`，把 `DB_HOST` 改回即可。
   - 已经产生了新数据：要先把新库的数据同步回旧库。所以要先用试产确认无误，再开放给业务使用。

### 10.5 换应用服务器

1. 新服务器安装 Docker，拉取代码，把旧服务器的 `.env` 原样拷过去。
2. 执行 `docker compose up -d --build`，用 `curl -fsS http://localhost/health/ready` 确认正常。
3. 停旧服务器的后端，把域名解析或入口指向新服务器。
4. 如果 MES 侧按来源 IP 放行推送，要提前加上新服务器的 IP。
5. 旧容器删除前，先导出日志。

### 10.6 冷热分离

**是什么**：把已经交付完、长期不再变动的 PI（冷数据）移到归档表，号池只留还在使用的号（热数据），这样常用数据始终装得进内存。

**前提**：已与业务确认归档政策（见《容量、性能与扩展评估报告》6.2）。需求文档写的是「SN 不归档」。这是一项开发工作，需要改生成、导入、删号和各个查询，MES 接口不变。

**目标结构**（与评估报告 6.2 相同）：

| 表 | 内容 |
| --- | --- |
| SN 登记表 `sn_registry`（新） | 只有 SN 一列，作为主键，保证全局不重复；10 年约 20 GB，永久在线 |
| 号池 `sn_item`（现有，作热表） | 还在交付中的号，以及尚未归档的 PI |
| 冷表 `sn_item_archive`、`sn_delivery_item_archive`（新） | 已归档 PI 的号和交付记录，按归档月份分区 |

**步骤（顺序不能颠倒）**：

1. **建表**：用 V{n} 脚本建上面的新表。
2. **发版：写号时同时登记**：生成、导入在同一事务里写登记表，删号时同时删除登记。
3. **回填登记表**：把已有的 SN 补进登记表。按 id 分段，每段 1 万行，循环到最大 id，不锁号池：

   ```sql
   INSERT IGNORE INTO sn_registry (sn) SELECT sn FROM sn_item WHERE id BETWEEN <起> AND <止>;
   ```

4. **核对**：同样按 id 分段执行，结果必须全部为 0。在这一步通过之前，**不得开始归档**：号离开号池后，只有登记表能保证它不重复。

   ```sql
   SELECT COUNT(*) FROM sn_item i LEFT JOIN sn_registry r ON r.sn = i.sn
   WHERE i.id BETWEEN <起> AND <止> AND r.sn IS NULL;
   ```

5. **发版：查询合并冷热两表**：先查热表，再查冷表，结果标「已归档」。MES 查询已下发 SN 时，两表结果合并返回，内容和翻页方式不变。
6. **开始归档**：
   - 每天定时、限量，避开每日维护的时段；
   - 归档条件：PI 的号全部已交付；没有未确认或失败的批次；没有进行中的转移或订单变更；6 个月没有变动；
   - 保留期限：冷数据在线 3 年、总共 5 年，超过的按年导出备份后删除（届时再与业务确认）；
   - 按整张 PI 归档，在该 PI 的操作锁内，每批一个事务：把号和交付记录复制到冷表，再从热表删除。
7. **恢复**：已归档的 PI 需要再生成、转移、删号时，先把整张 PI 搬回热表，再操作。

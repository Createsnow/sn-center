## 1. 准备 MySQL

公司 MySQL：`10.0.200.125:3306`，账户 `appuser`。应用首次启动时自动执行建表脚本（`app/db/migration/V*.sql`，按 Flyway 格式记录在 `flyway_schema_history`），**不需要手工执行 SQL**。

连库、备份、删表、删库都以 `SHOW DATABASES` 为准。`SHOW GRANTS` 里多出来的名字只是授权，不代表库还在。2026-10-09 在这台实例上核对：

```sql
SHOW DATABASES;
SHOW GRANTS FOR 'appuser'@'%';
```

| 来源 | 名字 | 处理 |
| --- | --- | --- |
| `SHOW DATABASES` | `sn_dev`、`sn_test`、`sn_prod` | 本系统的三个库，按环境使用（见下表）。`.env` 的 `DB_NAME` 以及下文 SQL 里的 `<库名>` 只填这三个之一 |
| `SHOW DATABASES` | `information_schema`、`mysql`、`performance_schema`、`sys` | 系统库，不配成 `DB_NAME`，也不删除 |
| 只出现在 `SHOW GRANTS` | `sndb` | 库已经不在，只留下 `GRANT ALL PRIVILEGES ON sndb.*`。按库授权不会随删库消失。不对 `sndb` 执行 `USE`、备份或 `DROP DATABASE` |

库名按环境固定：

| 环境 | `DB_NAME` | 说明 |
| --- | --- | --- |
| 开发 | `sn_dev` | 本机开发、联调；`.env.example` 与代码的默认值 |
| 测试 | `sn_test` | 测试环境、业务验收 |
| 正式 | `sn_prod` | 生产环境（Docker 部署）。只按第 7 节上线，不做第 8.1–8.3 节的清库操作 |

自动化测试（`uv run pytest`）另用独立的测试库（默认 `sndb_test_py`，`SN_TEST_DB_NAME` 可改），每次运行都会整库删除重建，**不要把它指向上面三个库**。

`appuser` 在 `sn_dev`、`sn_prod`、`sn_test` 上已是 `ALL PRIVILEGES`，覆盖本系统要的 `SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES`。`ALTER` / `DROP` 用于按月加分区与归档过期痕迹分区。

还要新建库时（名字避开上面的系统库）：

```sql
CREATE DATABASE <库名> CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

新库名不在现有授权里时才需要再授一次（`sn_dev`、`sn_prod`、`sn_test` 以及残留的 `sndb` 都已经授过）：

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES ON <库名>.* TO 'appuser'@'%';
```

不再使用 `sndb` 这个名字时，删掉残留授权，之后 `SHOW GRANTS` 里就不会再出现它：

```sql
REVOKE ALL PRIVILEGES ON sndb.* FROM 'appuser'@'%';
```

连通性自检（`<库名>` 用 `SHOW DATABASES` 里的那个，例如 `sn_dev`）：

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p <库名> -e "SELECT DATABASE(), CURRENT_USER()"
```

### 基线版本

**先理解执行记录**：程序是否执行建表脚本，只看库里的 `flyway_schema_history`（下称"记录表"）：脚本执行完记一笔，下次启动有记录就跳过。程序只看记录，不看库里实际有哪些表。当前只有 `V1__init.sql`（版本 `1`，创建本系统的 `sn_*` 表）。

**基线是什么**：库里已有表、却没有记录表时，程序分不清这些表是不是本系统的，默认拒绝启动。基线就是由人在新记录表里写下的第一笔（类型 `BASELINE`）："版本号小于等于 X 的脚本都当作已执行过，从下一个版本开始执行"。

**两个变量的关系**：`DB_BASELINE_ON_MIGRATE` 决定**要不要**写基线，`DB_BASELINE_VERSION` 决定基线**写成几**。后者只在前者为 `true` 且库处于「有表无记录表」状态时才被读取，其余情况两者都不起作用。

按库的情况选：

| 场景 | `DB_BASELINE_ON_MIGRATE` | `DB_BASELINE_VERSION` | 启动时发生什么 |
| --- | --- | --- | --- |
| A. 空库（一张表都没有） | `false`（默认） | 不写 | 建记录表，执行 V1 |
| B. 共用库：只有其他业务的表，没有 `sn_*` | `true` | `0` | 写基线 0，再执行 V1 建 `sn_*` 表 |
| C. `sn_*` 表已在且与 V1 一致，只缺记录表（如记录表被误删） | `true` | `1`（默认，可不写） | 写基线 1，跳过 V1，不建表 |
| D. 已有 `flyway_schema_history`（已启动过） | 任意 | 任意 | 只执行记录里没有的版本；两个变量都被忽略 |

`.env` 写法：

```bash
# 场景 A：空库
DB_BASELINE_ON_MIGRATE=false

# 场景 B：共用库（库里已有其他业务的表）
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=0

# 场景 C：补记录表
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=1
```

常见错配：

| 错误配置 | 结果 |
| --- | --- |
| 场景 B 没设 `ON_MIGRATE=true` | 拒绝启动，报「已有表但没有 flyway_schema_history」 |
| 场景 B 设了 `true` 但漏了 `VERSION=0` | 按默认 `1` 跳过 V1，启动报表不存在 |
| 场景 C 写成 `0` | 重新执行 V1，报「表已存在」 |

错配后已启动过一次：停服务，删掉 `flyway_schema_history`（及可能已建出的 `sn_*` 表），改好 `.env` 再启动。

首次在共用库上启动前，先查一下：

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
```

| 查询结果 | 处理 |
| --- | --- |
| 没有结果 | 按场景 B 启动 |
| 有同名 `sn_*` 表（不是本系统建的） | V1 会报「表已存在」，只能换库 |
| 有 `flyway_schema_history`（其他系统的记录） | 程序会沿用对方的记录，可能跳过本系统的 V1。只能换库 |

注意：

- 基线只在「有表但没有记录表」的那一次启动写入；之后再改这两个变量无效，要改须先删掉记录表。
- 首次建表中途失败会留下记录表和部分 `sn_*` 表，之后每次启动都报「表已存在」。按 [8.1](#81-删除本系统的表并重建) 删掉 `sn_*` 表与 `flyway_schema_history` 后重启。
- 版本号须为数字（可带点分，如 `1.2`）。无法解析时按 `1` 处理。

## 2. 配置 `.env`

在仓库根目录：

```bash
cp .env.example .env
```

至少填写：

| 变量 | 说明 |
| --- | --- |
| `DB_HOST` / `DB_PORT` / `DB_NAME` | 数据库地址、端口、库名。地址默认 `10.0.200.125:3306`。库名按环境：开发 `sn_dev`（`.env.example` 默认）、测试 `sn_test`、正式 `sn_prod`；换库只改对应一项，重启后端生效 |
| `DB_USER` / `DB_PASSWORD` | 数据库账户（密码原样读取，可含 `#`、`=`；首尾有空格时用引号包住） |
| `DB_URL` | 可选，兼容旧的 JDBC 一行写法；上面单独写了的项优先 |
| `DB_BASELINE_ON_MIGRATE` | 库里已有表但没有 `flyway_schema_history` 时，`true` 才允许启动并写入基线。空库保持 `false` |
| `DB_BASELINE_VERSION` | 基线版本。`1` 跳过 V1；`0` 仍执行 V1。见上文「基线版本」 |
| `SN_SECRET` | 令牌签名密钥，同时用于加密保存各生产组织的 MES 凭证。换成至少 32 位的随机串（`ENVIRONMENT=production` 时为空、为示例值或过短会拒绝启动）。**上线后不要随意更换**：更换后所有人须重新登录，已保存的 MES 凭证无法解密，须在「生产组织」页逐个重新填写并连接测试 |
| `SN_INIT_ADMIN_EMP_NO` / `SN_INIT_ADMIN_PASSWORD` | 空库首次启动自动建的系统管理员的工号、密码（直接可用；`ENVIRONMENT=production` 时密码仍为 `Admin@123` 会拒绝启动） |
| `K3_ACCT_ID` / `K3_APP_ID` / `K3_APP_SECRET` / `K3_USERNAME` | 金蝶账套、第三方应用、用户名（向金蝶管理员获取） |
| `NPM_REGISTRY` | 可选，只在构建 `web` 镜像时传给 `npm ci`。国内访问 `registry.npmjs.org` 中断时设为 `https://registry.npmmirror.com`。见 [4.5](#45-前端依赖安装失败) |

`.env` 含密码，已在 `.gitignore` 中，**不要提交**。进程环境变量优先于 `.env`。

按需调整（默认值即 `.env.example` 里的值，完整清单见 `.env.example` 与 `app/core/config.py`）：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SN_SYNC_ENABLED` | `true` | 定时比对同步开关：按修改时间增量拉取已审核单据并与快照比对（反审核、删除、变更都在这一步发现） |
| `SN_SYNC_INTERVAL_MINUTES` | `10` | 比对同步间隔（分钟） |
| `SN_PUSH_ENABLED` | `true` | MES 推送调度开关；关闭后只能由 MES 拉取（SN 导出页仍可下载） |
| `SN_PUSH_POLL_SECONDS` | `5` | 推送调度轮询间隔（秒） |
| `SN_PUSH_RETRY_INTERVALS_MINUTES` | `1,5,15` | 推送未确认时的自动重试间隔（分钟，逗号分隔，个数即次数）。用尽后批次记为失败、推送中断，由总部「继续推送」 |
| `SN_BATCH_UNCONFIRMED_ALERT_MINUTES` | `30` | 拉取的批次超过该时长仍未回执时产生交付告警 |
| `SN_MES_AUTH_MAX_FAILURES` / `SN_MES_AUTH_LOCK_MINUTES` | `10` / `15` | MES 接口账户密钥认证连续失败该次数后锁定该时长（423 `ACCOUNT_LOCKED`） |
| `SN_MES_PULL_RATE_PER_MINUTE` | `60` | 每个生产组织每分钟最多取批次数，超过返回 429 `RATE_LIMITED`（带 `Retry-After`） |
| `K3_PAGE_RETRIES` / `K3_PAGE_RETRY_SECONDS` | `3` / `10` | 金蝶分页查询失败时的重试次数与间隔（秒） |
| `SN_GEN_SYNC_THRESHOLD` / `SN_GEN_DEFAULT_LIMIT` / `SN_GEN_MAX_PER_RUN` | `5000` / `10000` / `500000` | 生成：超过阈值转后台任务；生成窗口默认单次上限；单次硬上限 |
| `TZ` | `Asia/Shanghai` | 服务器时区：只用于月分区与每日维护任务（`SN_PARTITION_CRON`）的执行时间。业务时间一律按 UTC 存储，页面按各生产组织配置的时区显示 |

已删除的配置项：`SN_ACQUIRE_REQUIRE_SNAPSHOT`、`SN_CALLBACK_MAX`（不再有打印回调与页面领取）。旧 `.env` 里留着也不会读取，可以删掉。

**多实例部署**：推送调度、订单比对同步、每日维护都在进程内运行。推送任务有租约、分区维护有命名锁，多实例同时开启不会重复推送或重复建分区，但会白白轮询；建议只在一个实例上保持 `SN_PUSH_ENABLED=true`、`SN_SYNC_ENABLED=true`，其他实例设为 `false`。

本机没有金蝶也想试用：`SN_DEMO_SEED=true`，空库启动时会灌入 3 个演示生产组织（`110` 越南、`120` 大磡、`130` 泗洪，均未开启对接 MES）、2 条规则、若干生产订单物料行和演示账户 `vn01 / dk01 / sh01`（普通操作员，各授权一个组织）、`query01`（审计员，授权全部 3 个组织），密码 `SN_DEMO_PASSWORD`（默认 `Demo@1234`）。**连公司库时务必为 false。**

## 3. 方式 A：本机一键启动

> 只用于本机开发、演示。**生产环境只允许方式 B（Docker Compose：nginx + api）**：后端端口不对外暴露，来源地址（`X-Real-IP`）与请求号（`X-Request-ID`）由 nginx 填写；直连 8000 端口时这两个请求头由客户端自报，登录留痕里的来源地址不可信。

要求：Python 3.12+（`python` 在 PATH）、Node.js 20+。

```bash
python start.py             # Linux / macOS / Windows（Windows 也可双击 start.bat）
python start.py --rebuild   # 强制重新构建前端
python start.py --port 8001
```

首次会建 `.venv` 并安装后端依赖、`npm install` 并构建前端；之后只有前端源码变化才重新构建。启动后浏览器打开 `http://127.0.0.1:8000`，用 `SN_INIT_ADMIN_EMP_NO` + `SN_INIT_ADMIN_PASSWORD`（默认 `admin` / `Admin@123`）登录；不强制改密，建议登录后在左下角账户菜单里改掉初始密码。

关闭：本窗口 `Ctrl+C`，或 `python start.py --stop` / `stop.bat`（按 `tools/runtime.json` 与端口找进程）。

## 4. 方式 B：Docker Compose

服务器部署使用分支 `sn-center-python`，克隆时只取这一支。仓库：`https://github.com/Createsnow/sn-center.git`。`Dockerfile` 与 `docker-compose.yml` 在仓库根目录。

### 4.1 服务器首次拉取

```bash
git clone -b sn-center-python --single-branch https://github.com/Createsnow/sn-center.git
cd sn-center
cp .env.example .env    # 按第 2 节填好 DB_*（正式环境 DB_NAME=sn_prod）、SN_SECRET、SN_INIT_ADMIN_EMP_NO / SN_INIT_ADMIN_PASSWORD、K3_*
docker compose up -d --build
```

仓库为私有时，`git clone` 需要登录：HTTPS 使用有读权限的 Personal Access Token；已配置 SSH 密钥时改用 `git@github.com:Createsnow/sn-center.git`。

- `api`：FastAPI（Uvicorn），`ENVIRONMENT=production`（日志为单行 JSON），健康检查 `/health/ready`（含数据库连通）；
- `web`：nginx 托管前端，反代 `/api`、`/health`、`/docs`（含 `/openapi.json`）；读超时 600 秒（全量同步、大导出），请求体上限 50 MB（MES 回执、大批量请求）。

Compose 不随附 MySQL，数据库按 `.env` 的 `DB_*` 连接已有库。`.env` 只留在服务器上，更新代码时保留原文件，也不要提交进 Git。

浏览器打开 `http://<IP>`（`WEB_PORT`，默认 80）。停止：`docker compose down`（不要加 `-v`）。

### 4.2 更新代码后重新构建

在部署目录执行，只更新 `sn-center-python`：

```bash
cd sn-center
git pull origin sn-center-python
docker compose up -d --build
```

切换过分支（见 4.3）后，把命令里的 `sn-center-python` 换成当前分支名；当前分支用 `git branch --show-current` 查看。

### 4.3 切换分支

4.1 克隆时用了 `--single-branch`，本地只有 `sn-center-python`，直接 `git checkout 其他分支` 会报 `pathspec ... did not match`，须先把目标分支取下来。以切到 `sn-center-python-v2` 为例，在部署目录执行：

```bash
cd sn-center
git status                                                  # 确认没有本地改动（.env 不在 Git 里，不受影响）
git remote set-branches --add origin sn-center-python-v2    # 登记要拉的分支，每个分支只需做一次
git fetch origin sn-center-python-v2
git diff --stat HEAD origin/sn-center-python-v2 -- app/db/migration .env.example   # 看表结构、配置项有没有变化
git checkout sn-center-python-v2                            # 首次切换会自动跟踪 origin/sn-center-python-v2
docker compose up -d --build
```

- 上面 `git diff` 列出 `app/db/migration/` 有变化：两个分支的表结构不同，按第 8 节「改表」一行处理后再启动；列出 `.env.example` 有变化：对照补齐服务器 `.env` 里的新配置项。
- 之后更新：`git pull origin sn-center-python-v2`，再 `docker compose up -d --build`。
- 切回原分支：`git checkout sn-center-python`，再 `docker compose up -d --build`（同样先看表结构是否一致）。

### 4.4 基础镜像拉取失败

构建停在 `load metadata`，报 `failed to resolve source metadata` 或 `failed size validation`（例如 `nginx:1.27-alpine` 报 `28445 != 27783`）时，先失败的那一个会把同一次构建里的其他基础镜像取消。涉及的镜像是 `python:3.12-slim`、`node:22-alpine`、`nginx:1.27-alpine`（`web` 的 Dockerfile 第 9 行）。本地已有的镜像会显示 `0.0s`，不必重新拉。先清掉构建缓存再构建：

```bash
docker builder prune -af
docker compose up -d --build
```

`docker builder prune -af` 会删掉本机全部构建缓存，下次构建会重新拉取基础镜像并重装依赖。

仍是同一报错时，先单独拉三个基础镜像，再构建：

```bash
docker pull python:3.12-slim
docker pull node:22-alpine
docker pull nginx:1.27-alpine
docker compose up -d --build
```

`docker pull` 也报 `failed size validation` 时，多半是 `/etc/docker/daemon.json` 里的 `registry-mirrors`，或 HTTP 代理改写了响应（清单声明的大小和实际字节数不一致）。把镜像加速配置挪走或换成可用的源后执行 `sudo systemctl restart docker`，再重复上面的 `docker pull`。怀疑代理时，去掉代理再拉一次：

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY docker pull nginx:1.27-alpine
```

### 4.5 前端依赖安装失败

`api` 镜像可以已经构建成功，`web` 停在 `frontend/Dockerfile` 的 `npm ci`：

```text
npm error Exit handler never called!
target web: failed to solve: process "/bin/sh -c npm ci --registry=..." did not complete successfully: exit code: 1
```

这是安装过程中连 `https://registry.npmjs.org` 中断后，npm 自身崩溃，不是 `package.json` 或 lock 文件写错。`package-lock.json` 里的地址仍是官方源；`npm ci --registry=...` 会把这些地址改写到下面配置的源，不用改 lock 文件。

在服务器的 `sn-center/.env` 增加（该文件不提交）：

```bash
NPM_REGISTRY=https://registry.npmmirror.com
```

然后重新构建。`api` 层会走缓存，主要重跑 `web`：

```bash
docker compose up -d --build
```

不想写入 `.env` 时，只对这一次生效：

```bash
NPM_REGISTRY=https://registry.npmmirror.com docker compose up -d --build
```

## 6. 账户与权限

系统有三种页面账户（系统管理员、普通操作员、审计员）和一种接口账户。系统管理员只有一个（工号 `SN_INIT_ADMIN_EMP_NO`），只有它能在「账户」页创建、修改、停用账户、重置密码或密钥、授权生产组织，不能再建第二个系统管理员。账户只停用、不删除，停用后可重新启用。工号 4–32 位字母和数字，唯一，区分大小写；页面账户密码 8–64 位，同时含字母和数字，只能用字母、数字和 `! @ # $ & *`。新建页面账户用创建时设定的密码直接登录，任何时候都不强制改密；本人改密或系统管理员重置密码后，该账户已登录的页面全部退出，用新密码重新登录。同一账户只在最后登录的那个页面有效。

| 角色 | 角色值 | 授权生产组织 | 登录方式 |
| --- | --- | --- | --- |
| 系统管理员 | `admin`（工号 = `SN_INIT_ADMIN_EMP_NO`，唯一） | 不绑定（全部组织） | 页面 |
| 普通操作员 | `operator` | 多选，**至少一个** | 页面 |
| 审计员 | `auditor` | 多选，**至少一个**（只读） | 页面（也可调用 MES 只读接口④⑤核对） |
| MES 接口账户 | `mes` | 必须绑一个生产组织（不要求已开启「对接 MES」） | **不能登录页面**，只能调 `/api/mes/v1` |

普通操作员、审计员没有任何授权组织时不能登录（提示「账户未授权任何生产组织」）。从金蝶同步新增的生产组织**不会自动授权**给任何账户，需要时由系统管理员在「账户」页加上。

系统管理员由首次启动按 `.env` 的 `SN_INIT_ADMIN_EMP_NO` / `SN_INIT_ADMIN_PASSWORD` 自动创建，直接可用；之后若在页面上改过密码，以新密码为准（改 `.env` 不会改库里已有账户，见第 9 节「忘记系统管理员密码」）。密码不写在本文。

**MES 接口账户**（F-01、MES 对接接口文档 2.1）：

- 在「账户」页「MES 接口账户」页签创建，系统生成密钥，当场复制交给 MES 方。密钥用 `SN_SECRET` 派生的密钥加密保存，列表不显示；之后需要时点「查看密钥」再看（每次查看都留痕）。泄露或想换新时点「重置密钥」：旧密钥立即失效，须把新密钥交给 MES 方更新。更换 `SN_SECRET` 后旧密钥无法查看（认证不受影响），需要时重置即可。
- 可填来源地址白名单（IP 或 CIDR，逗号分隔，空 = 不限）。白名单按 nginx 写入的 `X-Real-IP` 判断，生产须走方式 B。
- MES 每次请求带 `Authorization: Bearer <工号>:<密钥>`，不换令牌；连续失败 `SN_MES_AUTH_MAX_FAILURES`（默认 10）次锁定 `SN_MES_AUTH_LOCK_MINUTES`（默认 15）分钟，锁定、解锁都留痕。
- 停用账户后所有请求返回 403 `ACCOUNT_DISABLED`。所绑组织关闭「对接 MES」后，取批不再新建批次，只能取回已有的未确认批次（含转出批次）并回执。

## 7. 上线步骤建议

1. 确认库（正式 `sn_prod`、测试 `sn_test`）、配 `.env`（含 `K3_*` 连接参数），启动一次（自动建表、建 `admin`、建月分区）。从旧版本升级的库须先按 8.1–8.3 之一重建（见第 8 节的「PRD V30 版本说明」）。
2. `admin` 登录（建议先在左下角账户菜单里改掉初始密码）→「生产组织」页 **从金蝶同步**（之后每天 02:10 自动同步一次；名称、启用状态随金蝶更新）。
3. 对接 MES 的生产组织：在「生产组织」页逐个填写 MES 对接配置（接收推送的地址、认证方式与凭证（与 MES 方约定为 TOKEN，凭证填 `工号:密钥`，见《MES 对接接口文档》2.1；HMAC 为备用方式；MES 在内网按来源 IP 等自行限制访问时可选「无认证」，不填凭证）、gzip 压缩（默认关）、单批枚数、推送超时、推送并发、时区），点 **连接测试**（发 `PING` 批次）通过后才能开启「对接 MES」（正式环境建议第 7 步联调通过后再开启）。开启前已分配的已分配号会转为待推送，但不会自动推送，需在 SN 分配页「继续推送」。
4. 「账户」页为每个对接 MES 的组织建 **MES 接口账户**（记下密钥，按需填来源地址白名单；不要求该组织已开启「对接 MES」，未开启时 MES 只能取转出批次、提交回执和只读查询），连同 [MES 对接接口文档](MES对接接口文档.md)、[MES 对接说明](MES对接说明.md) 交给 MES 方；再按需建普通操作员、审计员并授权生产组织。
5. 「生产订单」页 **全量重建** 一次快照（首次上线导入；之后靠定时比对同步与按单据同步），检查附件项次待填写、无客户编码的单据。
6. 「规则库」新建规则（前缀必填且不能与别的规则相同；按需带米数）；给 PI 或物料行选规则在「SN 生成」页做。
7. **MES 联调**：按 PRD 9.2「上线准入：MES 异常场景联调」逐项验证（推送超时重试、同一批重发、回执不符、整批拒收、推送与取批撞车、转出批次、限流、令牌过期等），全部通过后再在正式环境开启对接。MES 方未接入前可先用模拟 MES 演练、用契约测试验收 MES 的接收接口，方法和场景对照表见 [MES 联调指南](<MES 联调指南.md>)。
8. 小范围试产：选一张 PI 走完 生成 → 分配 → 推送 / 拉取 → 回执确认（未对接 MES 的组织在 SN 导出页下载），核对首页看板、交付批次与操作痕迹。

**清库重建：三种做法**

三种做法都只用于开发库 `sn_dev`、测试库 `sn_test`；**正式库 `sn_prod` 不做**。按库里有没有别的系统的表、手上有没有 root 选一种：

| 做法 | 删掉什么 | 保留什么 | 执行账户 | 适用 |
| --- | --- | --- | --- | --- |
| [8.1 删除本系统的表并重建](#81-删除本系统的表并重建) | `sn_` 开头的表和 `flyway_schema_history` | 库、授权、其他系统的表和视图 | `appuser` | 库里还有其他系统的表（共用库）；或只想重建本系统的表 |
| [8.2 清空整库并重建](#82-清空整库并重建) | 库里所有表、视图、存储过程、函数、事件 | 库、授权 | `appuser` | 库只给本系统用，要一个空库，但没有 root |
| [8.3 删除整库、重建并授权](#83-删除整库重建并授权) | 整个库 | 账户 | `root` | 库只给本系统用，要从建库开始重来（字符集按新建时设定）；或库不再使用，只删不建 |

> **三种做法都会清空本系统的全部数据，只能从备份恢复**：账户（含 MES 接口账户）、生产组织与 MES 对接配置、规则、订单快照与出号台账、号池、交付批次、转单与转组织记录、操作痕迹。

命令约定（三节通用）：

- 下文的 `10.0.200.125` 是公司 MySQL，`sn_test` 是示例库名：照抄前把 `sn_test` 换成要处理的库（`sn_dev` 或 `sn_test`）。
- `mysql`、`mysqldump` 是 MySQL 客户端命令，Linux / macOS 终端、Windows 命令提示符、PowerShell 都能执行；`-p` 表示回车后输入密码。
- 「登录 MySQL」后出现 `mysql>` 提示符：把 SQL 整段粘贴进去回车执行，做完输入 `exit` 退出。用 Navicat / DBeaver 时，连到同一个库，在查询窗口执行同样的 SQL。
- 8.1、8.2 的删除 SQL 会先检查当前库：不是 `sn_dev` / `sn_test` 时只输出 `REFUSED: current database is not sn_dev / sn_test`，什么也不删。

### 8.1 删除本系统的表并重建

只删本系统的表：`sn_` 开头的表与迁移记录表 `flyway_schema_history`。库里其他系统的表、视图原样保留。删完启动一次，程序按 `V1__init.sql` 重新建表。演示阶段改了 `V1__init.sql` 后用这种做法（已有的库不会重新执行 V1，日志只有 `migration_checksum_mismatch` 警告）。

**第 1 步：停止服务**（所有实例都要停，否则删表会被正在跑的请求或定时任务卡住）

```bash
# 方式 A 本机：启动窗口按 Ctrl+C，或执行
python start.py --stop
# 方式 B Docker：在部署目录执行（不要用 down -v）
docker compose stop api
# 方式 C 开发：在 uvicorn 窗口按 Ctrl+C
```

**第 2 步：备份整个库**

```bash
mysqldump -h 10.0.200.125 -P 3306 -u appuser -p --single-transaction --no-tablespaces --routines --triggers --events --result-file=backup_sn_test.sql sn_test
```

生成 `backup_sn_test.sql`（同名文件会被覆盖）。`--no-tablespaces` 避免 `appuser` 没有 `PROCESS` 权限时报错。要恢复时执行：

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"
```

**第 3 步：登录 MySQL，确认库和连接**

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test
```

```sql
SELECT DATABASE() AS current_db;
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = DATABASE();
```

`current_db` 必须是要处理的库。连接列表里应当只有你自己这一条（`command` 为 `Query`）；还有别的连接说明服务没停干净，回到第 1 步。

**第 4 步：预览要删的表**

```sql
SELECT table_name, table_type,
       IF(table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history', 'DROP', 'KEEP') AS action
FROM information_schema.tables
WHERE table_schema = DATABASE()
ORDER BY action, table_name;
```

- `DROP`：本系统的表，第 5 步会删。当前版本是 34 张 `sn_` 表加 `flyway_schema_history`；旧版本留下的 `sn_` 表（例如 `sn_batch`、`sn_key`、`sn_print`）也在其中，一并删除。
- `KEEP`：其他系统的表和视图，不动。
- `DROP` 里出现不是本系统建的表时停下，不要继续。

**第 5 步：删表**

```sql
SET SESSION group_concat_max_len = 1000000;
SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP TABLE IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_type = 'BASE TABLE'
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
SELECT @drop_sql;
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;
```

`SELECT @drop_sql` 显示的就是实际执行的那条 `DROP TABLE`。本系统不建外键，删除顺序无所谓；`sn_audit` 是分区表，连分区一起删掉。

**第 6 步：确认已删干净**

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND (table_name LIKE 'sn\_%' OR table_name = 'flyway_schema_history');
-- 应当返回 Empty set

SHOW FULL TABLES;
-- 剩下的都是其他系统的表。记下有没有剩下的表，第 7 步要用
exit
```

**第 7 步：设置 `.env` 的基线**（最容易出错的一步）

| 第 6 步 `SHOW FULL TABLES` 的结果 | `.env` | 原因 |
| --- | --- | --- |
| `Empty set`（库已经空了） | `DB_BASELINE_ON_MIGRATE=false` | 空库直接执行 V1 |
| 还有其他系统的表 | `DB_BASELINE_ON_MIGRATE=true` 和 `DB_BASELINE_VERSION=0` | 不设：拒绝启动，报「已有表但没有 flyway_schema_history」；设成 `1`（默认）：跳过建表，启动报表不存在 |

库里还有其他系统的表时，`.env` 写：

```bash
DB_BASELINE_ON_MIGRATE=true
DB_BASELINE_VERSION=0
```

设错了且已经启动过一次：停服务，从第 3 步重做（会删掉已写入的 `flyway_schema_history` 和已建出的 `sn_` 表），改好 `.env` 再启动。

**第 8 步：启动并检查**

```bash
# 方式 A 本机
python start.py
# 方式 B Docker（部署目录）
docker compose up -d
docker compose logs --tail=200 api
```

启动日志里应当依次出现 `partition_added`（建月分区）、`bootstrap_admin`（建系统管理员）、`sn_center_ready`。浏览器打开 `http://<服务器>:8000/health/ready`（方式 A）或 `http://<服务器>/health/ready`（方式 B），应返回 `{"status":"ok","db":"mysql"}`。再登录 MySQL（同第 3 步）确认：

```sql
SELECT installed_rank, version, type, script, success
FROM flyway_schema_history
ORDER BY installed_rank;
-- 空库：1 行      1 | 1 | SQL | V1__init.sql | 1
-- 基线 0：2 行    1 | 0 | BASELINE | << Flyway Baseline >> | 1
--                 2 | 1 | SQL | V1__init.sql | 1

SELECT COUNT(*) AS sn_tables
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_name LIKE 'sn\_%';
-- 34

SELECT emp_no FROM sn_user;
-- 只有 .env 里的 SN_INIT_ADMIN_EMP_NO（默认 admin）
```

**第 9 步：重新初始化数据**

1. 用 `.env` 里的 `SN_INIT_ADMIN_EMP_NO` + `SN_INIT_ADMIN_PASSWORD` 登录（旧账户都已删除），建议先改掉初始密码。
2. 按[第 7 节](#7-上线步骤建议)第 2–6 步重做：同步生产组织、填 MES 对接配置并连接测试、建 MES 接口账户（新密钥要重新交给 MES 方）、全量重建订单快照、配规则库、创建普通操作员和审计员账户并授权生产组织。
3. 只看演示效果时，可在 `.env` 设 `SN_DEMO_SEED=true` 再启动，自动放入演示生产组织、订单和账户（**连公司库时务必为 false**）。

### 8.2 清空整库并重建

删掉库里**所有**表、视图、存储过程、函数、事件，库本身和授权保留，得到一个空库；启动时程序按空库直接建表。用 `appuser` 就能做，不需要 root。

> **会删掉库里所有系统的数据。** 先确认这个库只给本系统用，或库里其他系统的东西确实都不要了。拿不准时用 [8.1](#81-删除本系统的表并重建)。

**第 1 步：停止服务**，命令同 [8.1 第 1 步](#81-删除本系统的表并重建)。库里还有别的系统在用时，也要先停掉它们。

**第 2 步：备份整个库**

```bash
mysqldump -h 10.0.200.125 -P 3306 -u appuser -p --single-transaction --no-tablespaces --routines --triggers --events --result-file=backup_sn_test.sql sn_test
```

要恢复时执行 `mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"`。

**第 3 步：登录 MySQL，确认库和连接**

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test
```

```sql
SELECT DATABASE() AS current_db;
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = DATABASE();
```

`current_db` 必须是要处理的库；连接列表里应当只有你自己这一条。

**第 4 步：预览库里有什么**

```sql
SELECT table_type AS object_type, COUNT(*) AS cnt
FROM information_schema.tables WHERE table_schema = DATABASE() GROUP BY table_type
UNION ALL
SELECT routine_type, COUNT(*)
FROM information_schema.routines WHERE routine_schema = DATABASE() GROUP BY routine_type
UNION ALL
SELECT 'EVENT', COUNT(*)
FROM information_schema.events WHERE event_schema = DATABASE();

SHOW FULL TABLES;
```

第一条按类型计数：`BASE TABLE` 表、`VIEW` 视图、`PROCEDURE` 存储过程、`FUNCTION` 函数、`EVENT` 事件。本系统只有表（34 张 `sn_` 表加 `flyway_schema_history`）；`SHOW FULL TABLES` 里有别的表又不确定能不能删时停下，改用 8.1。

**第 5 步：删除所有表和视图**

```sql
SET SESSION group_concat_max_len = 1000000;
SET FOREIGN_KEY_CHECKS = 0;

SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP VIEW IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_type = 'VIEW';
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SELECT IF(DATABASE() IN ('sn_dev', 'sn_test'),
          IFNULL(CONCAT('DROP TABLE IF EXISTS ', GROUP_CONCAT('`', table_name, '`' SEPARATOR ', ')), 'DO 0'),
          'SELECT ''REFUSED: current database is not sn_dev / sn_test'' AS error')
INTO @drop_sql
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_type = 'BASE TABLE';
PREPARE stmt FROM @drop_sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SET FOREIGN_KEY_CHECKS = 1;
```

先删视图、再删表。其他系统的表之间可能有外键，所以先关外键检查，删完再打开（只影响当前连接）。

**第 6 步：删除存储过程、函数、事件**（第 4 步里这三类都没有时跳过）

先生成删除语句：

```sql
SELECT CONCAT('DROP ', routine_type, ' IF EXISTS `', routine_name, '`;') AS drop_sql
FROM information_schema.routines WHERE routine_schema = DATABASE()
UNION ALL
SELECT CONCAT('DROP EVENT IF EXISTS `', event_name, '`;')
FROM information_schema.events WHERE event_schema = DATABASE();
```

把结果里的每一行（形如 ``DROP PROCEDURE IF EXISTS `xxx`;``）复制出来，在同一个连接里粘贴执行。执行前再看一眼 `SELECT DATABASE();`，这些语句不带库检查。

**第 7 步：确认已是空库**

```sql
SHOW FULL TABLES;
-- 应当返回 Empty set
SELECT COUNT(*) AS routines FROM information_schema.routines WHERE routine_schema = DATABASE();
-- 0
SELECT COUNT(*) AS events FROM information_schema.events WHERE event_schema = DATABASE();
-- 0
exit
```

**第 8 步：检查 `.env`**

空库启动时直接执行 `V1__init.sql`，**不读取** `DB_BASELINE_ON_MIGRATE`、`DB_BASELINE_VERSION`（`.env` 里留着也没关系）。`DB_NAME` 仍是这个库，不用改。

**第 9 步：启动并检查**，命令和检查 SQL 同 [8.1 第 8 步](#81-删除本系统的表并重建)。`flyway_schema_history` 应当只有 1 行 `1 | 1 | SQL | V1__init.sql | 1`，`sn_tables` 为 34，`sn_user` 里只有系统管理员。

**第 10 步：重新初始化数据**，同 [8.1 第 9 步](#81-删除本系统的表并重建)。

> 以后这个库里又放进了其他系统的表，再清本系统的表时就要按 8.1 做，并设 `DB_BASELINE_ON_MIGRATE=true`、`DB_BASELINE_VERSION=0`。

### 8.3 删除整库、重建并授权

用 `DROP DATABASE` 删掉整个库，再新建同名空库并给 `appuser` 授权；启动时程序按空库直接建表。比 8.2 更彻底：库里的所有对象一次删掉，字符集和排序规则按新建时设定。删库、建库、授权用 `root`（或有建库、删库和 `GRANT OPTION` 权限的账户）执行。

> **整个库连同其中所有系统的数据一起删除。** 先确认这个库只给本系统用。拿不准时用 [8.1](#81-删除本系统的表并重建)。

**第 1 步：停止服务**，命令同 [8.1 第 1 步](#81-删除本系统的表并重建)。库里还有别的系统在用时，也要先停掉它们。

**第 2 步：备份整个库**

```bash
mysqldump -h 10.0.200.125 -P 3306 -u appuser -p --single-transaction --no-tablespaces --routines --triggers --events --result-file=backup_sn_test.sql sn_test
```

要恢复时，先做完第 5、6 步（建库、授权），再执行 `mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "source backup_sn_test.sql"`。

**第 3 步：用 root 登录 MySQL，确认库、授权和连接**

```bash
mysql -h 10.0.200.125 -P 3306 -u root -p
```

```sql
SHOW DATABASES;
SHOW GRANTS FOR 'appuser'@'%';
SELECT id, user, host, command, time
FROM information_schema.processlist
WHERE db = 'sn_test';
```

- `SHOW DATABASES` 里要有 `sn_test`。系统库 `information_schema`、`mysql`、`performance_schema`、`sys` 和正式库 `sn_prod` 不能删；`sndb` 只剩授权、库已不存在（见第 1 节），不用删。
- 连接列表应当为空。还有连接说明服务没停干净：回到第 1 步，或对列出的连接执行 `KILL <id>;`。

**第 4 步：删库**

```sql
DROP DATABASE IF EXISTS sn_test;
```

**第 5 步：重建空库**

```sql
CREATE DATABASE sn_test CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**第 6 步：给 appuser 授权**

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES ON sn_test.* TO 'appuser'@'%';
```

- 这些是本系统要的权限（`ALTER` / `DROP` 用于按月加分区和归档痕迹分区）。按库授权不随删库消失，原有的 `ALL PRIVILEGES` 还在，再授一次也无妨，只会补上缺的。
- 新的 MySQL 实例上还没有 `appuser` 时，先建账户再授权，密码与 `.env` 的 `DB_PASSWORD` 一致：`CREATE USER 'appuser'@'%' IDENTIFIED BY '<密码>';`

**第 7 步：确认库和授权**

```sql
SHOW CREATE DATABASE sn_test;
-- 应含 utf8mb4 和 utf8mb4_0900_ai_ci
SHOW GRANTS FOR 'appuser'@'%';
-- 应有 sn_test 上的授权
exit
```

再用 `appuser` 连一次，确认能连上、库是空的：

```bash
mysql -h 10.0.200.125 -P 3306 -u appuser -p sn_test -e "SELECT DATABASE(), CURRENT_USER(); SHOW FULL TABLES;"
```

应显示 `sn_test` 和 `appuser@%`，且没有任何表。

**第 8 步：检查 `.env`**：`DB_NAME` 仍是这个库，不用改；空库启动不读取 `DB_BASELINE_ON_MIGRATE`、`DB_BASELINE_VERSION`。

**第 9 步：启动并检查**，命令和检查 SQL 同 [8.1 第 8 步](#81-删除本系统的表并重建)。`flyway_schema_history` 应当只有 1 行 `1 | 1 | SQL | V1__init.sql | 1`，`sn_tables` 为 34，`sn_user` 里只有系统管理员。

**第 10 步：重新初始化数据**，同 [8.1 第 9 步](#81-删除本系统的表并重建)。

**只删库、不再使用**（例如废弃的测试库，或本机自动化测试留下的 `sndb_test_py`）：做完第 1–4 步即可，不做第 5 步以后的步骤；`.env` 的 `DB_NAME` 不能再指向这个库。想把残留授权也清掉时，用 root 执行（权限名照 `SHOW GRANTS` 显示的写，显示 `ALL PRIVILEGES` 就写 `ALL PRIVILEGES`）：

```sql
REVOKE ALL PRIVILEGES ON sn_test.* FROM 'appuser'@'%';
```

## 9. 常见问题

| 现象 | 处理 |
| --- | --- |
| 构建报 `failed size validation` 或 `failed to resolve source metadata` | 见 [4.4 基础镜像拉取失败](#44-基础镜像拉取失败) |
| `web` 构建报 `Exit handler never called!`，停在 `npm ci` | 见 [4.5 前端依赖安装失败](#45-前端依赖安装失败)。在 `.env` 设置 `NPM_REGISTRY=https://registry.npmmirror.com` 后重新 `docker compose up -d --build` |
| 启动报 `Can't connect to MySQL server` | 检查 `DB_HOST` / `DB_PORT`、防火墙、账户密码 |
| 启动报「已有表但没有 flyway_schema_history」 | 库里已有其他表。本系统表尚未建立时设 `DB_BASELINE_ON_MIGRATE=true`、`DB_BASELINE_VERSION=0`。表已与 V1 一致、只缺迁移记录时版本设为 `1`。见上文「基线版本」 |
| 升级后报表或列不存在（如 `sn_delivery_batch`、`sn_line_count`、`sn_rule.factory_code`），日志有 `migration_checksum_mismatch` | `V1__init.sql` 已按 PRD V31 重写，旧库不会重跑 V1，也没有就地升级脚本。按 [8.1 删除本系统的表并重建](#81-删除本系统的表并重建) 删掉 `sn_` 表与 `flyway_schema_history`，或按 [8.2 清空整库并重建](#82-清空整库并重建) / [8.3 删除整库、重建并授权](#83-删除整库重建并授权) 得到空库后重新启动 |
| 同步报 `金蝶配置缺失` | `.env` 中 `K3_*` 未填 |
| 比对同步显示失败 | 「生产订单」页统计栏看最近一次比对同步的原因（与手动同步的报错相同）；快照未改动，修好后等下个周期或点「立即比对同步」 |
| 订单页附件项次、米数、PO 一直为空 | 系统按固定字段读取：附件项次 `FTERM`、长度 `Flength`（明细）、PO `F_HX_PO`（表头），见 [生产订单查询接口](k3/k3cloud_query.md)。先在金蝶里确认这张单这几个字段确有值；有值仍为空时向金蝶实施方确认字段标识是否变了（改字段名须改代码 `app/services/k3.py`）。附件项次金蝶确实没有时在生成页填写（米数可不填，默认 000） |
| 生成页附件项次、米数输入框置灰 | 该物料行已经生成过号。号还没分配时，在「已生成」页签撤销这一行的生成（物料行上或勾选后底部「撤销」，流水排在其后的物料行会一并撤）后再改；已分配的不能再改 |
| 首页「推送中断」有数字 | 某批次自动重试（默认 1、5、15 分钟）用尽仍未确认。到「SN 查询 → 交付批次」看失败原因（地址错、认证失败、超时、报文过大、整批拒收等），处理后在 SN 分配页或批次详情点「继续推送」：先用原批次号、原内容重推，再推后续的号。MES 方确认已全部入库的可「人工确认」（原因、依据必填）；MES 没处理过的批次可「作废」 |
| 批次失败原因为「回执不符」（`RECEIPT_MISMATCH`） | 推送时 MES 响应中的回执与批次对不上（批次号不一致，或 `code` 不是 `OK` / `NG`），批次详情里写明差异。请 MES 方修正后用同一批次号重新提交回执（③）；这种批次 MES 已处理过，不能作废。MES 拉取后提交的回执不合法时只返回 400，批次仍为未确认，不会出现这种失败 |
| MES 取批返回 429 `RATE_LIMITED` | 该组织每分钟取批超过 `SN_MES_PULL_RATE_PER_MINUTE`（默认 60）次。请 MES 方按 `Retry-After` 等待、`remaining = 0` 时停止轮询；确需更高频率时调大该值 |
| MES 调用返回 423 `ACCOUNT_LOCKED` / 403 `IP_NOT_ALLOWED` | 连续认证失败被锁定，等 `SN_MES_AUTH_LOCK_MINUTES` 分钟后自动解锁，或核对密钥（必要时重置密钥）；来源地址不在白名单时在「账户」页修改白名单 |
| 关闭「对接 MES」被拒（`MES_DISABLE_BLOCKED`） | 该组织还有运行中的推送任务或未确认 / 失败的批次：先续推、等待回执，或人工确认 / 作废后再关闭 |
| 换了 `SN_SECRET` 后推送全部认证失败 | 已存的 MES 凭证用旧密钥加密，无法解密：在「生产组织」页逐个重新填写凭证并连接测试 |
| 同步报 `金蝶登录失败` | 账套 / AppId / AppSecret / 用户名不对，或服务器到 `10.0.200.42` 不通 |
| 生成、分配提示生产组织不存在或已禁用 | 「生产组织」页从金蝶同步（生产组织只来自金蝶，不能手工新增）；金蝶里已禁用的组织不能作为分配、转入目标 |
| 生成提示「预演失效」 | 期间有人生成过同一 PI，或数量 / 规则 / 订单变了：重新预演 |
| 生成提示「正在生成，请稍后再试」 | 同一 PI 已有生成任务在跑，等它结束（首页或生成页可见进度）。若是服务在后台生成途中重启过，重启后该任务会自动标为失败（`INTERRUPTED`，号已整批回滚），重新预演后生成即可 |
| 启动报「SN_SECRET 未设置 / 仍是示例值 / 长度不足 32 位」 | `ENVIRONMENT=production`（Docker 方式默认如此）时要求强密钥：在 `.env` 设置 `SN_SECRET`，可用 `python -c "import secrets; print(secrets.token_hex(32))"` 生成；更换后所有人需重新登录 |
| 请求返回「参数不合法」（422 `VALIDATION`） | 参数格式不对，或 PI、SN、生产组织、客户、物料等编码超过 64 位；修正后再提交，重试无效 |
| 提示「PI 正在进行其他操作」（`PI_BUSY`） | 同一 PI 的生成、撤销、分配、转单、转组织确认同一时刻只能做一个，等前一个结束再试 |
| 忘记系统管理员密码 | 其他管理员不能重置系统管理员。在服务器上以 `SN_RESET_ADMIN=true` 启动一次：工号 `SN_INIT_ADMIN_EMP_NO` 被重置为 `SN_INIT_ADMIN_PASSWORD`、启用并改回管理员（不存在则新建，留痕）；**随后立即去掉该变量再重启** |
